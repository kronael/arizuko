strategy

GitOps for agents: from multi-channel orchestration to a declarative product platform.

One sentence: Arizuko is GitOps for agents. Persona, skills, ACL, routes, secrets, diaries, decisions — all in git. The gateway commits per turn. Containers run against the working tree. The store is derived cache. Audit, fork, distribute — native git verbs.

This page documents the research direction: from today's multi-channel orchestration platform to tomorrow's declarative product platform. Four tiers map competitive gaps to shippable features. Each agent research topic (tools/security, memory, subagents, project management) projects into concrete platform capabilities.

Why GitOps?

  • State lives in git, not the database. agents.toml (products + deployments), acl/, routes/, skills/, personas/, MEMORY.md, .diary/, decisions/, secrets (age-encrypted). The store becomes an operational cache — rebuildable from git + inbound message log.
  • Gateway is the only writer. Agents act through MCP; gateway sees every state-changing call and commits at turn boundary. Prevents "agent forgot to commit" bugs. One commit per turn with JSON sidecar listing events.
  • Audit = git log. Fork = git worktree. Distribute = git push. No bespoke versioning machinery. Signed commits + branch protection = compliance trail.
  • Products are TOML files in shared repos. Same shape as Terraform modules. arizuko product fetch <url> includes via submodule. One repo per instance (krons, marinade, sloth); products defined elsewhere.

Defensible wedge

The combination, not any single axis. Each axis has a stronger specialist alone; nobody has all four:

  1. Multi-channel persistent team agent — 11 adapters in tree (Telegram, Discord, WhatsApp, Slack, email, Bluesky, Reddit, X/Twitter, LinkedIn, web chat, webhooks)
  2. Per-folder agent identity — PERSONA + skills + MEMORY + .diary + ACL + secrets; filesystem as tenant boundary
  3. Operator-owned footprint — Go daemons in Docker, one KVM guest per turn, one store endpoint the operator runs or rents; no ClickHouse, no Redis, no managed control plane
  4. Uniform MCP+REST per resource — agent-first protocol, REST as impedance match for external tools

Real gaps (we lose today)

  • Observability — every daemon exports OTLP when OTEL_EXPORTER_OTLP_ENDPOINT is set, but journalctl + dashd is still not Langfuse.
  • Sandbox strength — the turn runs in one KVM guest, so the boundary is a hypervisor and the agent's kernel is not the host's. The gap is runed's own container, which compose runs as root with NET_ADMIN, SYS_ADMIN and apparmor=unconfined because AppArmor's default denies the staging tree's mount(2). A profile that permits just that one mount is unwritten.
  • Product abstraction — no arizuko product clone, no manifest, no registry.
  • No K8s / cloud-provider templates — no Helm chart, no operator; the turn path still pins routd and runed to one node.
  • Evals at scale — specs/10/1-self-healing-loop.md is a draft; none of the judge/evaluate/repair loop is built.

GitOps architecture

Three layers. Truth shifted out of the database.

GIT TREE   source of truth: versioned, signed, distributed
  agents.toml            products + deployments
  acl/ routes/ skills/ personas/
  MEMORY.md  .diary/  decisions/
  secrets/               age-encrypted blobs or vault refs
  turns/                 per-turn markdown, the trace
    ↓ derive
STORE      operational cache: one endpoint, rebuildable from git + input log
  messages queue + cursors
  indexes                fast routing and dispatch
  in-flight turn state
  materialized projections (graph view)
    ↓ projects
GUESTS     ephemeral: a projection of git@HEAD into runtime
  read the working tree at turn start
  MCP over vsock to routd's per-group socket
  gateway commits state changes at turn end

arizuko apply = read agents.toml from git → diff against the store → reconcile.
Audit = git log. Fork = git worktree. Distribute = git push.

The path forward

Four tiers map gaps to shippable capabilities. GitOps direction influences every tier.

Tier A
4 weeks · Declarative composition
  • agents.toml schema (products + deployments) — committed to git, source of truth
  • arizuko plan / arizuko apply verbs (Terraform-for-agents)
  • deployments table in the store (cache; rebuildable from git)
  • Three canonical product templates: oncall, support, sales-assist
  • Folder/user-scope secrets layering (BYOA primitive) — specs/5/14-credentials.md
  • Spec: specs/5/8-yaml-manifests.md — it decides the opposite of this card: the store is authoritative, the YAML manifest is a dump/import artifact, and no agents.toml is a source of truth
Tier B
6 weeks · Monitoring + sandbox + git-as-event-log
  • Drop the bespoke events table. Gateway becomes the only git writer; commits per turn with sidecar event list
  • Projection function over working tree + the store's hot path → graph view for plan/dashd/fork/OTLP
  • OTLP-out via OpenLLMetry → Langfuse self-host (operator's choice)
  • gVisor RuntimeClass under existing Docker — superseded. The turn is a KVM guest as of 6/41 step 4; the unwritten piece is a narrow AppArmor profile for runed itself.
Tier C
10 weeks · Distribution + proof product
  • Product registry = git repo of TOML files
  • arizuko fork <folder> --at <commit> = git worktree add + spawn container against that worktree
  • Eval primitive — Haiku-judge as gated post-turn hook
  • Ship oncall agent end-to-end through the whole pipeline as the proof
Tier D
When deals demand it · Enterprise
  • Helm + multi-node — federation via git remote basically free
  • Signed product manifests + cosigned images
  • OPA/Rego as policy alternative

Bridge: agent research → platform features

For each major research topic, how it becomes a shippable arizuko feature and which tier it slots into.

Tools & security
  • Tier A: Per-product tool profiles in agents.toml (minimal/coding/messaging/full)
  • Tier B: Hermes threat-pattern scanner (932 LOC) → product sandbox profiles with gVisor. Tap (credential injection proxy) already exists — ships with Tier B.
  • Research insight: Muaddib's host/guest tool split is cleanest privilege model; smolagents' code-first approach eliminates schemas. NanoClaw's IPC proxy = tap component.
Memory
  • Tier A Phase C: BYOA primitive = bring-your-own-pgvector as alternative to in-folder markdown. ElizaOS pgvector pattern, OpenClaw hybrid (vector + BM25).
  • Tier C: Memory projection function: MEMORY.md + .diary/ + facts/ → unified queryable surface across all products.
  • Research insight: All converge on markdown as substrate; differ on write safety (LLM-editable vs operator-only).
Subagents
  • Tier A: Product mixins in agents.toml. Compose a support product from (base-agent + slack-responder + escalation-child) fragments.
  • Already shipped: delegate_group, escalate_group, observe_group MCP tools. Per-folder isolation is one guest per turn, per folder.
  • Research insight: Six trust models compared; we already ship the strongest (a hypervisor boundary per turn, per folder).
Project management
  • Tier C: Oncall agent proof — autonomous PM loop (Stripe ships 1,300 PRs/week from Slack messages, zero human interaction).
  • Tier B: Git-as-event-log enables post-turn eval hooks (Aeon's Haiku-scores-Opus quality gate).
  • Research insight: Autonomy spectrum maps to isolation strength. More autonomous = stronger boundaries needed.
Building blocks
  • Tier A: Doom loop prevention (max-turns cap, explicit continue required). Network isolation (per-spawn egress allowlist).
  • Tier B: Harness engineering — per-product test harness in TOML. Blueprints = product templates.
  • Research insight: 13 patterns distilled; most map directly to agents.toml declarative config.
Aeon
  • Tier C: Self-healing batch loop = git-as-database (already Tier B direction) + Haiku quality gate (eval primitive) + reactive triggers (scheduled tasks already exist) + category repair playbooks (product templates).
  • All mechanisms already designed. Tier C integrates them.
  • Research insight: GitHub Actions runtime is the container orchestration we already have (Docker Compose).

What we will not do

  • Runtime-graph fantasy — The interior of an agent is Turing-complete; don't model it. The organizational layer (products + deployments + folders + ACL + channels) IS a graph, expressed as files in git. No bespoke projection beyond git checkout.
  • Pure event-sourcing — ActiveGraph (arxiv:2605.21997) overreaches. Hard parts (bit-perfect replay across stochastic LLM calls, cheap-prefix-share fork, schema migration via events) are future work. We need enough history to analyze + improve + audit — not bit-perfect replay. Git already ships this.
  • K8s pre-emptive — Docker on a host the operator owns wins on operator burden until deals demand multi-node; the Kubernetes page says which daemons can move and which cannot. Federation via git remote is Tier D (when revenue forces it).

Open questions

  1. Inbound message storage — Per-day JSONL in git, or fully hot in the store? Lean per-day in git for replay-enough.
  2. Crash recovery — Between a store write and a git commit, what's the recovery protocol? Idempotent reapply on restart?
  3. Fork lifecycle — Does forked branch get its own container? Same DB? Separate cache? Spec the lifecycle.
  4. Operator UX — arizuko log, arizuko diff, arizuko revert wrappers — what's the surface?
  5. dashd admin write — Currently writes the store directly. Under GitOps: commit → apply, or commit-immediate-apply? Pick a default.
  6. Tracing granularity vs audit granularity — Commit-per-turn loses sub-turn lineage; sidecar restores it; is sidecar enough or do we need per-event commits on a side branch?
  7. Is "GitOps" the right term? Too K8s-coded? Substitute "git-native"? Sharper positioning vs Argo CD ("Argo CD for AI agent fleets") or against it?

Trace vs projection distinction:

  • Trace = git log (history, queryable)
  • Projection = working tree at HEAD (current shape, queryable as graph)
  • Fork = git worktree add on a sha + spawn container
  • Replay-enough = git checkout <sha> + walk the tree
  • Audit = signed commits + branch protection
