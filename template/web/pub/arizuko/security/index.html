arizuko › security

security

arizuko treats every agent run as untrusted code. Three controls are enforced today: a per-folder egress allowlist at a forward proxy started fresh for each turn on that guest's own tap, OAuth-gated identity stamped at the edge with an ES256 transit bearer, and a credential broker that keeps every capability token out of the guest. The sections below mark each one shipped or planned.

1. Threat model

The agent is the threat surface. Claude Code runs with bypassPermissions inside its guest and can shell out, fetch URLs, run generated scripts — under normal operation. Under prompt injection, RCE in a tool call, or an adversarial skill, that same scope is what the attacker gets. The platform assumes this and enforces around it.

The primary threat is cross-tenant: a compromised agent in one group reaching another group's files, secrets, messages, or network. arizuko closes that path structurally — the turn is the isolation boundary. Every turn runs in its own KVM guest with its own bind-mounted share (groups/<folder>/ at /home/node/), its own tap with a proxy-only rule set, its own DB view through the per-turn MCP socket, and its own egress allowlist. solo/inbox and corp/eng see none of each other — not because policy says so, but because they are separate kernels on separate taps with separate mount sets. bypassPermissions inside the guest doesn't change that: there is no path from the agent's shell to another group's data.

The guest itself is already per-turn fresh: each agent invocation runs in its own KVM guest, booted for one turn read over vsock and powered off after, so no compromised process survives into the next turn. What persists across turns is the group folder under /home/node/ — conversation history, diary, skills, and the Claude Code session jsonl — re-loaded each turn so context accumulates. That persisted state, not a long-lived process, is the same-group cross-turn surface: a compromised turn could poison files the next turn reads. A fresh kernel per turn closes that risk at the kernel level, not only at the network and mount level: one guest per turn is the only substrate.

The system surface (operator, split daemons, store) sits outside the agent boundary. It trusts the operator, the chat-platform adapter ingress authenticated by a rotating ES256 service:<adapter> token, and the unified acl + acl_membership tables resolved through auth.Authorize. Inbound web traffic is OAuth-gated at proxyd; proxyd proves the channel to each backend with an ES256 service:proxyd bearer and then trust-stamps the X-User-* headers, verified by every backend via auth/middleware.go.

The full trust-zone diagram and per-boundary mechanism table is in SECURITY.md in the repo. Per-daemon files ship next to the source when a daemon's threat model outgrows a row (e.g. ipc/SECURITY.md for the MCP socket and SO_PEERCRED check).

2. egress — one proxy per turn, sealed below the kernel

Every turn's KVM guest has exactly one network interface, a tap whose rule set is static: accept the guest's own proxy port, drop everything else in both directions. runed starts one egress forward proxy on that tap's host side, with the folder’s allowlist baked in, waits for its /health, and only then boots the guest. The proxy dies with the turn. This is not a setting: runed refuses to start at all if the egress binary is missing.

The proxy filters; the tap rules confine. A process that ignores HTTPS_PROXY and opens a raw socket finds every packet dropped below the kernel it runs on. Each proxy serves exactly one address, that guest's, and answers 403 to every other peer and every host off the list. CONNECT is tunnelled, never decrypted. The whole path, refused branches included, is one figure on the egress page.

The default seed is anthropic.com and api.anthropic.com. Operators extend per folder, and resolution walks the folder ancestry:

arizuko network <instance> allow <folder> api.github.com

The wildcard * is appended only for a folder holding the egress grant or an elevated /root turn.

3. Secrets never enter the guest

A credential takes one of two doors. The four model keys enter the guest's env at spawn, because the harness process spends them and there is no tool call to hang a broker on. Every other token stays on the host: when a connector call needs GITHUB_TOKEN, routd resolves it, puts it in the outbound request, and hands the agent the answer with the value scrubbed. Infra keys like SECRETS_KEY never leave the host .env.

With the litellm package the model key stays out too: the gateway holds it, and each turn gets its own MODEL_GATEWAY_KEY, minted by routd and deleted when the turn ends. Values in the secrets table are encrypted at rest (AES-256-GCM, required SECRETS_KEY). The two doors are drawn on the secrets page.

4. No DNS filter needed — there is no resolver to filter

The guest carries HTTP_PROXY/HTTPS_PROXY/NO_PROXY and no resolver at all, so a host name is meaningful only inside a CONNECT line to the proxy. That closes the side channel a shared-kernel container left open: there, /etc/resolv.conf pointed at docker’s embedded resolver, which forwarded upstream from the host namespace regardless of the container’s own routing, so getent hosts example.com returned real addresses even with no proxy environment set and no route to the internet.

The tap closes the rest: its rule set drops UDP/53 the same as every other packet that is not to the proxy, both directions. A name never reaches netfilter, and the proxy is the one matcher. An IP literal is a different matter: the allowlist matches names, the matcher skips IP entries, and a literal destination therefore matches nothing — so an allowlist row written as an address grants no access.

Status today: shipped, and closed rather than scoped. Cost accepted: a tool inside the guest that resolves a name itself before connecting fails; which tools those are is being measured, not guessed.

5. proxyd — auth at the edge

Every request from outside the docker network passes through proxyd. It terminates TLS, verifies the OAuth-issued JWT (refresh-token cookie fallback), strips any client-supplied identity headers, then re-stamps its own and attaches a transit bearer:

X-User-Sub:    google:alice
X-User-Name:   Alice
X-User-Groups: solo/inbox,corp/eng/sre
Authorization: Bearer <ES256 service:proxyd token>

The bearer is an authd-minted ES256 token whose subject is pinned to service:proxyd. Every backend verifies it via auth/middleware.go — ProxydTransit checks the signature, expiry, issuer, and that subject pin against authd's public JWKS. Only on that proof does a backend trust the stamped X-User-* headers. There is no per-request HMAC signature; the transit bearer is what makes a request a genuine “came through proxyd” call. Without the subject pin, any holder of a valid authd token reaching a backend directly could forge X-User-* and be treated as that user — covered in SECURITY.md § Identity header trust.

One OAuth login covers GitHub, Google, Discord, and Telegram — account linking unifies them under one auth_users.sub. Per-route auth modes (public / user / operator) are declared per-daemon in service config and written into proxyd_routes by arizuko generate. Public paths today: /pub/*, /health, /chat/* and /hook/* (route-token bearer, per-token rate bucket).

Adapter ingress is a separate trust boundary — channel adapters reach routd over the internal docker network only. Each adapter exchanges a bootstrap secret, AUTHD_SERVICE_KEY, for a service:<adapter> ES256 token that rotates roughly hourly (chanlib/chanlib.go), and every channel-registration call to routd carries that token as the bearer. routd's channel gate verifies it against authd's JWKS and requires a service: subject prefix (routd/channels.go channelAuth); with no verifier configured (local dev) the gate is open. On first registration, routd pins a channel name to the (source IP, verified subject) pair, not to the token itself — the token rotates, so pinning the raw bearer would reject every legitimate re-register after a refresh. proxyd does not see channel traffic; channels do not see web traffic.

6. Configuration surface — REST and MCP

The destination: every security configuration (secrets, allowlists, grants, routes, invites) is reachable two ways, sharing one handler per resource.

  • Outside the box (REST). Federated per-daemon /v1/<resource>, OAuth-gated through proxyd. Each daemon owns its tables and exposes them; dashd aggregates the UI on top.
  • Inside the agent (MCP). The same operations registered as MCP tools on the per-group unix socket, gated on the same acl rows. Both faces call auth.Authorize; only the identity source differs — a JWT subject for REST, the socket's folder for MCP.

Nothing is granted by position in the folder tree. A folder starts with the messaging verbs and nothing else; operations that spawn new state, mutate ACLs, or read audit data require a row somebody delegated, and that row's scope glob is the boundary it may act inside. An action with no matching row is refused — there is no fallback that quietly grants it.

Status: shipped and uniform. Each daemon exposes its resources over both surfaces from one hand-written handler — REST (/v1/<resource>, OAuth-gated through proxyd) and MCP (per-group unix socket). The MCP tools/list a session sees is filtered by grants: a tool registers only when the folder is granted its scope, so an agent sees exactly what it may call. External REST tools ([[connector]], transport = "rest") join the same surface, gated on ext:<service>:<operation>.

7. What arizuko does not do

  • No output classification. No jailbreak detector, no response scanner. The boundary is what the agent can reach, not what it can say.
  • Encryption at rest covers secrets only. The secrets table is encrypted (AES-256-GCM, required SECRETS_KEY; see SECRETS_KEY); the rest of /srv/data/<instance>/ is plain files. Operator trusts disk + FS perms.
  • No enterprise SSO yet. SAML 2.0 and OIDC federation are not built. Today the only identity entry points are OAuth (GitHub, Google, Discord, Telegram) and the invite-token onboarding flow.
  • No defense against host root. The operator owns the host. arizuko does not try to keep secrets from the person running it.
  • No revocation list for tokens. JWT access TTL is 15m, refresh 30d. Short TTL is the revocation primitive today.
  • No IPv6 for the guest. runed disables IPv6 on each turn's tap before the link comes up, because the tap's rule set is IPv4 only. A turn whose tap cannot be sealed fails.
