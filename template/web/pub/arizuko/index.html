arizuko

arizuko hosts many specialized agents on one platform — each a folder with its own persona, skills, and memory, each shaped by talking to it. You say what you want; an LLM edits the files that are the agent. The conversation is the console.

arizuko is simple on purpose, and the simplicity is the reason it is flexible. An agent is a folder of plain files. A route is a row in the store, the database of the instance, that sends the messages of one chat to one folder. A grant is a row that lets one person or agent do one action. You read a folder as files and a row with the arizuko command.

Daemons do the work around the folders. A daemon is a program that runs in the background all the time, and its name ends in “d”. routd decides which folder answers a message. runed runs each turn in its own KVM guest, a small virtual machine that exists for that one turn. A turn is one run of an agent. authd signs identity tokens. One directory on your server holds the folders and the store. You change an agent in chat, then read the result in its files.

Three commands create, configure and start an instance. They work after the setup guide builds the images and sets up the store server:

arizuko create demo --product slack-team   # makes /srv/data/arizuko_demo, prints the keys to set
$EDITOR /srv/data/arizuko_demo/.env         # the keys that create printed
arizuko run demo                            # starts the instance

The setup guide adds the build, the store server and the chat connection. See also all products and the source on GitHub. arizuko is free under the MIT license.

krons, at https://krons.fiu.wtf, is the reference deployment. The maintainers run it, every release deploys there first, and it serves these docs at https://krons.fiu.wtf/pub/arizuko/.

a product is an agent you install and own

A product is a folder of persona, skills, routes and knowledge. The catalog has fifteen products. Eleven install with arizuko create --product, and four describe a setup you build yourself. Three of them:

Slack team agent

Slack · shared workspace

One agent per channel: channel-scoped persona, per-teammate memory, email ingest, a usage dashboard.

Repo worker (Atlas)

GitHub · single-developer

Your own repositories, worked by an agent that reads the diff instead of the description and cites path:line. Merge is held for you, every time.

Reality agent (Rhias)

Telegram · single-user

A personal agent that holds the threads of your life across weeks: named situations, reflection on demand, a monthly sweep over its own diary.

Twelve more sit in the catalog: a support desk, a personal assistant with memory, a PM board, a domain researcher, a public price bot. Each is the same engine with different folder contents.

many agents run side by side

Those three are three folders in one instance, not three installs. The design bet is that a focused persona with a small set of skills stays on task, and a do-everything assistant drifts. arizuko runs many focused agents in one instance, and each folder keeps its own grants and secrets.

  • Isolation that keeps memory. Each folder has its own persona, memory and secrets. Every turn runs in a fresh KVM guest. Outbound traffic leaves through the egress proxy of that guest, a gate that opens only the host names the folder allows. The network interface of the guest drops every packet that skips the proxy. A support agent can face strangers on a public channel and keep its own history. A normal turn never receives the home folder of another agent.
  • Agents hand work along the tree. A folder path such as corp/eng/sre is the org chart. An agent hands a prompt down to a child folder or up to its parent folder, and every link needs a grant. The child runs its own turn in its own KVM guest, so each sub-agent gets a machine of its own. A child folder runs in its own guest gives the limits.
  • People move between agents. Send @acme/sales on its own, and the whole chat goes to the sales agent. A bare @ sends it back. You change agents without changing the app you chat in.

every event takes the same six steps

A Slack mention in #eng, a scheduled task, a webhook and an email all take these steps in this order. The Slack mention ends as a reply in the Slack thread.

  1. Event. Anything that happens becomes one row in the inbox: a chat message, a call from another service, a clock tick.
  2. Routing. The route table maps the event to the folder that answers. The first matching route wins.
  3. Agent. The folder loads its persona, skills and memory.
  4. Authorization. One question decides: may this person or agent do this action here? A grant row answers it.
  5. Turn. A fresh KVM guest runs the agent once and powers off. The guest sees only the files shared into it and reaches only the hosts its proxy allows.
  6. State. The store keeps the rows, and the folder keeps the files.

you own the files

An instance is one directory. Everything the system is lives in it:

/srv/data/arizuko_demo/
├── .env                 tokens and config
├── store/               every row, on the store server of the instance
│   ├── extenddb/        the server’s config and certificate
│   └── extenddb_db/     its PostgreSQL data
├── groups/
│   ├── main/            one agent
│   │   ├── PERSONA.md   who it is
│   │   ├── CLAUDE.md    how it operates
│   │   ├── .claude/skills/  what it can do
│   │   ├── facts/       what it has learned
│   │   └── diary/       what happened, dated
│   └── ops/             a second agent, same shape, its own memory
└── web/pub/             public pages, one folder per agent, and these docs

Edit the persona file, and the next turn uses it. Stop the instance, and one tar of the directory is a complete backup: every row, every memory, the secrets and the site. The platform does not version the folders. Put groups/ under git yourself, and each change the agent makes shows as a diff, the list of lines that changed. The agent image ships git and a commit skill.

what arizuko needs and what it does not do

  • One Linux host with Docker and KVM. The daemons run as Docker Compose services, and each turn is a KVM guest, so the host needs /dev/kvm. Compose on one host is the tested path. A Helm chart for Kubernetes exists, and no cluster has run it.
  • You pay for the host and the model. arizuko is free software. The model provider bills the key you supply. The default network allowlist opens anthropic.com and api.anthropic.com.
  • Self-hosted only. arizuko has no managed control plane and no hosted service.
  • Sized for agent teams. arizuko serves teams of agents behind chat channels, not consumer traffic.
  • Not a search system. arizuko has no document connectors, no vector index and no choice of model provider per task. One harness serves the whole instance: Claude Code by default, or codex or pi through ARIZUKO_BACKEND.
  • The parts a deploy needs. The store server runs ExtendDB over PostgreSQL. A daemon without a store key exits, and runed does not start without /dev/kvm. A minimal deploy is the store server, authd, routd, runed, timed and one channel adapter. The web daemons start when you set WEB_PORT, and onbod starts when you turn onboarding on.
  • Egress is not a switch. runed starts one egress proxy per turn and refuses to start without the proxy binary. The guest has no DNS resolver, so a compromised turn can call only the hosts you allowed.
  • Two faces, one handler. An agent calls platform actions as MCP tools, the Model Context Protocol for agent tools. A person or script calls the same actions as REST, ordinary web requests at /v1/<name>. Actions that only an agent uses in a turn, such as reply and send, exist as MCP alone.
  • Connectors keep the credential on the host. One TOML block gives an agent the API of another service as a tool. The call leaves from the host, the host adds the secret, and the secret never enters the guest. Connectors has the detail.
