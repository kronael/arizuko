Repo worker setup

gitd receives GitHub webhooks. Register a repo, org or App source to connect events to a group. Outbound comments use GITHUB_TOKEN and carry the token's user identity. GitHub App installation-token issuance and refresh are not implemented.

1. Seed the group

On a running instance, create the group with the GitHub product. The agent's persona and facts belong to that group. 

arizuko group <inst> add web:dev dev --product github

2. Set the environment

arizuko packages <inst> add gitd

The package enables gitd's compose fragment and webhook routes. Set these values in <data-dir>/.env:

VariableRequiredWhat it is
GITHUB_TOKENyesenables comments as the token's user; requires access to the watched repositories
WEB_HOSTyespublic HTTPS host for webhook delivery and approval links

3. Enable the github connector

Add the [[connector]] block from template/connectors/github.toml to <data-dir>/connectors.toml once. GitHub's hosted MCP server supplies the tools. Store a separate folder-scoped token for the broker. The agent never receives that credential. 

arizuko secret <inst> set folder:dev GITHUB_TOKEN --value <token>
arizuko group <inst> grant folder:dev dev "mcp:github_<tool>"

Grant each required tool by its exact name. Scope the token to the repositories and operations the agent needs.

4. Register the webhook source

Register a source to create a sealed secret and seed its route rows: 

arizuko github <inst> add repo me/proj dev

Paste the printed URL and secret into the repository's Settings → Webhooks. Select application/json and the events the agent should receive. Comments and new issues or PRs trigger turns. Other events go to dev#observe as context. Addresses use github:me/proj/pr/<n> or github:me/proj/issue/<n>. Within one repository, each PR or issue has its own topic.

For an installed GitHub App, register an App source:

arizuko github <inst> add app <slug> dev

Paste the URL and secret into the App's webhook settings. Install the App on the repositories it should watch. One App source receives events from all its installations. Source registration does not supply an outbound App token.

5. Hold what you want to sign off

Merge is the one that matters. A hold grant stops the call and asks you: 

arizuko group <inst> grant folder:dev dev "hold:mcp:github_merge_pull_request"

A hold does not grant access to the tool.

Approvals reach you two ways with no chat platform running: /approve <id> wherever you talk to it, and the link the held notice carries to /dash/approvals/.

6. Restart the instance

sudo systemctl restart arizuko_<inst>

7. Fill in the facts

facts/repo.md ships as a placeholder and must be replaced. Put the exact build, test and lint commands in it, name the generated directories that must never be hand-edited, and write down what “done” means for a change.

A wrong fact is worse than a missing one, because the agent cites it. Treat a stale line in facts/ as a bug with a filename.

8. Verify

arizuko send <instance> dev "what are the build and test commands here?" --wait

A correct answer quotes facts/repo.md. If it guesses from the source tree instead, the product seed did not land in that folder.

Then run its own case suite against the live agent: 

anteval run <host> --cases <data-dir>/groups/dev/eval
