Company brain

This is a shape, not a template. No tree ships for it in ant/examples/, so there is no --product company-brain to run. The page describes how the product is assembled from the primitives; every command below is one you run yourself. The catalog marks which products ship as templates.

A network of per-team agents, each with its own inbox and memory, reading intake from Slack, email, and webhooks — writing briefs, escalating issues, coordinating across folders on schedule.

The company brain acts on knowledge and does not search it

The company brain is the action layer over the knowledge of an organisation. Agents read intake, write daily briefs, escalate issues to the right team and coordinate across the folder tree.

It is not a search engine, and it is not a pipeline that syncs Confluence into a vector store. For semantic search over 10,000 documents, add Onyx or a retrieval skill. The company brain then acts on the results of that retrieval. Three limits explain this.

The company brain is the complex end of the product range. The other end is the supermarket price agent, with one folder, one route and no hierarchy. Every step of the pipeline exists in both, and the supermarket uses each step at its smallest.

The folder tree follows the org chart

Folder tree as org chart
Each team gets its own group folder. corp/eng/sre is the SRE team, corp/pm is product management, and corp/intake is the shared desk for inbound triage. You decide the depth and the shape of the tree.
Memory for each team
Each folder holds a PERSONA.md with the behaviour of the team agent, a facts/ knowledge base with runbooks, decisions and reference documents, and a diary. Context stays in the team until an agent delegates or escalates.
Scheduled briefs
A timed task starts a turn on a schedule: a daily standup summary, a weekly digest or an on-call handoff. The agent writes the brief to facts/ and sends it to the channel. No cron on the host is necessary, because the scheduler is part of the stack.
Many input sources
Slack messages, inbound email through emaid, webhook POSTs from GitHub, Sentry, Linear or PagerDuty, and WebDAV file drops all arrive as events in a team inbox. Routes map the source JID to the right folder.
Escalation and delegation
The SRE agent can call escalate_group to reach corp/eng. A triage agent can call delegate_group to give work to the responsible team. These are normal MCP tool calls.
Observed channels
A Slack channel can route to corp/eng#observe, so the agent collects context and does not reply to every message. find_messages searches the stored messages, and the agent uses the relevant ones when a task or a question arrives.
ACL for each folder
The acl rows of a folder decide what its agent can do: which MCP tools and which external hosts. The operator manages them in /dash/ or with the CLI.

A Sentry alert becomes a Slack reply in one turn

[Sentry webhook fires]
  POST /hook/<token>
  X-Sentry-Hook-Signature: <signature>
  {"issue": "OOM in billing-worker", "level": "error"}

  ↓ Event lands in corp/eng/sre/oncall

  ↓ Agent reads alert + facts/runbooks/billing-worker-oom.md
  ↓ Checks find_messages for recent occurrences (last 7 days)
  ↓ Drafts a reply: root cause, recommended action, prior incidents

  ↓ Sends to #eng-oncall Slack channel
  sre-bot   OOM in billing-worker — seen 3x this week.
             Last fix (2026-05-30): heap limit too low post-deploy,
             fix was rolling restart + config bump. Runbook:
             /dav/corp/eng/sre/facts/runbooks/billing-worker-oom.md
             Action: restart billing-worker pod + check HEAP_MAX.

  ↓ Creates task: "Raise HEAP_MAX cap — billing-worker"
  ↓ Logs to diary: alert handled, task created

The agent read the alert, found the runbook, found earlier incidents, wrote a reply and made a task in one turn. No person had to route the alert.

Each team is a folder with its own routes

corp/
  intake/           # triage inbox — all unrouted inbound lands here first
  eng/
    sre/
      oncall/       # on-call rotation folder; per-shift diary
    review/         # code review requests from webhook
  pm/               # product management briefs, roadmap context
  sales/            # deal summaries, CRM webhook ingest
  finance/          # budget alerts, expense webhook

Part of the route table:

seq  match                                        target
-10  chat_jid=hook:corp/eng/sre/oncall/sentry     corp/eng/sre/oncall
0    room=T012ABCD/channel/C0ONCALL               corp/eng/sre/oncall
0    room=T012ABCD/channel/C0ENG                  corp/eng#observe
5    chat_jid=hook:corp/eng/github                corp/eng/review
10   (empty match, catches everything)            corp/intake

arizuko group add writes the Slack rows at seq 0. Each hook and the catch-all is one arizuko route corp add <match> <target> --seq N, as the setup shows. A lower seq comes first.

Three limits apply

Know what the product does not do before you deploy it:

No connector sync
You fill facts/ by hand, over WebDAV, or through agents that a webhook starts and that write to it. No OAuth crawler for Confluence, Notion or Google Drive exists. If your knowledge base is in those systems, a person or a connector skill must copy the relevant parts into Markdown files in facts/. The product works for hundreds of documents. It fails for corpora of enterprise size without a connector.
No embeddings and no vector search
The agent searches facts/ with grep. find_messages is a BM25 search in memory over the stored messages, not over facts/. For hundreds of well-structured Markdown documents, this is fast and reliable. For tens of thousands, add Onyx or a retrieval skill: the agent calls the retrieval service over MCP, gets ranked results and acts on them.
No permissions from source systems
The operator manages the ACL for each folder. arizuko does not copy Jira roles, Salesforce profiles or Confluence space permissions. A user who can read a Jira board but has no access to the arizuko folder of that team cannot reach the agent. The two permission systems are separate, and the operator manages both.

Each team sees only its own folder

Your server
The knowledge bases, briefs and agent state of all teams are files under /srv/data/arizuko_<name>/groups/. The messages are on the store server of the instance.
Outbound paths
The channel adapters, Slack and email, for bot replies, and Anthropic for model calls. Other traffic, such as webhooks and external APIs, goes through egress for each folder.
Folder isolation
Other teams cannot read the memory, facts and diary of a team, unless an agent delegates or the operator grants read access across folders. The SRE agent does not see the sales context, and sales does not see the SRE runbooks.

The setup makes folders, routes and tasks

arizuko create corp
arizuko packages corp add slakd
$EDITOR /srv/data/arizuko_corp/.env     # SLACK_BOT_TOKEN, SLACK_SIGNING_SECRET, ANTHROPIC_API_KEY

# make the team folders: the JID first, then the folder; the route is written for you
arizuko group corp add 'slack:T012ABCD/channel/C0ONCALL' corp/eng/sre/oncall

# webhook intake: make a hook token and route its JID
arizuko token corp issue webhook corp/eng/sre/oncall sentry
arizuko route corp add 'chat_jid=hook:corp/eng/sre/oncall/sentry' corp/eng/sre/oncall --seq -10

# add the knowledge base of each team
$EDITOR /srv/data/arizuko_corp/groups/corp/eng/sre/oncall/facts/runbooks/billing-worker-oom.md
arizuko run corp

# schedule briefs on the tasks page of /dash/, or ask the agent:
# "schedule a task: every weekday at 09:00, write a daily standup summary"
