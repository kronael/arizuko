connectors

A connector hands the agent a tool it did not ship with — a DNS registrar, an internal API, somebody else’s MCP server — and does it without letting the credential into the guest. You write one TOML block. routd makes the call on the host, fills the secret in on the way out, and hands the agent back the response body and nothing else.

the shape of the problem

An agent that can only talk is not much use. Sooner or later it needs to read a DNS zone, file a ticket, or query your own service. The usual way to arrange that is to put an API token in the guest and let the agent call curl. That works, and it means the token is now readable by anything the agent runs — including whatever it was asked to summarise from a web page.

A connector splits the two halves. The agent gets the tool; the host keeps the credential. From inside the guest there is an MCP tool called cloudflare_dns_list, and no CF_API_TOKEN anywhere in the environment, the filesystem, or /proc.

one block, two transports

Every connector is one [[connector]] block, and transport picks which dispatch path it takes. A field is absent for a transport rather than meaning two different things:

  • mcp (the default when you leave transport out) — the far side is already an MCP server over HTTP. It discovers its own catalogue, so you declare no tools. It reads headers only, because that is where an HTTP MCP server takes its credential.
  • rest — the far side is an ordinary REST API that has never heard of MCP. You declare one [[connector.tool]] per endpoint, and you may use all three credential sinks.

Connectors reach out over HTTP, never over stdio. That is not a simplification — MCP’s OAuth flow is defined for the HTTP transport only, so a stdio connector could never carry a user’s own authorisation.

a rest connector, end to end

# connectors.toml in the instance directory
[[connector]]
name      = "cloudflare"
transport = "rest"
url       = "https://api.cloudflare.com/client/v4"
secrets   = ["CF_API_TOKEN"]
headers   = { Authorization = "Bearer {secret:CF_API_TOKEN}" }

  [[connector.tool]]
  name        = "dns_list"
  description = "List DNS records for a Cloudflare zone."
  scope       = "ext:cloudflare:dns:read"
  method      = "GET"
  path        = "/zones/{zone_id}/dns_records"

The agent sees a tool named cloudflare_dns_list — <provider>_<tool>. It takes one argument, zone_id, because {zone_id} is a path placeholder and those are schema’d for you. Any argument that is not a path placeholder becomes the query string on a GET or DELETE, and the JSON body on a POST, PUT or PATCH.

where the secret goes

There is no auth-method enum to pick from. You write {secret:KEY} at the spot in the request where the value belongs, and it is rendered per call into one of three sinks:

sinklooks like
headers{ Authorization = "Bearer {secret:CF_API_TOKEN}" }
query{ ApiKey = "{secret:NAMECHEAP_KEY}" }
body{ apikey = "{secret:PB_API_KEY}", secretapikey = "{secret:PB_SECRET}" }

“Bearer” is a literal prefix you typed, not a mode the loader understands. That is the whole reason a provider with an unusual scheme needs no new case, and a provider wanting four credentials is written exactly like one wanting one.

Three things happen to the value on every call, and they are worth knowing before you debug one:

  • It is looked up for the triggering user. Their own key beats the folder default, so one connector serves a team whose members each hold their own token.
  • It is scrubbed out of the response before the text reaches the agent, so an API that echoes your key back does not leak it into the transcript.
  • A declared key the store resolves to nothing has its whole entry dropped. An unset secret sends no header at all, rather than sending the literal text {secret:CF_API_TOKEN} upstream and getting a confusing 401.

The key is a row in routd’s secrets table, set with arizuko secret or at /dash/me/secrets. It is not the daemon environment. One name can live in both places with different values: GH_TOKEN in the instance .env is what a daemon process holds, and GH_TOKEN in a folder’s secrets is what the connector sends. The connector reads only the folder’s row, through the broker, so a token found in .env says nothing about what the connector has.

the grant decides who sees it

Each tool carries a scope shaped ext:<service>:<operation>. Registration is grant-filtered like every other MCP tool: the tool joins tools/list only where Authorize(folder, scope) passes. A folder without the grant does not see a refusal — it sees no such tool. The call-time check runs anyway, as defence in depth.

So one connectors.toml can declare your whole external surface, and which folder gets which piece of it is a grants question, decided per folder:

arizuko group <instance> grant main/infra 'ext:cloudflare:dns:read' 'main/infra/**'

what ships already

arizuko carries descriptors for four DNS registrars — Cloudflare, Porkbun, Gandi and Namecheap — each covering list, create and delete. They do nothing until the operator sets that provider’s token, because a descriptor is a shape, not a credential.

limits worth knowing

  • A connector is host-side, so the guest’s egress rules do not apply to it. The call leaves from routd, not from the agent’s network. Decide what a folder may reach with the grant, not with the allowlist.
  • The response body is all the agent gets. No status line, no headers. A connector that needs the agent to branch on a status code is the wrong shape for the job.
  • An mcp connector trusts the far side’s catalogue. It discovers tools at connect time, so a server that adds a tool gives your agent that tool the next time it connects — gated by the grant, but not by anything you wrote down.
