connectors

A connector gives the agent a tool it did not ship with, and keeps the credential out of the guest. The tool can be a DNS registrar, an internal API or the MCP server of another party. You write one TOML block. routd makes the call on the host, inserts the secret into the outbound request, and gives the agent the response body and nothing else.

The agent gets the tool and the host keeps the credential

An agent that can only talk is of little use. It must read a DNS zone, file a ticket or query your own service. The usual method puts an API token in the guest and lets the agent call curl. That works, but then anything the agent runs can read the token, including text it was asked to summarise from a web page.

A connector splits the two halves: the agent gets the tool, and the host keeps the credential. Inside the guest, an MCP tool called cloudflare_dns_list exists, and no CF_API_TOKEN exists in the environment, the filesystem or /proc.

One block has one of two transports

Every connector is one [[connector]] block, and transport picks its dispatch path. A field that one transport does not use is absent for it, and no field has two meanings:

mcp
The default when you leave out transport. The far side is already an MCP server over HTTP. It reports its own tool list, so you declare no tools. It reads only headers, because an HTTP MCP server takes its credential there.
rest
The far side is an ordinary REST API with no MCP support. You declare one [[connector.tool]] per endpoint, and you can use all three credential sinks.

Connectors use HTTP, never stdio. The MCP OAuth flow is defined only for the HTTP transport, so a stdio connector could never carry the own authorisation of a user.

A REST connector needs one block and one tool entry

# connectors.toml in the instance directory
[[connector]]
name      = "cloudflare"
transport = "rest"
url       = "https://api.cloudflare.com/client/v4"
secrets   = ["CF_API_TOKEN"]
headers   = { Authorization = "Bearer {secret:CF_API_TOKEN}" }

  [[connector.tool]]
  name        = "dns_list"
  description = "List DNS records for a Cloudflare zone."
  scope       = "ext:cloudflare:dns:read"
  method      = "GET"
  path        = "/zones/{zone_id}/dns_records"

The agent sees a tool named cloudflare_dns_list, in the form <provider>_<tool>. The tool takes one argument, zone_id, because {zone_id} is a path placeholder, and the loader writes the schema for placeholders. Any other argument becomes the query string on a GET or DELETE, and the JSON body on a POST, PUT or PATCH.

A placeholder puts the secret where it belongs

No list of auth methods exists. You write {secret:KEY} at the place in the request where the value belongs, and routd renders it on each call into one of three sinks:

sinkexample
headers{ Authorization = "Bearer {secret:CF_API_TOKEN}" }
query{ ApiKey = "{secret:NAMECHEAP_KEY}" }
body{ apikey = "{secret:PB_API_KEY}", secretapikey = "{secret:PB_SECRET}" }

“Bearer” is a literal prefix that you typed, not a mode that the loader knows. For this reason, a provider with an unusual scheme needs no new case. A provider with four credentials is written in the same way as a provider with one.

Three things happen to the value on every call:

  • routd looks it up for the triggering user. The own key of the user wins over the folder default, so one connector serves a team whose members each hold their own token.
  • routd scrubs it from the response before the text reaches the agent. An API that echoes your key does not leak it into the transcript.
  • If a declared key resolves to nothing, routd drops the whole entry. An unset secret sends no header at all. It does not send the literal text {secret:CF_API_TOKEN} upstream, which would cause a confusing 401.

The key is a row in the secrets table of routd, set with arizuko secret or at /dash/me/secrets. It is not in the daemon environment. One name can exist in both places with different values. GH_TOKEN in the instance .env belongs to a daemon process, and GH_TOKEN in the secrets of a folder is what the connector sends. The connector reads only the row of the folder, through the broker, so a token in .env says nothing about what the connector has.

The grant decides which folder sees the tool

Each tool carries a scope in the form ext:<service>:<operation>. Grants filter registration as for every other MCP tool: the tool joins tools/list only where Authorize(folder, scope) passes. A folder without the grant gets no refusal. It does not see the tool. The check at call time runs anyway, as a second defence.

So one connectors.toml can declare all your external APIs, and a grant per folder decides which folder gets which tool:

arizuko group <instance> grant folder:main/infra 'main/infra/**' 'ext:cloudflare:dns:read'

Four DNS registrars ship as descriptors

arizuko ships descriptors for four DNS registrars: Cloudflare, Porkbun, Gandi and Namecheap. Each covers list, create and delete. A descriptor does nothing until the operator sets the token of that provider, because a descriptor is a shape, not a credential.

Connectors have three limits

Egress rules of the guest do not apply
The call leaves from routd on the host, not from the network of the agent. Use the grant, not the allowlist, to decide what a folder can reach.
The agent gets only the response body
No status line and no headers reach the agent. If the agent must branch on a status code, a connector is the wrong tool.
An mcp connector trusts the tool list of the far side
It discovers tools at connect time. If the server adds a tool, your agent gets that tool on the next connect. The grant still applies, but nothing you wrote lists the new tool.
