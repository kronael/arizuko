a turn, end to end

A turn is everything that happens between a person typing a message and the reply of the ant in their chat. Two daemons do the work: routd owns the conversation, runed owns the guest, and one HTTP call joins them.

The whole path fits in one figure

Read the figure from top to bottom. Each box names the function that does the work, so you can open the file and check it.

routd decides and runed runs

The adapter posts the message to routd, and routd writes it with PutMessage. No other function appends a message. For this reason, one cursor per chat, agent_cursor, is enough to record what the agent has seen. A worker for each folder then picks the folder and builds the prompt. Before the worker calls runed, it binds the MCP socket of the folder and records the session id that the turn resumes. The order matters for two reasons. An agent whose first tool call finds no socket answers nothing. A turn that stops halfway must find its session on the next attempt.

runed answers POST /v1/runs in one of three ways:

  • If the folder already has a live guest, the new messages go in as a steer, and the running turn reads them.
  • If the guest cap is full, runed answers busy. routd tries again after 4 seconds and doubles the wait each time, up to one minute.
  • Otherwise, runed starts a new KVM guest for this one turn.

The guest runs one program before the agent

The guest boots a pinned kernel with one small program as PID 1, guest-init. guest-init mounts the folder at /home/node, starts socat on /run/ipc/gated.sock and runs the agent. A tool call goes from the agent to that socket, then over vsock to a bridge on the host, then into routd. The host kernel stamps the vsock CID of the guest on every packet, and the bridge accepts only the CID of its own guest. That stamp is the credential of the turn, so the agent has no token that a shell command could leak.

A child folder runs in its own guest

guest-init builds the root of the guest with overlayfs. The release rootfs is the read-only lower layer, and a tmpfs of 512 MiB in RAM is the writable upper layer. The folder home at /home/node and the web directories come from the host and keep what the agent writes. A write anywhere else is gone when the guest powers off. [kernel/guest-init/main.go]

A turn runs in one folder, and a folder has at most one live guest. To give work to a sub-agent on a second machine, an agent uses a second folder:

  • register_group creates a child folder and its first route. The caller needs a grant on mcp:register_group with a scope that covers the new folder. No count limits the children of a folder.
  • delegate_group writes the prompt as a message on the chat of the target folder. routd resolves that chat to the folder and calls runed, and runed boots a guest for the child. The child turn has its own session. Its reply goes to the chat that the parent names in chatJid.
  • escalate_group writes the prompt on the chat of the parent folder in the same way, and the parent answers through the child.

The parent turn and the child turn run at the same time, in two guests. MAX_CONCURRENT_CONTAINERS, default 5, caps the live guests of the whole instance. Past the cap, runed answers busy and routd tries again.

Three more limits apply:

  • The grant scope of delegate_group sets which folders an agent can name. A grant on corp/eng/** keeps it inside that subtree.
  • Both hand-off tools refuse a call with a depth argument of 1 or more. No code passes a depth to the child turn, so the check does not stop a chain of hand-offs.
  • Claude Code subagents that the agent starts with its Task tool run inside the guest of the turn. They cannot reach runed, so they get no guest of their own.

The reply goes out through the adapter

The agent calls reply or send, and routd delivers the message through the /send endpoint of the adapter. If the agent finishes without a call to either tool, the text of its final result is the reply. While the agent works, the chat shows typing. On a channel that can edit messages, one status line changes in place. When the guest powers off, runed returns the outcome on the same HTTP call that started the turn.

A failed delivery stays as a pending row, and a sweep tries it again with a longer gap each time. A turn that stops without a reply runs again up to three times. The exception is a failure that runed marks terminal, because a retry cannot fix it. Examples are a VMM that does not start and an exhausted model quota.

Five pages explain the parts of the figure

  • routing: how routd picks the folder, the second box.
  • topics: which session a turn resumes, and how a fork copies one.
  • retries: what happens when the guest stops before it answers.
  • live progress: the status line on the left of the figure.
  • runed: the guest, its files and its network.
