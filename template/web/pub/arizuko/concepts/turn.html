a turn, end to end

You’ve met the ant. Here is everything that happens between someone typing a message and the ant’s reply showing up in their chat. Two daemons do the work: routd owns the conversation, runed owns the guest, and one HTTP call joins them.

the whole path on one page

Read it top to bottom. Every box names the function that does the work, so you can open the file and check.

routd decides, runed runs

The adapter posts the message to routd, and routd writes it with PutMessage. Nothing else ever appends a message, which is why one cursor per chat, agent_cursor, is enough to say what the agent has seen. A worker per folder then picks the folder and builds the prompt. Before it calls runed, it binds the folder’s MCP socket and writes down the session id the turn will resume. The order matters: an agent whose first tool call finds no socket answers nothing, and a turn killed halfway must still find its session next time.

runed answers POST /v1/runs one of three ways. If the folder already has a live guest, the new messages go in as a steer and the running turn picks them up. If the guest cap is full, it says busy and routd tries again a few seconds later, doubling the wait up to a minute. Otherwise it boots a fresh KVM guest for this one turn.

inside the guest

The guest boots a pinned kernel with one tiny program as PID 1, guest-init. It mounts the folder at /home/node, starts socat on /run/ipc/gated.sock, and runs the agent. A tool call goes from the agent to that socket, over vsock to a bridge on the host, and into routd. The host kernel stamps the guest’s vsock CID on every packet, and the bridge accepts only its own guest’s CID. That stamp is the turn’s credential: there is no token for an agent with a shell to leak.

how the reply gets out

The agent calls reply or send, and routd delivers through the adapter’s /send. If the agent finishes without calling either, the text of its final result is the reply. While it works, the chat shows typing, and on a channel that can edit messages one status line updates in place. When the guest powers off, runed returns the outcome on the same HTTP call that started it.

A delivery that fails stays as a pending row and a sweep retries it with a growing gap. A turn that dies without replying is retried up to three times, unless runed calls the failure terminal: a retry can’t fix a VMM that won’t start or an exhausted model quota.
