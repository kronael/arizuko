audit trail

The audit trail is the table that records who changed what. It answers questions such as these: who revoked a grant last Tuesday, why did a guest stop during a turn, and who changed a secret? The page describes what the trail covers and what it does not cover.

One event can land in three places

One event in a daemon can land in three places, and they are not three copies of the same data. The row is the record. The log line shows what happens now. The span shows one turn across four daemons as one trace, when you connect a collector.

Each change writes one row

Every call that changes state writes one row to audit_log. The call can be an MCP tool call of the agent, a REST call of an operator, or a CLI command. Reads write no row. A route list or a chat fetch produces only a log line. Reads are very many, and their rows would record no decision.

The row is written in the same batch as the change, so both land or neither lands. No moment exists in which a route changed and nothing recorded it, and no cleanup job must reconcile two tables.

A row names who asked, in actor and actor_sub. It names what they touched, in action, resource and params_summary. It names the result, in outcome, error_msg and duration_ms, and the place, in folder, turn_id and instance. reference/schema has the full column list.

The log line is not the record

Every audited call also writes a structured log line, and the two are different. The log line goes to journald and, if you connect an OTLP collector, to your dashboards. The log can lose lines by design: journald rotates, levels filter, and nothing waits for a line to land.

So the table answers “every ACL write last quarter”, and the log answers “what happens now”. When the two disagree, the table is correct.

Tool use inside the guest goes to the log, not the table

Harness hooks capture the tool use of the agent while it works, such as every Bash, Edit and Read call. The hooks print one JSON line per call. runed moves these lines into the log stream. None of them reaches the database.

This is by design. Tool use in the guest is operational detail in large volume. The calls that change platform state already went through MCP, and MCP audited them like any other call. A hook that wrote to the database would make every step of the work of the agent a distributed transaction.

One kind of agent action gets a row, because it leaves no other trace. This is a like, dislike, edit, delete, pin or unpin on a message already on the platform. None of these appends a messages row, so the audit_log row is the only record. It has the category agent, the action message.<verb>, and the chat and target message as the resource, in routd/social_audit.go. An edit row names the message, never the new text. routd writes the row after the platform call, on success or error. A failed audit write goes to the log and is not returned, because the platform message already changed and a retry would change it twice.

The two streams do not match field for field. The hook line has tool, phase and args_summary. The line from the registry has caller, resource, action and surface. Both end with outcome and duration_ms. [audit/README.md] has the full row shape.

Each daemon keeps its own audit table

arizuko has no single audit table. Each daemon owns its own tables, including its own audit_log, and no daemon writes into the tables of another. A table name starts with the daemon that owns it, such as routd.audit_log, runed.audit_log, authd.audit_log and onbod.audit_log, so the name shows the owner. The turn_id travels with the work and connects the rows.

DaemonIts audit tableRecords
routdroutd.audit_logroutes, groups, grants, secrets, tasks and tokens, which is most of the trail
runedruned.audit_logwho claimed the run slot of a folder, run.hold, and who stopped a run, run.kill
authdauthd.audit_logidentity and token events: logins, and who ended whose session, sessions:delete
onbodonbod.audit_logadmissions, invites and onboarding gates

The same rule keeps each daemon the owner of its own schema. webd, proxyd and dashd keep no table of their own, and their rows go into the table of routd. One view still covers all four: the dashboard asks each daemon and merges the answers, and it reads no other daemon’s tables.

The dashboard merges the four trails

The dashboard page /dash/audit/ is the usual view, newest first, with fifty rows per page. It has filters for category, actor and folder, and an older link that keeps your filters. Only an operator can open it.

The page shows all four trails at once. Each daemon publishes its own table at GET /v1/audit. The dashboard asks all of them, merges the answers by time, and shows a source column with the daemon of each row. So you can find who stopped a run in the browser, with no shell on the host.

The dashboard asks over the network and does not read the tables of runed and authd itself. This is the same ownership rule as everywhere else: a daemon serves its own table, so one place decides who can read what. If one daemon does not answer, a banner names it and the other sources still show. An empty section would say that nothing happened there, and an audit page must never say that by accident.

A read of the trail writes no row. Only changes get a row, so a page refresh adds nothing. A refused read does get a row.

The same data is available over HTTP. Use an operator token: 
curl -s -H "Authorization: Bearer $TOKEN" \
  "https://<host>/v1/audit?category=authz&limit=50" | jq .
The filters are folder, category, actor, limit and before_id. folder covers that folder and every folder under it, and actor matches a substring. limit has a default of 50 and a maximum of 200, and before_id gives older pages. An agent can ask the same question about its own folder with the query_audit tool.

onbod is a source only where it is deployed. Onboarding is an optional profile, and a daemon that never ran is not a failed source.

A table that is already the record gets no audit row

A table that already is the record is not audited a second time. A turn is the clearest case. spawns already holds its kind, state, outcome, exit code and every timestamp, and the dashboard shows it. So runed writes no extra row per turn. Chat messages are the same: the messages table is the record of what was said.

Such a table never records who asked. For this reason, runed audits the run slot and not the run. A hold stops every turn in a folder, a kill is the decision of an operator, and both can happen without a spawns row.

One gap exists. A denied call gets a row for every resource that the registry serves: routes, grants, secrets, tasks, tokens and the audit read itself. The older hand-written endpoints refuse correctly but leave no row. The fix belongs at the authorization gate, and it is not complete.

Credentials never reach the table

The row records the arguments, so you can tell one call from another. Before the write, a marker replaces anything that looks like a credential: passwords, tokens, secrets, cookies, API keys, private keys and database connection strings. The marker keeps the length, as in <redacted:64chars>, so you can tell an empty value from a real key without storing the key.

Redaction happens where the row is written, not where it is read, so one rule applies and every daemon follows it. The match is narrow at the edges on purpose. private_key is hidden. serving_keys, a count of the keys a daemon serves, is not hidden, because too much hiding blocks the questions the table exists to answer. A very long argument is cut to its first 200 characters, with a note of its real length. The rest of the row stays complete.

Three READMEs have the detail

[audit/README.md] describes the row, its closed enums and the redaction rule. [obs/README.md] describes the log and span half. reference/schema lists every column, index and writer. grants explains who can do the action that the trail records.
