skills

A secret is a credential a skill can spend; a skill is the job that spends it. A skill is a directory of markdown the agent reads when it needs to do something specific — another set of files in the ant, exactly as page one promised. The agent ships with a built-in set and the operator can drop in more. The one thing to internalize: skills don’t fire on their own. An LLM won’t reliably notice a skill applies, so every turn tells the agent to run /solve, which matches skills through /dispatch — discovery is a deliberate step, not magic.

what a skill is

One directory under ant/skills/. Every skill has a SKILL.md with YAML frontmatter and a body:

---
name: skill-name
description: one-line summary; say in prose when the skill applies
---

Skill instructions here...

Names must match ^[a-z0-9\-]+$ — the seeder skips anything else. The body can be markdown plus any reference files (*.md) or executable helpers (*.sh, *.ts) that live next to SKILL.md.

built-in vs user skills

Two sources feed the agent’s skill list:

  • Built-in. Everything under ant/skills/ in the arizuko repo — self, migrate, diary, find, oracle, persona, visual, and 86 more (93 in all, measured at 7baffbb0). These ship inside the arizuko-ant Docker image and are copied into every new group by container.seedSkills(). See onboarding for the copy mechanism.
  • Package. A package can ship a skills/ folder. arizuko generate copies each of its skills into every existing group, overwriting the group’s copy, unless the group disabled it or a built-in skill already has the name.
  • User. A group can add its own skills under /home/node/.claude/skills/ (the per-group workspace shared into the guest). The agent loads them the same way; the only difference is they live in the group’s data dir, not the image.

Built-in skills get refreshed on every /migrate run; user skills are never overwritten.

discovery: dispatch is explicit

LLMs do not reliably auto-trigger skills by reading their descriptions. So every prompt ends with a [solve] line, added by runed, telling the agent to run /solve first: classify the message, recall context, then /dispatch, which scans every skill’s description against the request and invokes the matches. Without that nudge, skills sit there unused.

Why not just put the instructions in the always-loaded file? Because that file is read on every turn whether the turn needs it or not. A rule earns a place there only when the agent needs it before it could know to ask, or when breaking it would fail silently. Everything else is a skill, loaded when it applies.

migration and versioning

The agent image carries a version number in ant/skills/self/MIGRATION_VERSION — a single integer. Every release that ships skill changes bumps this number. Before each turn, runed compares the image’s version against the group’s last-seen value:

  • If higher, the prompt carries a [pending migration] line and the agent runs /migrate, which copies new and changed skill files from the image into the group’s .claude/skills/ — preserving user skills, replacing built-ins.
  • The same hook fires the release broadcast: the > blockquote at the top of the new CHANGELOG.md entry is extracted and posted into the chat. Skill update and announcement travel together — bumping the version is the single trigger.

Each version bump has a corresponding ant/skills/self/migrations/NNN-vX.Y.Z-summary.md file. The file’s existence is what fires the broadcast; an empty stub body is fine for docs-only releases.
