tasks

A task decides when a prompt arrives, also when no person is there to send one. A task is a saved prompt with a schedule. When the schedule says it is time, the prompt lands in a folder as if a user had typed it. The agent answers as on any other turn. A scheduled run uses no special code path: it is a synthetic message on the same path as every other message.

A task is one row with a prompt and a trigger

One row in the scheduled_tasks table is one recurring or one-time agent run. The body is a prompt string. The trigger is a cron expression, an interval in milliseconds, or one future timestamp.

routd posts the prompt as a message

The task ticker runs once at startup and every 60 seconds inside routd. It claims due active rows through DueTasks, which marks them firing. It sends each prompt through the normal message ingress in the same process. The destination is the task's owner folder. forwarded_from records the task's chat JID.

The sender is timed, or timed-isolated:<id> for an isolated task. The message ID contains the task ID and scheduled time, so a repeated fire has the same identity.

routd records the enqueue result in task_run_logs and advances the schedule. A successful one-time task becomes completed. A failed one-time enqueue retains its scheduled time for the next tick.

The trigger has one of three shapes

The cron column holds one of three shapes:

Cron expression
A standard 5-field cron, for example 0 9 * * 1-5 for weekday mornings. robfig/cron parses it in the timezone of the task, which is the TZ of the daemon, UTC by default.
Interval
A plain integer string of milliseconds. 1800000 means every 30 minutes. After each run, the next next_run is now + interval.
One-time
An empty cron. The row runs once at next_run, then changes to status='completed' and leaves the poll. The row stays in the table for audit, and nothing deletes it.

The context mode picks the session

One column of the row decides the session of the run. With group, the default, the synthetic message goes to the main session of the folder like any other turn. The task sees the chat history of the folder and shares state with it. With isolated, the sender becomes timed-isolated:<task-id>, and routd treats it as its own conversation. Use it for a recurring health check that must not fill the context of the human chat. reference / schema has the full column list of scheduled_tasks.

Agents manage tasks, and operators use REST

An agent with the scheduling grants gets MCP tools to create, list, pause, resume and cancel tasks. schedule_task creates a task and removes duplicates on the prompt, chat and schedule, so a repeated call returns the existing ID. inspect_tasks joins task_run_logs to show when each task last ran and whether it succeeded. reference / mcp has the full signatures.

The REST endpoints live on routd at /v1/tasks:

GET /v1/tasks
Lists tasks.
GET /v1/tasks/{id}
Reads one task.
PATCH
Takes {status} to pause or resume, and {next_run} to run now.
DELETE
Cancels a task.

No arizuko task CLI subcommand exists. An operator can use the REST resource, and the agent can use arizuko chat.

Every group starts with five tasks: /compact-memories for episodes by day, week and month, and for the diary by week and month. They run isolated, so a compaction never summarises its own work. the ant shows what they compact.

A failed turn does not stop the schedule

If the insert of the synthetic message fails, routd writes an error row to task_run_logs. It restores a one-time task to active with the same next_run. Recurring tasks advance to their next scheduled time.

If the insert succeeds but the agent run fails later, the task ticker does not know. For the scheduler, the run succeeded. next_run advances as usual, and the task runs again at its next time. The task ticker does not retry the failed agent turn. Normal turn retry rules still apply. The error is in the logs of routd and in the chat history of the folder. An operator, or the agent on its next run, decides what to do.

A failure never changes the status to paused. A failing recurring task keeps running until someone pauses it or fixes the problem.
