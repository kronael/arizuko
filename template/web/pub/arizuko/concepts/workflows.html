workflows

An arizuko agent handles a chat well and fails at a job with many steps. It improvises every turn from the chat history, never writes a plan down, does not read its own skills, and starts each session with no context. A workflow fixes this with one rule, not a new engine: keep the conversation free, but make the opening strict.

Jobs with many steps go in circles for four reasons

Watch a travel agent plan a trip of one week over chat. The pattern is always the same:

The plan lives in the transcript
No single file holds the itinerary, so every turn rebuilds it from the chat history. The agent adds the same stop, questions it, removes it and adds it again within an hour. Nothing exists to converge on.
Nothing forces an opening
The agent can run its triage step, but the step is only a hint, and the model skips it. A plain “hello” can stay unanswered while the agent starts on something else.
The context is not loaded when the agent decides
The agent says “I do not have the history” during a session although the context exists, because nothing makes it load memory and facts/ before it acts.
The agent does not read its own skills
A user teaches a rule that a skill already holds, four times, because nothing makes the agent read its skills at the start of the job.

None of these is a missing capability: the memory, the skills and the plan file all exist. What is missing is a gate that runs a fixed opening before the agent replies freely.

The chat stays free and the opening is strict

The discipline applies at the edges of a session, not in the middle. A waiter who knows you chats freely, but each time you sit down, he runs the same steps: greet, recall your table, take the order, read it back, then act.

BoundaryWhat runs
A new session, after a cold start, an idle expiry or /newthe full opening: load the persona, memory and facts, read the open plan for this topic, and confirm the goal, all before any free reply
A continuation in the same sessionfree conversation, with the plan edited in place as the work moves
A new topic from a forkthe context of the parent, plus an opening for the new thread

Inside a session, conversation is the default. The strict part applies only at the boundaries: a new session and a new thread.

One plan file is the record of the job

A plain file stops the circles. Every job with many steps gets one ~/plans/<topic>.md, written first and edited in place. The opening reads it, and the work updates it. “Done” means that the plan file is updated, not a closing chat message. The file is markdown that the agent owns, with no schema and no database row, and you can diff it like every other file in the agent folder.

You write the opening in CLAUDE.md

You write what the opening says. Each group has a CLAUDE.md, its operating manual, and a ## Session opening section in it is the contract. Keep the section short and concrete:

## Session opening

Before replying to anything multi-step:
1. Load context — read MEMORY.md, the relevant facts/, and the diary.
2. Open the plan — read ~/plans/<topic>.md, or create it if missing.
3. Scan skills/ for one that fits the job, and apply its rules.
4. Confirm the goal and name the deliverable, then act.

"Done" means the plan file is updated — not a message that says done.

Two more rules make the opening useful. Keep the persona coherent: one identity and one focused facts/, because an agent with three personas has nothing clean to load. Treat the plan file as the source of truth for the whole job.

A workflow is not a new primitive

A workflow is not a seventh part of the system. It is Turn and State and the session lifecycle, combined. The session boundary already starts each run fresh. The discipline makes that boundary run a fixed opening and keep a plan file. No state machine and no DAG runtime exist. The session lifecycle of arizuko is the structure, and the agent supplies the intelligence.

You write the opening, and the platform does not enforce it. The opening is a convention that you write in CLAUDE.md and the agent follows. The plan file and the opening section work as described. The platform does not enforce the opening, and no durable workflow engine runs under it, by design. Checkpoint-and-replay engines assume that the orchestration code is deterministic. Here the orchestrator is a model, and a replay of a model does not give the same steps back.

Existing parts give what an engine would give

You wantarizuko does it with
recovery from a failurethe turn: a failed turn runs again as a whole, with a note that it is a retry
sleep, or a run on a scheduletimed
a wait for an eventrouting: the event is a message, and a route wakes the folder
a hand-off to a childdelegate_group and escalate_group
a restart without lossstore rows plus the files of the folder

This is not enough for a shipped product that needs a job of many hours with side effects, where a second run of the turn is not acceptable. Such a job gets its own daemon with its own store and a checkpoint-or-execute step, not an engine under every turn.

Agents can talk to each other with existing parts

Long-lived groups that message each other need nothing new either. A chat link or a route token gives a group an address, send posts to it, and the skill files decide who talks to whom. routd does not change: the topology is text in the folders.
