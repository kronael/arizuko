retries

Every turn runs in its own short-lived virtual machine. A turn can fail without an answer: the guest stops, the guest does not start, or the model provider refuses. Then routd keeps the input, retries on a fixed schedule and shows one status message in the chat. You get a slower reply or a short cause, never silence.

A turn without a bot message counts as failed

The test is “did any bot message arrive?”, not “did the agent finish without an error?”. An agent that posted half an answer and then stopped counts as a success, and routd does not retry it. A partial reply that you can read is better than a wait while the agent does the whole task again. A status message never counts as that reply.

A failed turn retries three times on a fixed schedule

A failed turn gets three retries, so the input runs four times in all. The gap before each retry depends on the sender of the turn:

turnretry 1retry 2retry 3
chat message30 s2 min5 min
scheduled task15 min45 min180 min

The long task schedule gives a host fault, such as a full disk, about four hours to clear. routd saves the waiting retry in the turn_context row: the input message keys, the due time, the failure cause and state='pending_retry'. In the same write, routd moves the chat cursor past that batch, so new messages keep flowing while the retry waits. The row survives a restart of routd, with the correct count of attempts already used.

At the due time, routd replays the saved input with the saved folder, topic, sender and return address. It does not resolve the current routes again. New messages do not move the due time. Deleting the group retires its waiting turns. If runed answers busy, the attempt does not count. routd waits four seconds, doubles the wait up to 60 seconds and tries again.

One status message shows the failure and the retry

Each failed turn gets one status message in each chat that waits for it. The first failure posts a short cause and the retry time. The retry edits the same message, and a success deletes it:

Server storage is full. Retry 1/3 at 03:15:00 UTC.
Retry 1/3 is running.

If every retry fails, the message changes to the final cause:

Server storage is full. Stopped after 3 retries.

The cause comes from a short fixed list: server storage is full, model unavailable, time limit reached, agent could not start, agent stopped unexpectedly, agent setup needs attention, or agent could not complete the request. No error text, path or stderr reaches the chat. routd also marks the chat as errored, so an operator can find it on the dashboard.

A channel that cannot edit and delete gets the first post and the final post only. Email is such a channel. If a retry succeeds there, the final post says The request completed. GitHub and Google Drive edit and delete their own comments, so they show one status comment, like a chat.

One failure stops new launches on the whole instance

A failed execution opens one breaker for the whole instance. A crash, a launch fault, a time limit, a network failure between routd and runed and a provider refusal all open it. While it is open, no new agent starts. Runs that already started can finish, but their success does not close the breaker.

The next retry of the failed turn is the probe. A probe that runs without a failure closes the breaker. A probe that fails applies the next gap of the schedule. When the probe turn has used all its retries, the breaker stays open for one hour. Then the oldest waiting turn probes next.

The breaker is the singleton turn_control row, so it survives a restart. Startup reads it before routd admits work. An operator stop never opens it. No operator command writes it: only a probe closes it.

A provider refusal uses the same breaker

A structured provider error can report a spend limit, a rate limit, refused authentication or an outage. Every folder of an instance shares the provider credential, so the refusal opens the instance breaker. The refused turn keeps its input and retries on the normal schedule. The first retry is never earlier than the reset time that the provider reports. The status message names the cause Model unavailable.

provider refusal ──► breaker open, input saved, due no earlier than reset
                                   │
                                   ▼
                     the refused turn retries: the probe
                         │                    │
                     refusal              no refusal
                         │                    │
                         ▼                    ▼
               next gap, or one hour     breaker closed,
               after the last retry      pause rows cleared

The refusal also writes a model_pauses row for the folder that reported it. Operators list these rows at /dash/model-pauses/, through arizuko model-pauses, or with the operator MCP tools. Clear removes the row of one folder. It does not close the breaker or start the saved input: only a probe without a refusal does that.

Exit code 78 alone, assistant quotations, tool failures and unknown errors are not provider refusals. They are ordinary failures and follow the same retry schedule.

The agent knows that a run is a retry

Before the agent sees the prompt of a retry, routd adds a note at the start:

<system-note>This is retry attempt 2 of 3. The previous attempt
did not complete.</system-note>

The note does not guess the cause. The rest stays the same: the same messages and attachments and the same conversation history, in a new guest.

Five kinds of turn never retry

Turns that replied
Any bot message, even a partial one, counts as done.
Turns that the agent failed on purpose
The agent reported its own failure through submit_turn.
Turns that a person stopped
An explicit /stop or an operator kill ends the turn. The status says Turn stopped.
Turns that reached the time limit
A run that reaches RUNED_RUN_TIMEOUT ends with the status Time limit reached. Another full attempt would cost the same time again.
Runs that runed marks terminal
Container exit 125, 126 or 127 and a substrate that cannot start are terminal. runed makes this decision and routd obeys it. A retry cannot repair these failures.

Two instance-wide settings control retries

MAX_TURN_RETRY sets the number of retries. The default is 3, and a higher value is capped at 3 with a startup warning. Set it to -1 to turn retries off and get the final status on the first failure. No folder or skill can override it, because the number of guests the runtime starts again is a property of the host, not of the content of a tenant.

MAX_CONCURRENT_AGENTS, default 5, bounds the agents that run at once. Scheduled tasks hold at most one of those slots, so a free slot still serves a chat. One folder runs one turn at a time. If turns stop because of memory and not because of content, change RUNED_GUEST_MEM, not the retry count.
