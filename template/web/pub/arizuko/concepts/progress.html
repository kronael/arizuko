live progress

When you ask for a task that takes real work, you get a checklist while you wait. It is one message that changes in place, not a stream of separate “still working” messages. The list is the plan of the agent, and arizuko posts it for the agent. So the progress you see does not depend on the model remembering to report.

One message shows the plan and changes in place

One message arrives as soon as the agent has a plan. The message changes as the work moves:

⏳ ☑ Read the three log files
☐ Cross-check the timestamps
☐ Write the summary

A minute later, the same message, edited:

⏳ ☑ Read the three log files
⏳ Cross-checking the timestamps
☐ Write the summary

The checklist uses three marks:

☑
Done.
⏳
In progress now. If the plan gives an in-progress wording, such as “Cross-checking the timestamps”, the line shows it. If not, the line shows the plain item text.
☐
Not started.

The ⏳ at the start of the first line belongs to the message, not to an item. Every status message carries it, so you can see at once that the agent still works. When the turn ends, that one mark changes: ⏳ becomes ✓ if the turn finished, or ✗ if it failed. The rest of the message stays as the agent left it, so no message says “in progress” after the work stopped.

A hook posts the plan, not the model

The agent plans with the TodoWrite tool of the SDK. The agent writes that list to organise its own work, not to report to you, so it writes the list whether anyone watches or not. arizuko attaches a hook to that tool. Each time the list changes, the hook reads the new list, renders it and sends it. Nothing asks the model to report progress, so the model cannot skip the report.

A design that asks the model to narrate its progress fails, because models follow such instructions unevenly. Users then get either silence for ten minutes or many separate plan, step and done messages. Progress is bookkeeping over a list that already exists, not a decision for the model.

Later updates edit the first message

The first update of a turn sends a new message, and every later update edits that message. routd finds the message to edit from the last status row that it stored for the turn. No table in memory tracks live messages. So if routd restarts in the middle of a long turn, it reads the message from the database and continues to edit it.

The chat shows that the agent is busy until the turn ends

The channel also shows that the agent is busy. Telegram, Discord and WhatsApp use their own typing indicator. Slack and GitHub have no such indicator, so they put an eyes reaction, 👀, on the message that started the turn. The indicator stays on until the turn ends, not until the first reply. So an agent that answers and then continues to work still looks busy. If the adapter restarts during the turn, the reaction stays: the adapter records it and removes it when the turn ends.

Channels that cannot edit show only the answer

Email, Bluesky, LinkedIn and X cannot edit a sent message. On these channels, arizuko drops the status updates, and you get only the answer. A stream of separate “still working” posts is what the checklist exists to avoid, so these channels get no fallback. Google Drive comments behave the same way, because the Drive adapter does not edit its replies.

An edit can fail for a real reason, such as an expired token, an adapter timeout or a 500 from the platform. Such a failure appears as an error. arizuko never posts it again as a new message, because a silent duplicate looks the same as the stream of messages that the checklist replaces.

The checklist never counts as the answer

Status messages are not replies. Each status message carries verb="status" in the messages table, and routd skips these rows when it asks whether the turn has replied. Without that rule, a checklist would count as the reply of the agent, and routd would drop the real answer.

So the final answer always arrives as its own message, next to the checklist. At that time, the checklist shows every box ticked.

Short plans and turns without a plan send no checklist

  • A plan with one step sends no checklist, because a one-item list is noise. A plan with two or more items gets a live message.
  • An agent that answers without a plan sends no checklist. Short turns do not need a plan and do not make one.

A long turn without a plan still shows progress. Every 90 seconds, the harness inside the guest asks the agent for a one-line <status>, and that line goes through the same edited message. This path is the minimum, not the main path.

The code that renders the checklist

The hook that renders the list is in [ant/src/todo-status.ts]. The code that creates or edits the message, and the end-of-turn mark, are in [routd/progress.go]. retries explains what happens when the turn stops before it finishes the list.
