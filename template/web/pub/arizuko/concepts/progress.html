live progress

Multi-step work starts with a short task summary. On compatible channels, that summary opens a thread for the live checklist and the answer.

what you see

The summary carries a robot mark and stays unchanged:

🤖 Review the log files

The checklist follows inside the summary’s thread. The answer, files and voice replies use that same thread. If the request already belongs to a thread, everything stays there.

⏳ ☑ Read the three log files
⏳ Cross-checking the timestamps
☐ Write the summary

Three marks, and that’s the whole vocabulary:

  • ☑ — done.
  • ⏳ — working on it right now. If the plan supplies an in-progress phrasing (“Cross-checking the timestamps”), that’s what shows; otherwise you get the plain item text.
  • ☐ — not started.

The checklist’s leading ⏳ changes to ✓ when the turn finishes or ✗ when it fails. The task summary keeps its robot mark.

the harness updates the checklist

The agent declares its overall task in the first <status> before planning with TodoWrite. A harness hook renders each list change into the same editable checklist. The first task never substitutes for the declared summary. Later status blocks update progress for work without a task list.

one message, edited

The first progress update sends the checklist. Later updates edit it. Stored message rows preserve the checklist, summary and thread identity across a router restart.

A queued summary retries with its original identity. Until the summary arrives, an unplaced answer returns an error and stays out of the retry queue. A failed summary read or refused thread destination never sends the answer at the parent channel.

the typing indicator

Alongside the message, the channel shows that the agent is busy. Telegram, Discord and WhatsApp use their own typing indicator. Slack and GitHub have none, so they put an eyes reaction (👀) on the message that started the turn. Either one stays on until the turn ends — not until the first reply — so an agent that answers and then keeps working still looks busy. The reaction is also still there if the adapter restarts mid-turn: the adapter remembers it, and removes it when the turn ends.

unsupported channels

An editable channel without compatible thread support keeps one progress message and its normal answer placement. There is no separate summary opener on that channel.

Email, Bluesky, LinkedIn and X have no edit-a-sent-message operation. On those, the agent’s status updates are dropped and you get the answer alone. A stream of separate “still working” posts is the thing this page exists to avoid, so there is no fallback to one. Google Drive comments work the same way for now: the adapter does not edit its replies yet.

An edit failure returns an error. The router never posts a replacement message to hide the failure.

the checklist is never the answer

The summary and checklist promise an answer. Neither counts as that answer. The agent delivers the answer explicitly with a tool such as reply; terminal text stays in its transcript. An addressed turn, or one that declares work, gets one prompt if delivery is missing. Continued silence produces a failure notice inside the same thread.

when you won’t see one

  • The plan has one step. A one-item checklist is noise, so it isn’t sent. Two or more items earn a live message.
  • The agent answers without planning. Short turns don’t need a plan and don’t make one.

Simple replies need neither a summary nor a checklist.

go deeper

The design and the two decisions that carry it: specs/5/24. The hook that renders the list lives in ant/src/todo-status.ts; the create-or-edit half and the end-of-turn mark are in routd/progress.go, specified in specs/6/46. What happens when the turn dies before it can finish the list: retries.
