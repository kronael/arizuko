live progress

While a long task runs, the chat shows one temporary progress line. It appears where the answer will go, and arizuko deletes it when the task ends.

One line, where the answer will go

The line is posted in the place the answer will use. If the request already belongs to a thread, the line stays in that thread. The line never starts a thread of its own. The checklist is one message that changes in place:

⏳ ☑ Read the three log files
☐ Cross-check the timestamps
☐ Write the summary

A minute later, the same checklist message, edited:

⏳ ☑ Read the three log files
⏳ Cross-checking the timestamps
☐ Write the summary

The checklist uses three marks:

☑
Done.
⏳
In progress now. If the plan gives an in-progress wording, such as “Cross-checking the timestamps”, the line shows it. If not, the line shows the plain item text.
☐
Not started.

When the turn ends, arizuko deletes the line: Telegram, Discord, WhatsApp, Slack and the web chat all do so. On GitHub the line is one comment, and on Google Drive it is one reply in the comment thread. Both adapters edit and delete what they posted. Nothing of the progress stays above the answer. A channel that cannot both edit and delete shows no progress line.

Claude tasks and Codex plans share one checklist

Claude uses its task tools or TodoWrite; Codex uses update_plan. Hooks send the parent agent's native snapshots to routd, which keeps the checklist and renders its text. Child-agent calls do not change it. An active checklist owns the progress line; <status> text cannot overwrite it.

A turn without a checklist gets one planning reminder after eight parent tool completions or 180 seconds, whichever comes first. This also applies to silent tasks and channels without a progress display. Clearing a checklist shows “No remaining tasks” and suppresses the reminder for the rest of the turn.

Updates coalesce within five seconds. Each message stays below 2,000 UTF-8 bytes; a long checklist keeps the current task visible and reports how many tasks were omitted.

Later updates edit the first message

The first progress update sends the checklist, and every later update edits it. The stored message rows keep the identity of the checklist, so a restart of routd in the middle of a long turn does not lose it.

The chat shows that the agent is busy until the turn ends

The channel also shows that the agent is busy. Telegram, Discord and WhatsApp use their own typing indicator. Slack and GitHub have no such indicator, so they put an eyes reaction, 👀, on the message that started the turn. The indicator stays on until the turn ends, not until the first reply. So an agent that answers and then continues to work still looks busy. If the adapter restarts during the turn, the reaction stays: the adapter records it and removes it when the turn ends.

Channels that cannot edit and delete show only the answer

Email cannot edit a sent message. On such a channel, arizuko drops the progress updates, and you get only the answer. A stream of separate “still working” posts is what the checklist exists to avoid, so such a channel gets no fallback. A failed turn still reaches email: the first failure and the final result each get one post, as retries shows.

An edit failure appears as an error. routd never posts a replacement message to hide it.

The checklist never counts as the answer

The checklist promises an answer, and it is not that answer. The agent delivers the answer with an explicit tool, such as reply. The terminal text of the agent stays in its transcript. If an addressed turn, or a turn that reported work, ends without a delivery, the agent gets one prompt. If the agent stays silent, a failure notice arrives in the same thread.

A checklist appears when the agent makes a plan

  • A plan with one or more steps gets a live checklist on a channel that can edit and delete it.
  • An agent that answers without a plan sends no checklist. Short turns do not need a plan and do not make one.

A simple reply needs neither a summary nor a checklist.

The code that renders the checklist

The shared checklist reducer is in [routd/progress_reducer.go]. The renderer and message lifecycle are in [routd/progress.go]. retries explains what happens when the turn stops before it finishes the list.
