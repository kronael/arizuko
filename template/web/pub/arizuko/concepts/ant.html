arizuko › concepts › the ant

ant

You know what arizuko is for; now meet the thing you actually talk to. An ant is one Claude Code process running inside its own KVM guest. There is one ant per group, and the group’s folder on disk IS the ant. Its diary, skills, and PERSONA.md are all files in that folder. Keep that picture in your head: every concept after this one is really about a file in that folder, or a rule about who may touch it.

the folder is the agent

Every group lives at /srv/data/arizuko_<instance>/groups/<folder>/ on the host. When a message arrives, runed starts a guest and shares that folder in at /home/node/ inside. Whatever’s in the folder is what the agent sees:

groups/solo/inbox/
  PERSONA.md       persona — name, tone, voice
  CLAUDE.md        the operator's runbook for this group
  work.md          what the agent is doing right now
  diary/           dated work log, survives restarts
  episodes/        compacted day, week and month summaries
  facts/           durable knowledge
  users/           one file per person the agent talks to
  .claude/         CLAUDE.md, skills/, output-styles/, session state

Copy the folder, you copy the ant. Delete the folder, the ant is gone. There is no separate database row holding the persona.

what the ant remembers

Memory is files in that folder too, in layers. A short form of the top three rides into every prompt; the facts wait until the agent goes looking:

layer        file in the group home           reaches the turn
──────────── ──────────────────────────────── ─────────────────────────────
now          ~/work.md                        pushed whole, every turn
today        ~/diary/YYYYMMDD.md              pushed: summary: of the
                                              newest 14 files
day, week,   ~/episodes/YYYYMMDD.md,          pushed: summary: of the
month        YYYY-WNN.md, YYYY-MM.md          newest 3 per type
people       ~/users/<id>.md                  pushed as a pointer,
                                              <user memory=...>
facts        ~/facts/*.md                     pulled: /recall-memories,
                                              then /find
index        ~/.claude/projects/-home-node/   read by Claude Code itself
             memory/MEMORY.md

session transcripts ──► /compact-memories episodes day ──► ~/episodes/
~/episodes/ day files ──► week ──► month ─────────────────► ~/episodes/
~/diary/ daily files ──► /compact-memories diary week ───► ~/diary/week/
~/diary/week/ ──► diary month ────────────────────────────► ~/diary/month/
    all five run as timed tasks with context_mode isolated;
    ~/diary/week/ and ~/diary/month/ are never pushed

The week and month diary rollups live in subfolders the prompt never reads: the 14 daily entries already cover that span, and pushing both would spend the context twice. The rollups are written by five scheduled tasks every group gets at creation, each running isolated so a compaction turn doesn’t summarise its own summarising.

what the ant reads each turn

Three processes build what the agent sees, and each builds the part only it holds:

routd  buildAgentPrompt, routd/prompt.go:26 ───► RunRequest.MessageBatch
       <system-note> <system> <autocalls> <persona> <rule> <topic>
       <surface> <pane-context> <link-context> <messages>
         │
         │ POST /v1/runs
         ▼
runed  preparePayload, runed/render.go:177 ────► the guest's stdin prompt
       [pending migration]  Topic session:  <episodes>
       <knowledge layer="diary">  <knowledge layer="work">  <user>
       [solve], then routd's string unchanged
         │
         │ vsock, guest-init, stdin
         ▼
ant    buildSystemPrompt, ant/src/index.ts:49 ─► the system prompt
       SYSTEM.md, ant/CLAUDE.md for codex and pi, PERSONA.md,
       the output style

The <user> tag is a pointer, not content — it names the sender’s file in users/ and the agent decides whether to open it. Bot rows never ride in as triggers, and where a tool returns history on purpose each one says bot="true", so the agent doesn’t mistake its own past words for somebody else’s.

One file is always loaded: ant/CLAUDE.md, seeded into the group as ~/.claude/CLAUDE.md. Everything in it is read on every turn whether the turn needs it or not, so a section stays there only if the agent needs it before it could know to ask, if breaking it would fail silently, if it’s a pointer no user phrase would trigger, or if a skill reads it from there. The rest lives in skills. A test fails when that file points at a skill or doc that doesn’t exist.

A group’s SYSTEM.md, if it has one, replaces the base system prompt outright; nothing merges into it. PERSONA.md and the output style come after it.

one guest per turn

The guest is short-lived. runed starts it when a message arrives, the agent reads the prompt, replies, and the guest powers off. Nothing important lives inside the guest — only inside the shared folder. The next turn gets a fresh guest, a fresh kernel, with the same folder.

A turn has one deadline, RUNED_RUN_TIMEOUT (20 minutes by default). The agent’s own timeout sits 30 seconds under it, so it can report before the guest is killed. A job longer than that wants splitting into turns, checkpoints in ~/facts/ or ~/tmp/, or a background task — not a bigger timeout.

capability is a grant, not a folder

How deep a folder sits says nothing about what its ant may do. solo/inbox and corp/eng/sre/oncall start with exactly the same power: the role:member role every folder is bound to at creation, which carries the messaging verbs and nothing else. Everything past that — registering groups, editing routes, opening egress, scheduling — is a row somebody explicitly handed over, scoped to a subtree. An ant with no row for a tool doesn't just fail the call; it never sees the tool. Same agent shape everywhere, and the only thing that varies is the grants.

how the agent talks back

The agent calls MCP tools (like send or find_messages) over a unix socket. routd hosts one socket per group in-process at ipc/<folder>/gated.sock on the host; runed runs a small bridge, one per turn, that accepts the guest's vsock connection and dials that socket. Inside the guest, Claude Code is wired up to a local path via its mcpServers config, same as always. Every tool call is a JSON-RPC message over that socket, and routd runs the same grant check on it that it runs when a human calls the matching REST endpoint — one gate, agent or operator.

the migration trick

When arizuko ships a new version of the built-in skills, you don’t want every group’s folder to fall behind. runed reads ant/skills/self/MIGRATION_VERSION from the agent image, compares it to <group>/.claude/skills/self/MIGRATION_VERSION, and if the group is older it adds a [pending migration] line to the next prompt. The agent runs /migrate, which copies the upstream skills into its own folder. Old groups catch up at their own pace; nothing is force-pushed.

what stays, what goes

  • Stays — everything under groups/<folder>/: diary, facts, skills, the JSONL session transcripts in .claude/.
  • Goes — the guest itself, anything written to /tmp inside, any process state held in RAM. Its own filesystem is a tmpfs overlay, discarded at power-off.

This is why “just edit the folder” works. Change PERSONA.md on the host (or via WebDAV) and the next spawn picks up the new persona — no restart, no reload.

arizuko vs standalone ant

Today: every arizuko group is an ant folder. arizuko chat <instance> [group] drops you into one for interactive use. runed starts guests from the same folders for inbound chat messages.

Alone: ant is the agent layer, not a daemon you deploy by itself. It occupies the guest runed hands it and talks over a stdin/stdout protocol, which is what makes a second harness — pi, codex — a sibling of ant rather than of runed. ant consumes the tool list the platform renders and is a component of nothing; the pieces arizuko does ship on their own are egress, substrate and mcpfw.
