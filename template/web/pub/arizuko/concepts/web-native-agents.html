web-native agents

each folder is a microsite

An arizuko folder owns a public website with no extra services. The site has static pages, an embedded chat widget, a form intake, and content that the agent writes itself. Many agent platforms put a model behind a chat box in the product of another company. In arizuko, the folder is the microsite, because the agent is the folder.

One folder serves four kinds of content

One folder has four web parts, which share one guest per turn and one history:

partwhat it doespath
public pageThe agent writes into ~/public_html/, and vited serves it to anyone./pub/<folder>/*
chat widgetslink embeds in the page, and messages land at web:<folder>./chat/<token>/
form intakeEach POST lands at web:<folder>/<sub>. That JID needs a real child group, for example one made with register_group for atlas/strengths/submissions, because each web JID maps to exactly one group./chat/<token>/ with a suffixed JID
generated contentThe agent writes HTML, PNG or JSON into ~/public_html/ over WebDAV, and vited serves it on the next request.the same /pub/<folder>/ tree

The diary, facts and notes per user collect in the same folder. A private counterpart, ~/private_html/, is served at /priv/<folder>/ behind OAuth, for content that is not public.

The /pub/<folder>/ path always works. A world can also get a short host name. When HOSTING_DOMAIN is set, proxyd answers <folder>.<HOSTING_DOMAIN> with a 302 redirect to /pub/<folder>/, with no configuration per host and no map file. An agent finds its own public URL with the get_web_presence tool.

A visitor request reaches the agent and comes back as a file

visitor
  GET /pub/<folder>/  ──►  vited  ──►  static HTML + chat widget

  POST /chat/<token>/  ──►  webd  ──►  message at web:<folder>
                                          │
  POST /chat/<form-token>/  ──►  webd  ──►  message at web:<folder>/submissions
                                          │
                                          ▼
                                        routd
                                          │
                                          ▼
                                    guest (agent)
                                          │
        davd write  ◄──  ~/public_html/<name>.html
                                          │
                                          ▼
                          next GET /pub/<folder>/<name>.html
                          serves the file the agent just wrote

The form post lands in a separate chat thread, and routing keeps it apart from the page chat.

A form post becomes a personal report

A visitor opens /pub/atlas/strengths/ and sees an intake form. The visitor pastes Gallup CliftonStrengths results and clicks submit.

  1. The form posts to /chat/<form-token>/, and webd writes a message into web:atlas/strengths/submissions. The group atlas/strengths/submissions must exist, because each web JID maps to exactly one group folder and the route table does not apply.
  2. routd starts the turn, and runed starts the atlas/strengths/submissions guest to process the form post.
  3. The agent runs its process-strengths skill and writes ~/public_html/strengths/<name>.html through davd. The file is served at /pub/atlas/strengths/submissions/strengths/<name>.html.
  4. The visitor is redirected to that new path, and vited serves the personal report on the next request.

One folder replaces four services

On a typical stack, the same work needs four services. They are a Webflow page, a Zapier or Make webhook, an OpenAI call from a backend, and a storage bucket. Here it is one folder, with no CMS, no glue service and no backend code except a skill that writes HTML. The agent is the CMS, the ETL step and the generator.

Five kinds of site fit this shape

Personal reports
Paste data and get a report URL: CliftonStrengths, resume reviews, lab results.
Tools
Calculators, generators and intake forms where a model must write the answer.
Customer demos
A one-page site that shows what the agent does, with a working chat next to it.
Submission queues
Intake forms whose entries the agent triages, answers or escalates to a topic.
Tutors
Context per user across visits, with the page as the workbook.

The site has three limits

  • One folder is one site. Sub-sites under one folder share the same agent, ACL and history. For separate sites, use separate folders.
  • A page is what the agent writes. No template layer reads from a database, so a dynamic page needs a skill that writes the HTML.
  • vited is the origin, with no CDN and no edge cache. Put one in front if the traffic needs it.

Six pages cover the parts

  • routing: how web:<folder> and web:<folder>/submissions reach the correct agent.
  • route tokens: the /chat/<token>/ URL that the page and the form post to.
  • tasks: schedule the agent to rebuild or clean the site.
  • skills: the markdown instructions that turn a form post into HTML.
  • webdav: the file workspace that the agent writes through.
  • how-to: chat link: create the token that the page embeds.
