grants

Auth minted the principal; a grant decides what that principal may do. Every permission check asks the same question: may principal P do action A on scope S? — for example, may google:114alice send a message in eng/oncall? Two tables hold the answer: acl — ACL, Access Control List, the permission rows — for the rules, and acl_membership for “this id belongs to that group.” One auth.Authorize() call walks both. Get those two tables right and there is nothing else to learn.

the four words

Four words name everything in that question. Get these right and the rest is rows.

  • Principal — who is asking: a human (google:114alice), a folder's agent (folder:atlas/eng), a channel-side id, or a named role.
  • Action — what they want: interact, admin, mcp:<tool>, or *.
  • Scope — where: a folder path like atlas/eng, or a glob like atlas/**.
  • Effect — allow (default) or deny. Deny wins.

the action lattice

Actions imply each other. If you have *, you have admin; if you have admin, you have interact and every mcp:<tool>. So a single admin row on a folder covers every tool call inside it — you do not list them one by one. One matching deny stops the check, even when other rows would allow it. The full principal shapes, the action lattice, and the two seeded roles are tabulated in reference / grants; here we stay with the four words and some real rows.

three rows, three real patterns

Each row below is something you would actually write. The CLI form is arizuko group <instance> grant <principal> <scope> [action]; the action defaults to admin.

1. Alice can talk in her own folder.

principal: google:114alice   action: interact   scope: alice

2. The eng folder admin manages the whole subtree. The glob eng/** matches eng, eng/sre, eng/sre/oncall, and so on.

principal: google:114alice   action: admin   scope: eng/**

3. Ban one user globally. A deny row at scope ** beats every allow.

principal: discord:user/badguy   action: *   scope: **   effect: deny

The same shape grants a whole channel at once: make the room the principal (discord:837…/channel/1504… with interact on main/lab) and everyone who joins the room picks up the grant for free. Full syntax in reference / grants.

roles — one indirection, many members

When the same permission set should apply to several people, you do not copy the row. You make a role, grant the role, and add members: one acl row for the role, one acl_membership edge per member. Both travel in a manifest through arizuko apply.

acl:             principal: role:editor   action: admin   scope: docs/**
acl_membership:  child: google:114alice   parent: role:editor

Adding a second editor — one more edge. Granting editors a new scope — one more acl row. Roles can contain roles: role:senior-editor as a child of role:editor works the same way. A write that would make a principal its own ancestor is refused, so the walk always ends.

claiming a channel identity

Alice posts in Discord as discord:user/811…. She also has a Google login. The agent hands her a pairing link; she opens it in a browser, logged in as Google, and confirms. That writes one membership edge:

acl_membership:  child: discord:user/811...   parent: google:114alice   added_by: pairing

That edge is the claim, and only Alice's browser confirm can write it. The next Discord message from her expands to include the canonical sub; any grants on google:114alice apply automatically. No acl row gets rewritten, no migration runs — the channel-side id keeps working.

the person talking does not lend the agent their power

On the agent's socket a turn has two principals: the folder it runs in, and the person who sent the message. The folder's grants count everywhere they reach. The sender's grants count only inside that folder's subtree, and only on the exact action. Why so stingy? Because otherwise an operator chatting in a team room would quietly hand that room's agent the operator's reach — and anyone who could get the operator to say something there could borrow it. A deny counts on both, so a person's deny still refuses the turn they triggered.

where the check runs

Every gate asks the same question — may this principal do this action on this scope? A message wanting into a folder hits a gate once; a tool call leaving that folder hits one again. The two faces share the handler, the folder-containment rule, and the check itself. An operator’s REST call and an agent’s MCP call both land in auth.Authorize, over the same acl rows; what differs is only where the principal came from — a JWT subject on one side, the socket’s folder on the other. There is no second mechanism for agents and no default derived from where a folder sits. The full call signature lives in reference / grants.

A subagent holds exactly what its parent holds. When an agent spawns a Claude Code subagent inside its turn, the subagent talks over the same unix socket, so the gate sees the same principal and answers the same way. There is no narrower set for a narrower job: a subagent spawned to summarise one file can still call every tool the parent can, secrets and outbound requests included. That is deliberate — the socket is the boundary, and a second socket would be a second answer to the same question. Scope the parent folder to what you are willing to let a subagent do, not just what the agent itself needs.

don't do this

  • Don't insert deny rows to "take back" access. Remove the allow row or the membership edge instead. Denies are for true exceptions — banning one user from an otherwise-open channel — not for undoing yesterday's grant.
  • Don't grant admin with a params predicate. Admin means full write at scope. Conditional admin is surprising. Use mcp:<tool> with params when you want a narrow capability.
  • Don't put routing into ACL. The routes table answers "where does this message land." acl answers "may this principal act here." They share the principal namespace for room ids but never merge.
  • Don't bypass roles for operators. arizuko group <instance> grant <sub> '**' makes someone an operator by adding them to role:operator. Adding more operators is another membership edge — not a fresh wildcard grant each time.
  • Don't put a predicate on a folder: principal. The agent's socket carries no login claims, so the row can never match. Put the predicate on a user principal instead.
