onboarding

Onboarding is how a new user gets in and how a group comes to exist. When a new user arrives, the onbod daemon decides whether the user gets in and which group the user lands in. It also binds the identity of the user to one canonical sub. Nobody creates a group by hand: every group is the result of an admission. Three paths lead in: invite tokens, the admission queue, and pairing a second chat to an account that already has a world.

A chat needs a pairing and a route before an agent answers

The figure follows a chat that no route claims, from its first message to its route. Read it from top to bottom. Two separate facts must become true before an agent answers. First, the identity of the chat is tied to a person, which is the pairing edge. Second, the chat points at a folder, which is the route row. Routing never reads the ACL, and the ACL never creates a route, so a stranger with neither gets nothing from either side.

The figure has a second path at the top. The operator can claim a held chat from the dashboard with no pairing, which gives the route half alone. Onboarding is the self-service path to both halves, and the two paths never check each other. A chat that got a greeting and never paired stays in the held list until someone claims it.

An invite token admits one person to one folder

An operator creates a token with the CLI:

arizuko invite <instance> create <target_glob> [--max-uses N] [--expires DURATION]
arizuko invite <instance> list   [--issued-by SUB]
arizuko invite <instance> revoke <ref>

The token is a row in the invites table, which onbod owns. target_glob is a folder, and a trailing slash changes its meaning:

corp/eng
The person who redeems the token becomes an admin of that folder.
corp/eng/
The person can create a new folder under it and names it on the next screen.
/
The person can create a top-level world.

** is not a folder, so onbod refuses it. onbod keeps only the sha256 of the token. --max-uses defaults to 1. --expires takes a Go duration such as 72h, and without it the token never expires.

The recipient opens the link and picks an OAuth provider: GitHub, Google, Discord or the Telegram widget, as the instance configures. authd then signs the person in under the returned sub. auth explains what a sub is and how linking works.

The greeting is a pairing link

When ONBOARDING_ENABLED=true, a chat that messages the instance and matches no route gets a reply. The reply is one link, valid for ten minutes, that proves the person who opens it can read that chat. An agent creates the same link with issue_pairing_link, so onboarding has no login of its own. The greeting is fixed text plus the link, never an agent turn. A chat that belongs to no folder has no spend cap to limit a turn. The link signs the person in, shows exactly which chat account it attaches to their name, and asks for confirmation. Nothing is written until the person confirms.

The confirmation binds an identity and nothing more. It does not decide where the messages of the chat go. The next screen decides that, as a choice the person makes. See routing.

An expired link is not a dead end. Ten minutes is short on purpose, because the protection is the confirm page, not the clock. A new message in the same chat brings a greeting with a new link. Two conditions prevent noise: the chat must speak again, and the previous link must have expired. A chat that has a route since then, or that stopped speaking, never gets a second greeting.

The admission queue decides whether the instance takes you

Pairing says who you are, and the queue says whether this instance takes you. The two are separate on purpose, and they happen at different times. The binding is immediate. The verdict arrives at the next poll of onbod, every 10 seconds by default.

Rows in the onboarding_gates table of onbod control the queue. You manage them with arizuko gate or /v1/gates. A gate key names an identity provider:

*
Every account.
google:domain=example.com
Google accounts in one domain.
email:domain=example.com
Email accounts in one domain.
github:org=kronael
Every GitHub account. The gate does not check the organisation. To limit GitHub sign-in to one organisation, set GITHUB_ALLOWED_ORG for authd.

Each gate can carry a daily limit. The admitFromQueue loop runs about every 60 seconds. It counts the admissions of the current day and moves queued users to approved until the gate reaches its limit.

A queued user sees the position in the queue on /onboard, which refreshes every 30 seconds. An operator approves users manually in dashd or changes the gate configuration.

A refusal goes to the chat. If gates exist and none matches the account, the chat gets a message that says so. The person does not get a browser error on a page that they already closed. With no gates at all, everyone who pairs is approved.

An approval lets you create a workspace only when a gate exists

An approval lets you create your own workspace. You pick a username, and that name becomes a top-level world that you administer. You need no invite and no admin. This is the purpose of the queue: an approval gives a real right.

The right exists only on an instance with at least one gate. This condition is the switch between two very different instances. With no gates, everyone who pairs is approved. If an approval alone allowed a workspace, anyone who messaged the bot on a new instance could take a tenant. Because a gate is required, nothing changes until you decide.

The two setups are:

No gates
The default. Workspaces come only from invites. People can still pair chats and get approved, but an approval gives no workspace.
One or more gates
Self-service signup, limited by the gate. The gate decides who can queue, and its daily limit decides how fast they get in.

A disabled gate does not count, so a gate must be enabled. The same rule decides who gets queued and whether an approval gives a workspace, so the two can never disagree.

onbod checks the right when it writes the workspace, not when it draws the page. A hidden button is not a lock, so a request to the address of the button gets the same refusal.

SetupGroup writes every new group

When a user has the right to a workspace, through an invite or through an approval under a gate, onbod calls container.SetupGroup(cfg, folder, seedDir). That function is the only correct way to create a group. Never mkdir a folder under groups/ by hand.

The function creates the group directory and logs/. If a seedDir is given, it copies that directory in: the CLI passes a product template, and onboarding passes none. Then it runs seedGroupDir, which writes four things:

.claude/skills/
Every directory under ant/skills/ with a valid name. See skills.
.claude/CLAUDE.md
A copy of ant/CLAUDE.md.
.claude/.claude.json
A user id for the folder, the sha256 of arizuko:<folder>.
Ownership
Every file belongs to uid 1000, so the node user of the guest can write.

A folder made without SetupGroup is a folder the agent cannot use: it has no skills, no settings and the wrong owner. Everything that onbod does for a new user goes through this one call.

A second chat pairs to the same account

A person who already has a world and arrives on another platform does not onboard again. The person pairs the new chat to the existing account, and the chat gets everything that account holds. No queue and no new group are involved.

You can undo every binding with one verb, unpair. It reaches every binding, both those an agent created and those a greeting created, because one piece of code writes them all. Access ends on the next action of that account, not after a restart.

Invites and gates have limits

An invite token enforces max_uses at redemption: the UsedCount column increments, and RevokeInvite marks the token dead. onbod refuses an expired token, where expires_at < now, with an error. The daily limit of a gate resets at the UTC day boundary: the queue counts admissions whose queued_at is in the current day.
