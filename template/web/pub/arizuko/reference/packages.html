packages

A package is a git source or a local directory that ships any subset of the asset kinds as one versioned unit. The figure shows the path from the catalog or a git source to a running container.

┌──────────────────────────────┐   ┌──────────────────────────────┐
│ catalog: template/services/  │   │ source: git URL or local dir │
│ <name>.yml, <name>.yaml      │   │ *.yml, *.yaml, skills/       │
└──────────────┬───────────────┘   └──────────────┬───────────────┘
               │ packages add <name>              │ packages install <src>
               │ files linked                     │ files copied
               └─────────────────┬────────────────┘
                                 ▼
┌──────────────────────────────────────────────────────────────┐
│ installPackage: every check before the first write           │
│ 1 parsePkgManifests: rows parse, grants inside --folder,     │
│   no core route path, owner stamped package:<name>           │
│ 2 checkSourcedFiles: install only, the fragment stays in     │
│   its own namespace                                          │
│ 3 provisionPkgEnv: generate, default, required against .env  │
│ 4 files into <data>/services/                                │
│ 5 rows applied live through apply's engine, all or none      │
│ 6 skills/ into <data>/skills/                                │
│ 7 installed_packages row (folder '', name)                   │
└────────────────────────────────┬─────────────────────────────┘
                                 │ upgrade, sync, remove read the row back
                                 ▼
┌──────────────────────────────────────────────────────────────┐
│ arizuko generate                                             │
│ relink catalog copies, then compose.Generate: one include:   │
│ per fragment and COMPOSE_PROFILES; write proxyd_routes rows; │
│ copy package skills into every group; write                  │
│ docker-compose.yml                                           │
└────────────────────────────────┬─────────────────────────────┘
                                 ▼
                          docker compose up

products apply <folder>: the group-scoped half. groups/<folder>/arizuko.toml
is blended into that group, one installed_packages row per (folder, product).

Every check runs before step 4. A row apply that fails in step 5 removes the files again, so a refused package leaves no fragment and no row. The rows of step 5 apply at once. Only the compose fragment waits for generate.

Six commands manage packages

arizuko packages <instance> add gitd                     # a bundled package, from template/services/
arizuko packages <instance> install github.com/org/pkg   # or a local dir
arizuko packages <instance> upgrade pkg                   # refuses locally-edited assets
arizuko packages <instance> sync                          # re-apply every package at once
arizuko packages <instance> remove  pkg                   # deletes exactly what it owns
arizuko packages <instance> list

A package that adds a daemon which reads the store, gitd or a channel adapter, needs that daemon’s own store key minted and written to env/<daemon>.env before the next generate (INSTALL.md § The per-daemon store keys). Without it the daemon refuses to dial the store and exits at boot, and that one exit takes the whole instance into a restart loop under systemd (BUGS L406); generate logs store enrolment is partial at ERROR, names it, and then continues.

sync is upgrade for every installed package in one pass — useful after pulling new revisions of several sources. It prints updated, unchanged or SKIPPED per package, and a package already at its recorded revision is left completely alone, so running it twice costs nothing. A hand-edited file is skipped with a note rather than stopping the run: one local edit should not block every other package from syncing.

Not the same as the catalog relink generate does. That one turns a fragment which is still an exact copy of the bundled catalog into a symlink, so catalog fixes reach you; it never looks at the installed-package record. sync is about sources and revisions.

A package ships three asset kinds

KindFileApplied to
compose fragment<name>.ymlservices/, up on generate
config manifest<name>.yamlthe rows it names — proxyd_routes, acl, scheduled_tasks, network_rules, web_routes — applied live in one transaction, no restart
skillsskills/<name>/copied into every existing group on each generate, overwriting the group’s copy; a .disabled marker or a stock skill’s name stops it

What a package needs from .env

A manifest’s env section names each key the process needs, with one of three sources: generate: true (minted once at install, then it is your line), default: <value> (derived on every generate, never written; your .env value wins) or required: true (install and generate refuse until you set it). The point: a package never installs and then fails to start.

The section is a declaration, never a script. It names keys and where their values come from, and nothing runs. Hand the same file to arizuko apply and it refuses the env section and points you at packages add, because an apply would report success for keys it never provisioned.

Upgrade and remove touch only what the package owns

  • Each install writes an installed-package record (source + resolved revision + owned identities + a per-asset content hash).
  • upgrade compares the current content hash against the record; a locally edited (dirty) asset is refused, not overwritten.
  • An install is whole or nothing: the manifest is validated before the first write and its rows land in one transaction with pre-image rollback, so a package whose third grant is bad leaves the first two unwritten.
  • remove deletes exactly the identities the record owns — rows are withdrawn before the fragment is dropped, and a route or grant you added yourself at another key is untouched.
  • upgrade and sync run the same updater, so the refuse-a-dirty-asset rule is identical by construction. They rewrite only the file half of the record; the rows and skills it owns stay recorded, so remove can still find them.
  • A catalog package has nothing to re-fetch: its fragment is a link that follows the catalog. Its rows were applied once, by add. If the catalog manifest moved since then, upgrade and sync say so and name the fix, packages remove then packages add, rather than answering “nothing to do”.

Blending several products into one group

A package installs against the whole instance. A product seeds one group — and a group is not limited to one. Write groups/<folder>/arizuko.toml (the agent sees it as ~/arizuko.toml), listing the products in the order they should blend, then apply it:

name = "support-team"

[[product]]
source = "ant/examples/support"     # relative → joined to HOST_APP_DIR

[[product]]
source = "github.com/org/our-brand" # git → cloned and pinned to a revision
arizuko products <instance> apply <folder>

Two products have no common ancestor, so nothing here merges two files' text. Each kind of file gets one rule:

The group owns its arizuko.toml. Root metadata and ordered selections stay byte-identical through apply and sync. A selected source with its own nonempty selections refuses; list those sources explicitly in the group file.

A metadata-only manifest is a no-op without installed records. Missing or empty selections with records refuse before writes. If a group has products.toml, move or merge its entries into arizuko.toml, then remove products.toml. Both legacy-only and mixed declarations refuse.

The CLAUDE.md regions are <!-- arizuko:package:<name> BEGIN --> and its END twin, one pair per product. A malformed marker — a BEGIN with no END, a duplicate, an END before its BEGIN — refuses to rewrite the file. The alternative is guessing where a region stops, and a wrong guess deletes your own lines.

Re-applying also drops what a product shipped last time and no product in the mix ships now. “Still shipped” is checked against the whole mix, so moving an asset from product A to product B keeps the file. A dropped file that you edited since the last apply stays where it is, with a warning.

A collision refuses the whole apply and writes nothing, rather than picking a winner — if two products both ship facts/pricing.md, silently keeping one discards the other's knowledge. Rename one, or drop it from the mix.

Each product in the mix gets its own installed-package record, so re-applying is safe: an unchanged mix writes nothing and reports unchanged. arizuko packages <instance> sync re-applies groups discovered through installed records alongside the instance's packages.

arizuko create --product and arizuko group <instance> add <jid> <folder> --product seed one product's payload and write a single-source group declaration. They create no installed record. Matching existing declarations keep their bytes; conflicts refuse before payload writes. Run the first products apply explicitly before packages sync can update the group.

Installed packages and blended products are both listed in the operator dashboard at /dash/packages/; the folder column is empty for an instance-wide package and names the group for a product.
