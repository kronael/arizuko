environment variables

The environment variables of the arizuko daemons: the file and line that read each one, the type, the default and the effect. The last section names the variables that the code reads and that this page does not describe. Test-only variables are left out.

core (LoadConfig) agent spawn chanreg arizuko CLI arizuko run (compose) routd runed (turn substrate) proxyd webd onbod dashd timed ttsd litellm teled discd whapd emaid slakd split daemons (routd / runed / authd) the store server observability (OTLP)
Four helpers read most variables. chanlib.EnvOr(k, d) returns d when the variable is empty or unset. chanlib.MustEnv(k) calls os.Exit(1) when the variable is unset. chanlib.EnvDur(k, d) reads a Go duration such as 30s or 5m, and returns d when the value is empty or does not parse. The code default of an adapter LISTEN_ADDR differs for each daemon, but every service fragment in template/services/ sets :8080. The numbers 9001 to 9010 below are the source defaults for local development with several daemons.

core — consumed by every Go daemon via core.LoadConfig

These are read in core/config.go through chanlib.EnvOr / EnvInt / EnvDur and the resolveTimezone() helper. Every daemon that calls core.LoadConfig() (routd, onbod, webd, …) inherits this surface.

SECRETS_KEY

AES-256-GCM key for the secrets table — secrets are encrypted at rest. Required: routd refuses to start without it, and there is no plaintext mode and no AUTH_SECRET fallback. The value is a comma-separated keyring: the first key seals new writes, the rest are decrypt-only, so a value sealed under an old key still reads. To rotate, put the new key first and keep the old one after it; re-write each secret so the new key seals it; remove the old key only after every row is re-written. A v2: value that no key opens is an error, never plaintext. arizuko create generates a random key into the new instance’s .env; the arizuko secret CLI uses the same keyring. Stored values carry a v2: prefix; a row without it is read back as stored, and arizuko secret seal-legacy seals such rows in place.

Read bycore / core/config.go:266 → routd, arizuko secret CLI
Typestring (comma-separated keyring; first = active seal key)
Defaultnone — routd exits if unset; arizuko create generates one
Example9d4f...new,2a17...retired

agent spawn — what runed forwards into the turn's guest

Model keys are env-profile keys. ANTHROPIC_API_KEY, CLAUDE_CODE_OAUTH_TOKEN, OPENAI_API_KEY, and CODEX_API_KEY pick which model a turn talks to, so they are user-scoped credentials, not folder secrets — the store rejects them at folder scope. A user sets their own in a dedicated dashboard section at /dash/me/env, and that value overrides the operator default for their spawns. The host .env value below is the instance-wide default forwarded when a user has set nothing. See secrets. With the litellm package the forwarding stops: the gateway reads the credential from .env and the guest gets MODEL_GATEWAY_KEY instead.

routd

Apart from HITL_WAIT and the PROACTIVE_* set below, routd takes every value from core.LoadConfig above. Egress isolation is not a setting on routd or anywhere else: runed starts one egress proxy per turn and refuses to start if the binary is missing (RUNED_EGRESS_BIN).

The PROACTIVE_* vars tune proactive interjection — the agent speaking without being addressed. They are read once at startup by routd.LoadProactiveConfig, called from routd/cmd/routd/main.go. All of them do nothing unless PROACTIVE_ENABLED is on. Per-group opt-in is separate: a proactive: block in the group’s CLAUDE.md frontmatter, not an env var.

runed — the turn substrate

A turn is one ephemeral KVM guest: qemu-system-x86_64, direct kernel boot, two virtio-fs shares, a vsock control channel, and one tap with its own rule set and its own egress proxy on the host side. Every value below is a setting in the generated env, never something runed derives from a runtime path. The kernel and the rootfs are release artifacts whose names carry a version and a config hash; a daemon that went looking for them would find whichever was newest.

runed resolves and checks all of them once, at start, in runed/qemuhost.go qemuPreconditions — and refuses to start when any is unmet, naming every one in a single message. Checking per turn instead would give you a fleet that reports healthy and answers nothing. There is no substrate selector: one substrate, one legal value, no setting.

RUNED_KERNEL_DIR

The make kernel artifact directory, holding bzImage and initrd.gz. The directory name carries the kernel version and a hash of the build's inputs, so it is configuration and never a guess. runed boots the guest from both in place and copies neither. Required: unset, or either file missing, and runed refuses to start.

Read byruned / runed/qemuhost.go qemuPreconditions
Typepath
Defaultnone — required
Example/srv/data/arizuko_krons/images/kernel-6.1.112-40e1508980d0

RUNED_ROOTFS_DIR

The unpacked release rootfs, exported once per release by make images, shared into the guest read-only. The directory name carries the arizuko-ant image id it was exported from, so a guest cannot boot last week's tree against this week's agent. Beside the tree sits .image-env.json — the agent image's own ENV set, which a directory cannot carry and which runed applies in the guest instead. A rootfs with no readable copy of that file is a refusal, not a guess: without the image's PATH the agent's runtime is not on it.

RUNED_VIRTIOFSD

The daemon that exports the guest's two shares. It must be the Rust build. runed greps the binary's --help for --uid-map and --gid-map and refuses QEMU's C build, which advertises neither and needs real root. Alpine's virtiofsd package installs the Rust daemon at this default path; on Debian the same second path (/usr/lib/qemu/virtiofsd) holds the C one instead, which is why the check names the flags and not the file.

the store server

Every owner's tables live on one DynamoDB-protocol server per instance — ExtendDB over PostgreSQL, shipped as the extenddb package. Each daemon reads the five keys below and signs as itself, so the server's policy can bound what each one reaches. A daemon without DYNAMODB_URL refuses to start: there is no file to fall back to. Bring-up is in INSTALL.md § The store server: one extenddb init run prints the admin password, and extenddb manage mints one access key per daemon.

The key is minted by hand, so it can be missing. A daemon that has DYNAMODB_URL and no key refuses to dial (dynstore: endpoint ... takes an access key and a secret) and exits at boot. Because docker compose up runs under systemd, that one exit restart-loops the whole instance (BUGS L406, measured on sloth). arizuko generate logs store enrolment is partial at ERROR, names those daemons and then continues (compose/compose.go warnPartialEnrolment, over store.StoreReach). Enabling a package that adds a daemon, gitd for one, without minting its key puts the whole instance in a restart loop.

The endpoint every daemon opens its owner’s tables on. Required: unset, each daemon refuses to start with names no endpoint.
