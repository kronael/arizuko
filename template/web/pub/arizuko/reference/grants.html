arizuko › reference › Grants

grants

One policy evaluator checks whether a principal may perform an action on a scope. Matching local ACL rows decide before the release defaults. A folder path grants no authority.

See concepts › authorization for the mental model, GRANTS.md for the maintainer walkthrough, and auth/README.md for the figure and every rule behind the evaluator. Code: auth/authorize.go (the evaluator), auth/grant.go (delegation), auth/acl.go (scope matcher), store/acl.go (reader / writer).

One acl row is one rule

One row answers one question:

(principal, action, scope, params, predicate, effect, grant_option)
   → allow | deny
columnmeaning
principalWho is asking. Globbed segment-wise on / and :.
action*, admin, interact, egress, web:publish, gh:write, codex, mcp:*, mcp:<tool>, shell:env:<KEY>, ext:<provider>:<area>:<verb>, hold:mcp:<tool> or <resource>.<verb>.
scopeFolder path or glob. ** crosses /, * does not.
paramsOptional predicates over the call's arguments (jid=telegram:*).
predicateOptional condition on the caller's JWT claims (discord:guild=G123). Empty = none.
effectallow or deny. Deny wins within the selected layer.
grant_option0 or 1. 1 means the holder may re-delegate this row or a subset of it.

Holding a call for a human

A hold:mcp:<tool> row does not grant or deny anything. It says the call must wait for a person. When the agent makes it, the call does not run: a pending_actions row is written, the chat gets a notice, and an operator answers /approve <id> or /reject <id>.

# hold every delete this folder makes
principal = folder:atlas   action = hold:mcp:delete   scope = atlas

# hold only when the argument matches — reads and staging stay inline
principal = folder:atlas   action = hold:mcp:network_allow   scope = atlas
params    = host=*.prod.example.com

Approval buttons and /approve, /reject and /always reach the held call while the agent waits. A green or red reaction on the notice works too; 👍 and 👎 deliberately do not, because they are ordinary social reactions. The reviewer needs an admin grant covering the held row’s folder. The agent’s socket has no face of pending_actions at all: an agent that could approve would approve its own call.

  • The call waits. The gate suspends the tool call and polls for a verdict for up to HITL_WAIT, 10 minutes by default; it must stay under RUNED_RUN_TIMEOUT, or the guest is killed first. Approval runs the same call, with the arguments the notice showed, in the same turn. A reject or a timeout answers the agent with a tool result, NOT RUN (id …), telling it not to retry.
  • The hold runs before the authorization check, and never replaces it. An approved call still meets Authorize. An elevated /root turn has no hold gate.
  • A hold that cannot be recorded still holds. If the pending_actions row cannot be written, the call is blocked and the agent gets an error, because there is no id anybody could approve.
  • /always is /approve plus one skip-approval row. The row is effect = deny on the hold: action — deny on a hold means “do not hold” — and it is written in the same batch as the verdict. There is no third verdict on pending_actions. To revoke, remove that row with remove_acl or arizuko group … ungrant.
  • /always requires declared keys. The tool declares which arguments a standing rule pins. Only like declares a key, reaction. A missing scalar value or a value that cannot form an exact matcher refuses the rule. The notice, REST row and writer use the same rendered rule. Tools without keys offer no Always button and refuse /always.

Hold actions use the same evaluator as ordinary permissions. actionCovers accepts an exact hold action or hold:mcp:*. Other action grants do not cover holds. Matching local rows decide first. Defaults from auth/defaults.go decide only when no local row matches. Deny wins within the selected layer. A local hold can therefore override a default skip.

If the policy read fails, the hold gate blocks the call. Approval still requires the tool's authorization check. CheckGrant checks the reviewer and standing rule before their batch proves the policy version.

Nothing in the row is derived. A path is a routing target, a JID prefix, a home shared into the guest, and a web vhost — it is never an authority level, and how deep it sits means nothing here.

Two tables hold local policy data

  • acl — (principal, action, scope, effect, params, predicate, granted_by, granted_at, grant_option). Local permission rules in routd's store. The release defaults are code in auth/defaults.go.
  • acl_membership — (child, parent, added_by, added_at) edges. Walked transitively at authorization time to expand a principal into every role it carries and every identity it has been linked to. A write that would make a principal its own ancestor is refused.

Row counts stay small — hundreds, not millions. Adjacent tables in play but orthogonal: groups (what folders exist), routes (which JIDs land in which folder).

Actions form a lattice, evaluated rather than denormalized (actionCovers in auth/authorize.go):

*  ⊃  admin  ⊃  interact
*  ⊃  mcp:<tool>      admin  ⊃  mcp:<tool>      mcp:*  ⊃  mcp:<tool>

Granting admin is not the same as inserting one row per mcp:<tool>. The lattice is the contract — a tool added tomorrow is covered by yesterday's admin row.

There is no policy language. OPA and Rego are not used, and the lattice is never flattened into one row per tool: the common case is gating like reply(jid=slack:*), which one row and a params glob already say.

Scope is the folder path globbed segment-wise (matchPattern in auth/acl.go): * does not cross /, ** matches zero or more segments. It is a pure function — no DB query.

Params and predicates narrow a row

Two optional columns narrow a row further. Both use the same grammar:

spec  := clause ("," clause)*
clause := name "=" glob        # value must glob-match
        | name                 # must simply be present

params is checked against the call's arguments, predicate against the caller's JWT claims. A value glob runs over the whole value, so * crosses : and /: jid=telegram:* covers telegram:group/123. Every clause must hold; a missing key fails the row.

Arguments reach a row only where the gate passes them. The messaging tools pass jid, so a jid= row works. Most other tools check the grant with no arguments at all, so a row with params matches nothing there: a deny on such a tool is tool-wide only. A hold receives the arguments, so a hold can be shaped. A predicate on a folder: principal never matches, because the agent’s socket carries no login claims.

params:    jid=telegram:group/*     # only sends into telegram groups
params:    readonly=true            # only the read-only form of the call
predicate: discord:guild=G123       # only when the caller's token carries that guild

A row that fails on params or predicate simply does not match. It neither allows nor denies — denial comes from an explicit effect='deny' row, or from nothing matching at all.

auth.Authorize evaluates every request

auth.Authorize reads the policy and calls Policy.Allows. Operator REST and agent MCP calls use this evaluator with their own caller and target bounds.

1. Read memberships and local rows in one consistent policy read.
2. Add the applicable defaults from auth/defaults.go.
3. Match each layer against the action, scope, predicate and params.
4. Use matching local rows when any match; otherwise use matching defaults.
5. Within that layer, refuse on any deny; otherwise allow on an allow.
6. Refuse when neither layer supplies a matching allow.

Route grants use their full scope and action coverage. Sender-only allows require a target inside the turn folder's subtree. Sender actions match exactly or through their namespace wildcard. Denies count on both axes within the selected layer.

A failed policy read refuses access. Each ordinary non-elevated tool gate reads the current policy, so a revoke applies on the next checked call. Elevated turns bypass ordinary tool gates. Rule mutations still pass CheckGrant.

auth.EffectiveActions lists allowed tool actions at any scope from both layers. Denies do not hide a tool from the list. The per-call gate still checks the target and denies.

Default policy comes from one file

[auth/defaults.go] declares the release defaults. Membership selects which role defaults a principal receives. Folder creation adds the role:member edge. World creation also adds role:world.

The binary supplies the defaults at each deploy. Startup writes no default ACL rows. Local rows survive restarts. A stored copy remains a local override until an operator removes it after an audit. arizuko group grants lists stored rows and memberships without the release defaults.

Making someone an operator adds one membership edge:

arizuko group -i krons grant google:114alice '**'

The operator shortcut requires an omitted action, empty params and predicate, and an allow effect. An explicit admin or * writes an ordinary ACL row. The host CLI uses its own authority.

A holder delegates only what it holds

auth.CheckGrant checks the door's ACL question and the proposed mutation in one consistent read. It returns the policy version that the write must prove. A changed version refuses the batch with HTTP 409.

MutationRequired authority
Add an allow or remove a row outside hold:Covering authority with the grant option.
Add a deny outside hold:The door's authorization check.
Add or remove a hold ruleadmin on the rule's scope, without the grant option.
Add a membership edgeAuthority for the parent's allows and hold rules in both layers.
Remove a membership edgeAuthority for the parent's denies, hold rules and local allows.

For containment, any local row with an overlapping action and scope selects the local layer. Otherwise defaults decide. A deny in that layer refuses the authority check. A covering allow must have no predicate. Its scope must cover the request. Its params must be empty or identical. Sender-only allows cannot supply a turn's grant authority. An added allow cannot target a wildcard principal.

ACL writes, unpair, dashboard grants and approval resolution use this check. Elevated rule mutations use the issuer's current authority. Host CLI and manifest writes, consent pairing and folder bootstrap use their own authority.

An invite grants admin, so its issuer needs covering authority with the grant option. The check runs at issue, at redemption and before an invited world writes its grants. A world's default agent grants do not meet that requirement. The recorded issuers cli, onbod and routd use trusted authority.

Unpair also checks the authority carried by the parent. A parent deny or a local allow without sufficient grant authority can prevent self-unpair. The REST caller must also be the parent. An operator can perform the authorized agent operation.

A group purge can remove denies that affect other folders. Only the host CLI purges groups. Dashboard deletion removes nothing and names arizuko group -i <instance> rm <folder>.

The scope glob contains the folder

The grant's scope glob bounds its target. For an agent turn, sender-only allows also require the target to be inside the turn folder's subtree. Route grants retain their full scope. Authorize(caller, action, ACTUAL-target, params) checks these rules in one call.

acl(folder:acme/ops, mcp:register_group, 'acme/**', allow)

  register_group("acme/ops/oncall")   → allowed
  register_group("acme/billing")      → allowed
  register_group("other/team")        → denied

So a management call passes the real target as the scope, and the row's glob decides. Widening reach is editing one glob, not moving a folder.

Turn capabilities work the same way. At dispatch, routd resolves five booleans from acl and sends them typed on the run request (routd/dispatch.go): share_mount(readonly=true) makes the shared mount read-only, egress appends * to the folder's allowlist so the turn's proxy runs in allow-all, web:publish opens the web surface, and gh:write lets the agent make the GitHub writes that the gh gate of the agent refuses by default, such as a merge or a release, and codex lends the operator's Codex login (HOST_CODEX_DIR) to the turn. A plain folder holds none of them and runs with a writable share, an allowlist of exactly what its own rows name, and no web surface until an operator delegates. The proxy itself is never optional — every turn gets one, and the guest's tap drops anything that tries to go around it.

One grant carries a value rather than a boolean. A capability credential normally reaches a tool and nothing else, through the broker, per call. A CLI the agent drives itself — gh, buildkite — is a Bash call, so there is no tool name to resolve a secret for; it can only authenticate from the shell environment. A shell:env:<KEY> row names one secret that may cross, and with no row nothing crosses. The action matches exactly or through shell:env:*, so an operator's (*, **) row does not confer it: widening the shell is always an explicit act. shell:env:* is the explicit all-keys row. The five model keys never cross this way, even under shell:env:* — they already reach the guest by their own door, and the store keeps them off folder scope.

That grant cannot bound what the token buys. Once the credential is in the shell the agent spends it with curl as easily as with gh, and no acl row sees the difference. Scope the token at the issuing service — a PAT minted without pull_requests: write cannot approve a pull request however it is called.

Four example rows

# Let a support agent send only into telegram groups.
principal: folder:atlas/support
action:    mcp:send
scope:     atlas/support
params:    jid=telegram:group/*

# Ban one user in this folder. The local deny decides.
principal: telegram:user/123456
action:    interact
scope:     atlas/support
effect:    deny

# Let a world agent create its own subgroups, and only its own.
principal: folder:acme
action:    mcp:register_group
scope:     acme/**
grant_option: 1

# Hand a team lead the route table for one subtree, without
# letting them pass it on further.
principal: google:114lead@example.com
action:    admin
scope:     acme/eng/**
grant_option: 0

Prefer deleting an allow row or a membership edge over inserting a deny. Denies are for true exceptions — one banned user in an open room — a deny in the selected layer refuses matching calls.
