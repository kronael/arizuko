MCP tools

Every Model Context Protocol tool the arizuko platform registers on a per-group unix socket. Generated from ipc/ipc.go and ipc/inspect.go. What the caller holds in acl filters the tool set that a session sees. A tool that the caller holds nowhere is never registered.

Every tool is a grant. Calling <tool> requires an acl row covering the action mcp:<tool>, checked by auth.Authorize against the target as scope. The seeded role:member role — which every folder gets at creation — covers the thirteen messaging verbs, disengage included; read tools and set_work need no grant at all. Everything else is a row somebody delegated. What tools/list advertises is auth.EffectiveActions over those same rows, so the list and the per-call gate cannot disagree. See grants.

One socket, one gate

Every tool below lives on one unix socket that routd binds for the turn. The figure shows the path of a frame and the tools that the socket registers. A tool that the turn does not hold is not on the list. A call that reaches a tool still checks the same rows.

messages

post

Create a new top-level post on a platform (bluesky post, discord channel message, reddit submission). Use for broadcast/announcement content that is not replying to anyone. Not for replies (reply), direct messages (send), or file delivery (send_file).

Source: ipc/ipc.go:1427 · Grant action: post(jid=...).

nametypereqdescription
chatJidstringyesTarget chat JID; grant-checked + folder-authorized.
contentstringyesPost body.
mediaarraynoFilepaths under ~/; validated by mountsec.

Returns: JSON {"ok": true, "id": "<platformId>"}; on adapter "unsupported", returns error text with platform hint.

reply

Use reply for answers to the user. Omit replyToId to use the current conversation, or supply an earlier message to quote. A declared task summary keeps replies inside its thread where supported. Existing threads take precedence.

Source: ipc/ipc.go:1312 · Grant action: reply(jid=...) · In role:member, granted to every folder at create.

nametypereqdescription
chatJidstringyesTarget chat JID.
textstringyesReply body.
replyToIdstringnoPlatform message id to thread to; defaults to db.GetLastReplyID(jid, "").

Returns: JSON {"ok": true, "id": "<platformId>"}; routd records the outbound row in messages with that id. Pass the id to edit to change the message in place.

send

Use send for a notification or an explicit different chat. Within a declared task, send shares the task’s thread placement. An explicit foreign chat keeps its own destination. Use reply for answers and send_file for files.

Source: ipc/ipc.go:1286 · Grant action: send(jid=...) · In role:member, granted to every folder at create.

nametypereqdescription
chatJidstringyesTarget chat JID; grant-checked + folder-authorized via authorizeJID.

Returns: JSON {"ok": true, "id": "<platformId>"}; routd records the outbound row in messages with that id. Pass the id to edit to change the message in place.

find_messages

Ranked search over every message the instance has recorded. query is words and all of them must appear: budget review needs both. A "quoted phrase" matches those words adjacent and in order; a leading - excludes a word or a phrase. There is no OR, no prefix* wildcard and no NEAR. Use to find a past message by what it said. Not for whole-chat scroll (inspect_messages), single-thread slices (get_thread), or platform-truth fallback (fetch_history).

Source: ipc/ipc.go:2275 · Registered only when db.FindMessages != nil. An ordinary caller sees only rows whose chat_jid is routed to its folder (post-fetch ACL via db.JIDRoutedToFolder); an elevated /root turn bypasses the filter. Answered from an in-memory BM25 index routd keeps over the messages entity (routd/msgsearch), walked from the store at boot and fed by routd's own writes. A search made while that walk is running is refused, never answered empty.

nametypereqdescription
querystringyesWords, all required; "quoted" for an exact phrase; -word to exclude. An unclosed phrase or a dangling - is an error the caller reads, not an empty hit list.
scopestringnoOne chat_jid (contains :) or a folder subtree (no :; matches routed_to and its children).
senderstringnoExact match on the sender.
sincestringnoRFC3339 lower bound (inclusive) on timestamp.
limitnumbernoMax rows; default 20; a value of 0 or less, or over 200, gives the default.

Returns: JSON {messages, count, source:"local-db"}. Each row carries chat_jid, sender, timestamp, content (the matched fragment with «» around each hit, not the full body), and rank (BM25 — lower is a better match). Ordered by rank, then newest first.

egress

Manage the egress allowlist each spawn’s own egress proxy is started with. The proxy is default-deny — a folder only reaches hosts it (or an ancestor) has been allowed. Rules cascade down the tree: a rule at a parent folder opens the host for every descendant. All three require the matching mcp:network_* grant. network_allow and network_deny check it again with the folder argument as the scope, so you manage egress only inside the subtree that your grant covers. No grant, no egress management. Backed by the network_rules table. Agent-only by design — there is no REST twin, and network_rules is not mounted at /v1/network_rules or listed in routd’s /openapi.json.

cost accounting

There is no cost tool. Where an instance runs a model gateway, the gateway meters every call that passes through it and is the only ledger of what was spent — arizuko stores none of it. A number the agent reported about itself is exactly what a bypassed gateway produces, so the harness logs the agent’s self-report and stores nothing from it.

A call the agent makes outside the gateway — codex for /oracle, say — is metered by nobody, and no spend cap covers it. The operator sees it on that provider’s invoice.

external REST tools

Beyond the hand-written MCP tools above, arizuko can expose a REST API as an MCP tool from a declarative [[connector]] TOML descriptor — no Go code per endpoint. A descriptor maps a tool name to one HTTP call; when the agent invokes it, routd makes the request directly on the host, injects the credential from the secrets table, and hands back only the response body. The token never enters the guest. Loader: routd/ext.go; dispatcher: ipc/extcall.go CallExtTool.

the descriptor

Each provider is one [[connector]] block with transport = "rest": a URL, the secret keys it may read, where those secrets go, and one [[connector.tool]] per endpoint. The tool's MCP name is <provider>_<tool> (e.g. cloudflare_dns_list). Path params in {braces} are filled from the call arguments; remaining args become the query string on GET/DELETE or the JSON body on POST/PUT/PATCH.

# connectors.toml (operator) or a built-in routd/extproviders/*.toml
[[connector]]
name      = "cloudflare"
transport = "rest"
url       = "https://api.cloudflare.com/client/v4"
secrets   = ["CF_API_TOKEN"]
headers   = { Authorization = "Bearer {secret:CF_API_TOKEN}" }

  [[connector.tool]]
  name        = "dns_list"
  description = "List DNS records for a Cloudflare zone."
  scope       = "ext:cloudflare:dns:read"
  method      = "GET"
  path        = "/zones/{zone_id}/dns_records"

credential injection

There is no auth-method enum. You write {secret:KEY} where the value belongs, and it is rendered per call into one of three sinks:

sinkexample
headers{ Authorization = "Bearer {secret:CF_API_TOKEN}" }
query{ ApiKey = "{secret:NAMECHEAP_KEY}" }
body{ apikey = "{secret:PB_API_KEY}", secretapikey = "{secret:PB_SECRET}" }

A bearer is a literal prefix, not a mode, so a provider with an unusual scheme needs no new case — and a provider with four credentials is written the same way as one with one. The value is looked up per call for the triggering user (their own key overrides the folder default), never held in the descriptor, and scrubbed out of the response text before it returns to the agent. A declared key the store resolves to nothing has its whole entry DROPPED, so a placeholder never travels upstream as literal text.

built-in DNS providers

arizuko ships descriptors for four DNS registrars, ready to use once the operator sets the provider's token: Cloudflare (CF_API_TOKEN), Porkbun, Gandi, and Namecheap. Each covers the list/create/delete DNS operations. Operators add their own providers by dropping a [[connector]] block into connectors.toml in the instance dir.

grant gating

Every [[connector.tool]] carries a scope of the form ext:<service>:<operation> (e.g. ext:cloudflare:dns:write). Registration is grant-filtered like every other tool: the tool joins tools/list only when Authorize(folder, scope) passes, so an agent sees an external tool only where its folder is granted that scope. A call-time grant check stays as defense in depth.

notes & gotchas

  • Registration is filtered by grants. registerRaw consults db.Visible — auth.EffectiveActions over the caller's acl rows, asking whether the caller holds mcp:<name> at any scope. Hold it nowhere and the tool is never added to tools/list. The call-time check still runs, so a tool that shows can still refuse a particular target.
  • Some tools need no grant. The inspect_* reads and set_work are registered unconditionally — they are the agent's view of its own folder, and gating them would only blind it. An elevated /root turn skips the visibility filter entirely and sees everything.
  • Route ownership is checked on top of the grant. Most JID-targeted tools call authorizeJID after the grant check: a caller cannot dispatch to a JID whose DefaultFolderForJID resolves outside its own folder subtree, even when the grant would otherwise permit it. That is why role:member can carry the messaging verbs at scope ** without letting a folder message the whole instance. A /root turn bypasses it.
  • The secret broker is live. An mcp or rest connector that needs a capability token has it resolved on the host at call time for the triggering user (their own key overrides the folder default), so the token never enters the guest. Registration happens once, when the turn’s socket binds: registerRaw, granted, regSocial, raw srv.AddTool.
  • Optional registration paths. Several tools are nil-guarded on the backing store function and silently absent if not wired: inspect_routing, inspect_tasks, inspect_session, inspect_identity, inspect_messages, find_messages (requires db.FindMessages), get_thread, fetch_history.
  • Cold-tier tools are resreg resources. Groups, acl, routes, web_routes, route tokens, network rules, scheduled tasks and the like are CRUD resources of the resreg engine. One handler serves the MCP tool, the REST endpoint, the YAML manifest and /openapi.json. The resource declarations are in resreg/resources/. See OpenAPI.
  • Route tools are delegated, never default. list_routes, set_routes, add_route and delete_route are not in role:member, so a fresh folder holds none of them. Someone with the grant and a grant option has to hand them over, scoped to a subtree. See grants.
