arizuko › howto › Upgrade

upgrade an instance

An upgrade is a rebuild from the new checkout and one restart. The part people miss is the two guest artifacts: each lands in a new directory, and .env has to name it.

the whole upgrade

Run it in the arizuko checkout. demo is the instance name; use yours.

git pull                                          # the new release
make build                                        # ./arizuko + daemon binaries
sudo make images DATA_DIR=/srv/data/arizuko_demo  # prints rootfs: <dir>
sudo make kernel DATA_DIR=/srv/data/arizuko_demo  # prints kernel: <dir>
sudoedit /srv/data/arizuko_demo/.env              # RUNED_ROOTFS_DIR, RUNED_KERNEL_DIR
./arizuko generate demo                           # read every warning it prints
sudo systemctl restart arizuko_demo               # arizuko run regenerates, starts
./arizuko send demo main "ping" --wait            # one reply proves the path

each artifact is a new directory

A turn boots a kernel and a root filesystem that live under the data directory, named by what is in them. runed reads the two paths from .env and never guesses:

make images ──► DATA_DIR/images/rootfs-<image id>/        ◄── RUNED_ROOTFS_DIR
make kernel ──► DATA_DIR/images/kernel-<version>-<hash>/  ◄── RUNED_KERNEL_DIR

make images exports a new rootfs tree only when the arizuko-ant image changed, and prints the directory either way. It keeps the newest two trees and names the older ones with make rootfs-stale; removing them is yours. make kernel builds only when kernel/Dockerfile, kernel/arizuko.fragment, kernel/check-config.sh or kernel/guest-init/*.go changed. Otherwise it prints is current and you leave RUNED_KERNEL_DIR alone. A kernel build takes a while, so it's good news when it doesn't happen.

Forget to repoint RUNED_ROOTFS_DIR and the new daemons boot last release's guest. Nothing errors.

read what generate warns about

systemctl restart runs arizuko run, which regenerates the compose file anyway. Running arizuko generate first puts its warnings on your terminal instead of in the journal. Two of them matter before the restart: a fragment it calls FROZEN, and a daemon with no store key, which restart-loops the whole instance.

expect one /migrate turn per folder

A release that bumps MIGRATION_VERSION makes routd queue one /migrate turn for every folder whose skills are behind. Real messages wait behind them, so the first replies after an upgrade are slow. The queue is empty when no guest runs:

pgrep -c qemu-system-x86    # 0 when the /migrate turns are done

roll back the guest

The older rootfs tree is still on disk. Set RUNED_ROOTFS_DIR back to it and restart. The daemons stay on the new images; rolling those back means building the old checkout.

the release gates

A maintainer's release runs the five post-deploy gates in [gates.md]. The last one, anteval --smoke, is the only one that proves a live agent still answers. Run it after the /migrate turns drain, or it measures the queue instead of the release.
