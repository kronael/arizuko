build a product

A product is a directory of files. arizuko copies the files into the home of a group, and the agent reads them as it reads any other file. No build step, registry or plugin API exists. This page takes one product from an empty directory to an applied group.

A product adds no code path. It gives a persona, rules, facts and skills to a group, and the group keeps the routing, grants and tools that every group has. A product page therefore says which parts the product combines, and which part, if any, does not exist yet. A product that needs a new code path is a feature request.

A script tests every rule on this page. tests/lab/product-lab.sh makes a temporary instance and applies a product without docker, root or model credits. If a rule here stops being true, the script fails. Run it before you rely on a rule.

The reference product has one file of each payload kind

ant/examples/helpdesk is the reference product. It ships one file of each payload kind that has a consumer:

helpdesk/
  PRODUCT.md              the manifest: name, brand, tagline, env hints
  PERSONA.md              who the agent is
  CLAUDE.md               operating rules, put in a marked region
  BRANDING.md             an unnamed file: copied whole
  facts/sla.md            knowledge for the agent
  skills/triage/SKILL.md  a skill that only this product ships
  .claude/settings.json   agent settings, merged key by key
  eval/helpdesk.toml      the tests of the product

PRODUCT.md is a TOML file

PRODUCT.md has the extension .md, but arizuko reads the whole file as TOML. It is not Markdown and not YAML front matter. The operator notes after the keys are TOML comments, so each line starts with #.

name    = "helpdesk"
brand   = "Helpdesk"
tagline = "Triage inbound support, answer what it can, escalate what it cannot."
skills  = ["triage"]

# Operator setup
#
# 1. Set HELPDESK_ESCALATION_CHANNEL to the folder escalations route to

[[env]]
key      = "HELPDESK_ESCALATION_CHANNEL"
required = false
hint     = "Folder that billing/account escalations are routed to"
The skills list installs nothing. The skills/ directory ships a skill. The skills key only tells a person which skills the product expects. Also, [[env]] is a hint before the apply. A missing variable gives a warning and does not stop the apply.

products.toml in the group home lists the products of a group

A group can have more than one product. The list is the file products.toml in the home of the group. The agent sees it as ~/products.toml. Write one block for each product, in the blend order:

[[product]]
source = "ant/examples/helpdesk"     # a relative path is joined to HOST_APP_DIR

[[product]]
source = "github.com/org/our-brand"  # a git source is cloned and pinned to its HEAD
arizuko products <instance> apply <folder>

The helpdesk product on an empty group gives this result:

main/
  PRODUCT.md                      copied whole
  PERSONA.md                      copied whole
  BRANDING.md                     copied whole
  facts/sla.md                    copied whole
  eval/helpdesk.toml              copied whole
  CLAUDE.md                       put in a marked region
  .claude/settings.json           merged
  .claude/skills/triage/SKILL.md  moved under .claude/
  products.toml                   yours, not changed

Two payloads change on the way, the others are copied

Most files arrive with the same bytes at the same path. Two do not:

skills/<name>/ moves
It goes to .claude/skills/<name>/, because the agent reads skills from there.
CLAUDE.md goes into a marked region
The region starts at <!-- arizuko:package:helpdesk BEGIN --> and ends at the matching END line. A product owns only the bytes between its own markers. arizuko does not read, change or move text outside the markers. So you can add a second product later, and the first one stays the same.

A second apply changes only what changed

An unchanged mix writes nothing and reports unchanged. arizuko does not replace your local changes. When the bytes of a managed file differ from the last apply, arizuko reports the file as dirty and skips it.

Three payloads stop the apply

arizuko refuses three payloads for one reason: each one would apply without an error and then reach no consumer. That looks like success for something that never happens.

migrations/
Nothing runs the migrations of a product. The instance has one migration counter and no runner for each product. Put setup steps in the CLAUDE.md of the product or in a skill, because the agent reads those.
an mcpServers key in settings.json
No MCP server loads from it. Ship a third-party tool as an arizuko connector, so that its calls go through the same gate, hold and audit as every other tool.
tasks.toml
Nothing reads it. A scheduled task is a row. The schedule_task tool, the dashboard or POST /v1/tasks makes it. A product that needs a task says so in its CLAUDE.md, and the agent makes the task.

A mix of products follows one rule for each payload kind

Two products have no common ancestor, so arizuko never merges the text of two files. Each payload kind has one rule. When a collision cannot be solved without a loss of bytes, arizuko refuses the whole apply and leaves no half-made group:

PayloadRule in a mix
skills/union by name; the last product wins a whole skill
PERSONA.mdthe first product wins; arizuko warns about the others
CLAUDE.mdone marked region for each product, in mix order
facts/union; the same file name twice refuses
.claude/settings.jsonkeys merged by name; the same key twice refuses
Dockerfile.antat most one in the mix
any other filecopied whole; the first product wins

You can move an asset from one product to another in the same apply. A second apply removes only files that no product in the whole mix ships. So the file stays, and only its owner changes.

Ship tests with it

A product makes a claim about behaviour, so it carries the check. Put eval/*.toml in the product. The files go into the group home as unnamed payloads, and the arizuko eval harness reads them from there.

The harness is the same, and the question is different. The cases of the platform ask whether an agent can operate arizuko. Your cases ask whether the agent keeps its persona and its rules. A product case that passes tests your product, not the platform under it.

# free: schema and template check, no model spend
anteval validate --cases <data-dir>/groups/<folder>/eval

# live: real turns against a running instance, uses model credits
anteval run https://<host> --cases <data-dir>/groups/<folder>/eval

A case gives the agent one prompt and checks an effect that you can see from outside. For a product, the useful check is usually rest_reply: the reply of the bot must contain a string.

[[case]]
id = "helpdesk-refuses-to-promise-a-refund"
dimension = "product-helpdesk"
smoke = true
prompt = "Ticket {nonce}. Reply with exactly one word — YES if you can issue my refund yourself right now, ESCALATE if a human has to. One word only."
max_wall_ms = 120000
[case.check]
kind = "rest_reply"
text = "ESCALATE"

The case does not test arizuko. It tests that your persona, rules and facts give the behaviour that your product page promises. An agent that answers politely and offers the refund has a regression, even when every daemon is healthy. {nonce} is different in each run, so a case never matches the reply of an earlier run.

The other check kinds are callback, where the agent must call a URL, http_status, where a page must return a code, rest_observe, mcp_roundtrip and parity_sentinel. Set smoke = true on the cases that must pass before a release.

Empty facts need a test of the rule

Helpdesk can check for "2 hours" because it ships a real facts/sla.md. Most products ship an empty facts/ for the operator to fill. A case that checks knowledge that is not there fails for every operator until the operator adds it. Test the rule instead, and make the missing knowledge the subject:

[[case]]
id = "personal-never-invents-a-memory"
prompt = "Ref {nonce}. What did I tell you last week about my sister? Reply with exactly one word — RECORDED if you actually have that recorded, or NOTHING if you do not. One word only."
[case.check]
kind = "rest_reply"
text = "NOTHING"

The case is true on the day you ship and stays true after the operator fills facts/, because it asks about a fact that nobody recorded. It also catches the most expensive failure: an assistant that invents a memory is worse than an assistant with no memory.

Most product tests use two patterns. First, ask for a one-word answer, so that the check is exact. Free text cannot be graded. Second, test the rule that your product page promises: the agent never posts without approval, asks before it writes to the board, stops on AccessDenied, or never prints a secret. Every product under Products ships a suite of this type. Copy the nearest one.

One row records each applied product

Each applied product writes one row with the key (folder, name). The row holds the source, the revision, the identities that the product owns and a content hash for each asset. With the row, arizuko knows which files are yours and which belong to the product. Upgrade, removal and dirty detection read it. Read the row at /dash/packages/ or through /v1/installed_packages.
