add a connector

A connector gives an agent a tool that calls somebody else’s API, without putting that API’s credential in the guest. You write one TOML block, store the secret, and grant the scope to the folders that should see the tool. This page walks one through, end to end, with a real API.

Background on what a connector is and why the credential stays on the host: concepts / connectors.

1. decide which transport

If the far side is already an MCP server reachable over HTTP, you want transport = "mcp" and you declare no tools — it publishes its own catalogue. If it is an ordinary REST API, you want transport = "rest" and one [[connector.tool]] per endpoint you intend to expose. The rest of this page does the REST case, because it is the one with choices in it.

2. write the block

Connectors live in connectors.toml in the instance directory, beside docker-compose.yml. Create it if it is not there. 

[[connector]]
name      = "statuspage"
transport = "rest"
url       = "https://api.statuspage.io/v1"
secrets   = ["STATUSPAGE_TOKEN"]
headers   = { Authorization = "OAuth {secret:STATUSPAGE_TOKEN}" }

  [[connector.tool]]
  name        = "incident_list"
  description = "List open incidents for a status page."
  scope       = "ext:statuspage:incident:read"
  method      = "GET"
  path        = "/pages/{page_id}/incidents/unresolved"

  [[connector.tool]]
  name        = "incident_create"
  description = "Open an incident on a status page."
  scope       = "ext:statuspage:incident:write"
  method      = "POST"
  path        = "/pages/{page_id}/incidents"

Two details decide whether this works on the first try. The Authorization value is a literal string you are writing, so the scheme word — OAuth here, not Bearer — is yours to get right. And {page_id} is a path placeholder, so it becomes a required argument on both tools automatically; you do not declare it.

3. store the secret

The key named in secrets is resolved from the secrets table at call time. Set it for the folder that will use it: 

arizuko secret <instance> set main/infra STATUSPAGE_TOKEN --value 'sp_live_…'

A person can hold their own key instead, and theirs wins over the folder default for turns they trigger: 

arizuko user-secret <instance> set 'slack:user/U123' STATUSPAGE_TOKEN --value 'sp_live_…'

This row is the only place the connector looks. The instance .env is the daemons’ environment, and a STATUSPAGE_TOKEN there is never sent by the connector, valid or not. The two can hold different values under one name.

4. grant the scope

Until a folder holds the tool’s scope, the tool is not in its tools/list at all. Grant read and write separately if you want them separate — that is why they are two scopes: 

arizuko group <instance> grant main/infra 'ext:statuspage:incident:read'  'main/infra/**'
arizuko group <instance> grant main/infra 'ext:statuspage:incident:write' 'main/infra/**'

5. restart and check

Connectors are read at routd start, so the instance has to come back up before the tool exists: 

sudo systemctl restart arizuko_<instance>

Then ask the agent in the granted folder what tools it has. The name to look for is <provider>_<tool> — statuspage_incident_list. If it is absent, the grant is the first thing to check: a missing scope produces no tool and no error message, by design.

when it does not work

  • The tool is missing. The folder does not hold the scope, or the block failed to load. A connector whose transport is neither mcp nor rest, or a rest block with no [[connector.tool]], is refused at load with the connector named.
  • The upstream returns 401. Check the secret is set for the folder or the user, in the secrets table and not in .env. An unset key does not send a placeholder — the whole header is dropped, so the request arrives with no credential at all.
  • The agent says the response is empty. A connector hands back the response body and nothing else. There is no status code for the agent to read, so an endpoint that answers 204 with no body looks like nothing happened.
  • The call reaches a host the folder is not allowed to reach. It will work, and that is expected: the request leaves from routd on the host, not from the agent’s network, so the egress allowlist does not apply. The grant is the boundary here.
