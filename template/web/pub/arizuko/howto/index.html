getting started

This page walks a fresh host from zero to a running instance with one channel and one invited user. Each step is one command. Skim the whole list first; come back and run them in order.

1. What you need

  • A Linux host you can sudo on. arizuko is tested on Debian 12.
  • Docker (with the docker compose plugin), for the daemon fleet.
  • Hardware virtualization with /dev/kvm reachable. Every turn is one KVM guest that runed starts with qemu-system-x86_64; runed refuses to start without it.
  • Go 1.27 to install the arizuko CLI (go install) or build from source.
  • About 4 GB of free disk under /srv/data/ per instance.
  • A public domain and TLS, only if you want web chat, OAuth login, or inbound webhooks from Slack/Discord. A local-only instance needs neither.
  • No ports open to the internet by default. Channel adapters listen on the docker network; webd + proxyd bind :80/:443 only when you turn on the web layer.

2. Install

Clone the repo. A self-hosted deploy needs it: the daemon images build from it, and so do the two release artifacts a turn boots — the guest kernel and the agent rootfs. Nothing bind-mounts the checkout at runtime; ant/ is baked into the image.

git clone https://github.com/kronael/arizuko.git
cd arizuko
make build
sudo make images   # build agent + daemon docker images
sudo install -m 0755 arizuko /usr/local/bin/arizuko

To grab just the CLI, go install github.com/kronael/arizuko/cmd/arizuko@latest — handy for the command itself, but a full deploy still needs the repo for the images and the runtime mount.

The make images step is the longest (several minutes the first time). It builds arizuko-ant:latest, the per-group agent image, plus one image per shipped adapter. From here, arizuko run generates a Docker Compose file and brings the stack up — Docker Compose is the deploy path. For Kubernetes, see Deploy on Kubernetes.

3. Create your first instance

Pick a short name. The name becomes the data directory and the systemd unit name.

sudo arizuko create demo

This seeds /srv/data/arizuko_demo/ with:

  • .env — instance config with a fresh AUTH_SECRET and SECRETS_KEY. Mode 0600. Edit it to add API keys later.
  • store/ — empty until the store server runs. It then holds the server’s config and certificate under store/extenddb/ and its PostgreSQL data under store/extenddb_db/, so one copy of the data dir carries every row. The rows themselves are written by their owner daemon at its first boot: routd seeds the ACL floor, the egress floor and the default group main.
  • groups/main/ — the first agent's home: PERSONA.md, .claude/ session dir, facts/, diary/.
  • ipc/main/ — placeholder for the MCP unix socket the agent will use.
  • web/pub/ — a copy of these docs, served by vited.

Pass --product <name> (for example --product assistant) to seed skills and a checklist of API keys to fill in. See products for the catalog.

4. Bring up the store server

Every daemon keeps its tables on one DynamoDB-protocol server, ExtendDB over PostgreSQL, and refuses to start without DYNAMODB_URL. The extenddb package brings both containers. The server’s one-off init is yours to run, because it prints an admin password once:

sudo arizuko packages demo add extenddb    # mints STORE_DB_PASSWORD and STORE_APP_PASSWORD
sudo arizuko generate demo
cd /srv/data/arizuko_demo
sudo docker compose up -d extenddb_db
sudo docker compose run --rm extenddb init \
  --pg-host extenddb_db --pg-port 5432 \
  --pg-user arizuko_demo --pg-pass "$STORE_DB_PASSWORD" \
  --extenddb-user arizuko_demo_app --extenddb-pass "$STORE_APP_PASSWORD" \
  --bind-addr 0.0.0.0 --tls-san extenddb \
  --config /var/lib/extenddb/extenddb.toml

init prints the admin password and the account id once. Put them in .env as STORE_ADMIN_PASSWORD and STORE_ACCOUNT_ID, start the server, then give the daemons the certificate:

sudo docker compose up -d extenddb
echo "STORE_CA=$(sudo base64 -w0 store/extenddb/.extenddb/tls/cert.pem)" | sudo tee -a .env

Each daemon signs into the server as itself, with its own access key in env/<daemon>.env and a policy bounded to the tables it opens. Minting those keys is a hand procedure with extenddb manage, one per daemon: INSTALL.md § The per-daemon store keys lists the daemons and the exact commands. A daemon with no key starts, then fails at its first store call while every health check reads green. arizuko generate logs store enrolment is partial and names the daemons still missing one; read that line before you move on.

5. Run it

arizuko run generates docker-compose.yml from the instance state and brings the stack up in the foreground.

sudo arizuko run demo

You should see extenddb, authd, routd, runed and timed come up. onbod joins when onboarding is on, and the web layer when WEB_PORT is set. In another shell, check status:

sudo arizuko status demo

For production, run arizuko as a systemd service named arizuko_demo instead of in the foreground. Logs then live in journalctl -u arizuko_demo — the docker log driver is none on purpose, so docker logs shows nothing.

6. Wire your first channel

An instance with no channel adapter has no way to receive messages from the outside. Pick one platform to start. Each guide covers the platform's app/bot setup, the env vars to drop into .env, and the arizuko group add command that binds a chat to a folder.

  • Slack — Slack App, signing secret, Events API.
  • Discord — bot token, mention-only channels, threads.
  • Asymmetric channels — ingest on one platform, reply on another.

Telegram, WhatsApp, Slack, Discord, Bluesky, Reddit, Email, X, and LinkedIn adapters ship in the repo. Their setup follows the same shape; see the README.md next to each daemon (teled/, whapd/, …).

7. Invite your first user

Mint a one-time invite link. target_glob decides which folders the new user will be granted access to. main/** means “the main group and any sub-group under it.”

sudo arizuko invite demo create 'main/**' --max-uses 1 --expires 24h

The command prints a token. Share https://<your-host>/onboarding/<token>. The recipient signs in with one of the configured OAuth providers, lands on a confirmation page, and their auth_users.sub is granted admin on the matched folders. List and revoke with arizuko invite demo list and arizuko invite demo revoke <token>.

8. Verify the agent responds

Two ways to confirm the loop is live.

From the host, inject a message and wait for the reply:

sudo arizuko send demo main "ping" --wait

From the channel, send a message in the wired chat and watch routd pick it up:

sudo journalctl -u arizuko_demo --since "2 min ago" --no-pager | grep -iE 'mention|spawn|reply'

Red flags in the log, and what each one means:

  • this host cannot run turns — a substrate precondition is unmet. The message names every one; the full set is in reference/env § runed.
  • guest did not open ctl within — the guest booted and never called back.
  • staging tree: mount source — a path the turn mounts that runed itself cannot open.
  • circuit breaker open — one folder failed too many turns in a row.

9. Back up and restore the setup

An agent is data, so the configuration is too. Export the whole instance config to one YAML manifest, keep it in git as a backup, and re-apply it to rebuild — on this host or another.

arizuko export demo > demo.yaml   # groups, routes, grants, ACL, web routes, schedules…
git add demo.yaml && git commit -m "demo config"
arizuko plan demo demo.yaml         # dry-run: what would change
arizuko apply demo demo.yaml        # apply the manifest back

The export/import round-trip is exact — apply a manifest to a fresh DB and re-export it, and you get the same config back (tested in resreg/engine_test.go). The agent's files — persona, memory, skills, diary under groups/<folder>/ — are plain files; back them up with git or any file copy. Together the manifest plus the group folder are the whole agent.

Further reading

Vocabulary:

group
A workspace. Files, diary, skills, and one agent live here. Folder name like main or corp/eng/sre.
agent
The Claude Code instance for a group. Runs in its own KVM guest, one per turn, started on demand and thrown away when the turn ends.
channel
Where messages flow in and out: Slack, Discord, Telegram, web, email, …. Each adapter is a separate daemon.
skill
A markdown file under groups/<folder>/.claude/skills/ the agent loads on start. One file, one capability.
route token
A URL-bound credential mapping to a group. /chat/<token>/ opens the guest chat widget; /hook/<token> accepts fire-and-forget webhooks. /slink/<token> answers a 301 to /chat/<token>/. See route tokens.

Audit mode (mute outbound)

Two env vars on routd run a group or platform in shadow mode: the agent keeps producing turns, every outbound row lands in messages, but nothing reaches the channel.

SEND_DISABLED_GROUPS
CSV of folder names. Example: SEND_DISABLED_GROUPS=atlas,research.
SEND_DISABLED_CHANNELS
CSV of platform prefixes (the part before : in a JID). Example: SEND_DISABLED_CHANNELS=discord.

Inbound is unaffected. The agent does not know it was muted — reply and send return success. Rows are visible at /dash/activity/ and via the inspect_messages MCP tool. Source: routd/server.go (group mute via SEND_DISABLED_GROUPS; SEND_DISABLED_CHANNELS mutes in the channel Deliverer), core/config.go (parsing).
