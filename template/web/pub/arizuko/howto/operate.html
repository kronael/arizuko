when it goes quiet, where to look

An instance that answers nothing usually stops at one of four places. Walk the message down the path, check each stop, and the first one that fails is your incident. Each incident below gives the symptom, what to read, the cause, the fix and the line of code that decides it.

the logs are in the journal

The systemd unit runs arizuko run, which runs docker compose up in the foreground. Compose forwards every container's output to its own stdout, and journald keeps it. So one command reads every daemon:

sudo journalctl -u arizuko_<name> --since "15 min ago" --no-pager

Don't trust docker logs here. A host whose Docker daemon sets "log-driver": "none" answers it with an error on stderr, and a | grep -c ERROR behind it counts the empty stdout and prints 0. Zero errors, from a command that read nothing.

walk the message down the path

Each stop has one thing that must be true and one place to read it:

platform message
      │
      ▼
┌───────────┐  healthy, "channel registered"    docker ps, journal
│  adapter  │
└─────┬─────┘
      ▼
┌───────────┐  a route answers, cursor moves    /dash/routes/, /dash/activity/
│   routd   │
└─────┬─────┘
      ▼
┌───────────┐  preconditions met, breaker shut  journal: "cannot run turns"
│   runed   │
└─────┬─────┘
      ▼
┌───────────┐  boots, calls back, submit_turn   journal: "turn did not start"
│ KVM guest │
└─────┬─────┘
      ▼
routd ──► adapter ──► platform reply

The quickest end-to-end probe skips the platform. arizuko send writes a message straight into a folder's queue as the operator and prints the reply:

./arizuko send <name> <folder> "ping" --wait

A reply here and silence on the platform puts the fault at the adapter. No reply here puts it at routd, runed or the guest.

incidents

runed refuses to start

Read
sudo journalctl -u arizuko_<name> | grep -A20 'cannot run turns'
Cause
runed checks every input before it serves a turn and prints all the missing ones at once: this host cannot run turns; N precondition(s) missing. The list covers root, the three device nodes /dev/kvm, /dev/vhost-vsock and /dev/net/tun, the qemu, egress, iptables and ip binaries, RUNED_KERNEL_DIR, RUNED_ROOTFS_DIR, the guest memory budget and the tap subnet.
Fix
Fix every line it names, then restart. An artifact it can't find comes from sudo make kernel DATA_DIR=… or sudo make images DATA_DIR=…; point RUNED_KERNEL_DIR and RUNED_ROOTFS_DIR in .env at the directories they print.
Source
runed/qemuhost.go:117 qemuPreconditions, the message at runed/qemuhost.go:218

guest memory times the cap is more than the host has

Read
The precondition list above carries RUNED_GUEST_MEM=… × MAX_CONCURRENT_CONTAINERS=… is … MiB, over this host's MemTotal.
Cause
Every concurrent turn is a guest with its own memory, so the host must hold the guest size times the cap. runed refuses the pair at start instead of failing on the second turn.
Fix
Lower RUNED_GUEST_MEM (default 2G) or MAX_CONCURRENT_CONTAINERS in .env and restart.
Source
runed/qemuhost.go:318 memoryFits

routd exits at boot without SECRETS_KEY

Read
The journal shows SECRETS_KEY required: secrets are encrypted at rest and routd exits 1.
Cause
routd seals every stored secret with a key derived from SECRETS_KEY and won't start without one. arizuko create writes it into .env; an .env rebuilt by hand loses it.
Fix
Put the instance's own key back from your backup of .env. A fresh key starts routd, but no value sealed under the old key opens with it. To rotate, set SECRETS_KEY=new,old: the first key seals, the rest only open.
Source
core/config.go:140, routd/cmd/routd/main.go:69, store/store.go:63

the instance restart-loops after packages add

Read
systemctl is-active arizuko_<name> says activating, two containers run out of fifteen, and the journal shows dynstore: endpoint "https://extenddb:18443" takes an access key and a secret from the daemon you just enabled. arizuko generate said it first: store enrolment is partial.
Cause
The daemon reads the store and holds no key for it. It exits at its first store open, its exit ends docker compose up, and systemd starts the whole instance again. arizuko has no command that mints a store key yet (BUGS L319, L406).
Fix
./arizuko packages <name> remove <pkg>, ./arizuko generate <name>, restart. Then mint the key by [INSTALL § The per-daemon store keys] and add the package again.
Source
objstore/dynstore/dynstore.go:69, the warning at compose/compose.go:1100

make images or make kernel stops with "set DATA_DIR"

Read
kernel: set DATA_DIR=<instance data dir> or rootfs: set DATA_DIR=<instance data dir>, exit 1.
Cause
Both artifacts land under DATA_DIR/images/. make kernel checks first. make images builds every image and only then reaches its rootfs step, so a run without DATA_DIR fails after the slow part.
Fix
sudo make images DATA_DIR=/srv/data/arizuko_<name>. The image builds are cached, so the second run goes straight to the export.
Source
Makefile:57, Makefile:308

a second instance's turns fail with "address already in use"

Read
vsock bind port 5555: address already in use on the newer instance, from its first turn.
Cause
The vsock CID and port space belongs to the host, not to an instance. Two instances on the defaults both take CID 3 and ports 5555 upward. A guest's two ports come from its slot, so one instance uses MAX_CONCURRENT_CONTAINERS CIDs and twice that many ports.
Fix
Give the second instance its own window in .env: RUNED_VSOCK_CID_BASE at least the first base plus the cap, RUNED_VSOCK_PORT_BASE at least the first base plus twice the cap. Give it its own RUNED_TAP_SUBNET too: a tap's addresses come from the subnet and the slot alone. Nothing detects an overlap, so write the windows down.
Source
runed/vmrecord.go:208 allocateCID, runed/vmrecord.go:238 vsockPorts, runed/vmctl.go:98, runed/vmnet.go:38

replies crawl right after a release

Read
sudo journalctl -u arizuko_<name> | grep 'auto-migrate' shows one version behind, triggering /migrate per folder.
Cause
A release that bumps MIGRATION_VERSION makes routd queue one /migrate turn for every folder whose skills are behind. Those turns hold the run slots, so real messages wait in line behind them.
Fix
Wait. The storm is over when no guest runs: pgrep -c qemu-system-x86 prints 0. Match the process name, which the kernel cuts to 15 characters, and never pgrep -f, which matches its own shell. Run an eval only after that.
Source
routd/loop.go:475 checkMigrationVersion

the data disk fills up

Read
sudo make rootfs-stale DATA_DIR=/srv/data/arizuko_<name> names every rootfs tree past the two kept. The Makefile puts one tree at about 8.3 GB.
Cause
Every release whose agent image changed exports a new images/rootfs-<hash>/ tree. make images keeps the newest two and deletes nothing, because a running turn may have an older one mounted.
Fix
Remove the named trees one explicit path at a time. Several instances on one arizuko-ant image can share one DATA_DIR for the artifacts, so the export happens once. docker builder prune -f frees build cache. Never docker image prune -a: no container holds arizuko-ant between turns, so the prune deletes it and the next rootfs export has nothing to read.
Source
Makefile:352 rootfs-stale, compose/compose.go:1237 hostViewPaths

WhatsApp stops and whapd stays unpaired

Read
The journal shows session invalidated; staying up unpaired — re-pair through /v1/pair, and whapd's /health answers 503.
Cause
WhatsApp ended the linked-device session on its side. whapd stays up on purpose, because the pairing endpoint lives in that process.
Fix
Open /dash/channels/whatsapp/pair, enter the bot's phone number, and type the 8-character code on the phone: Settings › Linked Devices › Link a Device › Link with phone number instead. No QR scan. The code lives 60 seconds, and whapd allows 5 starts an hour.
Source
whapd/src/main.ts:320, dashd/main.go:578, [whapd README]

two bots on one platform read the same account

Read
Both services answer as one bot, or the second one duplicates the first.
Cause
A second account is its own fragment, <adapter>-<label>.yml, with its own CHANNEL_NAME. It takes the base adapter's keys unless .env carries a <KEY>_<LABEL> line, so without one it polls the base account.
Fix
Set the override, for example TELEGRAM_BOT_TOKEN_JYNX for teled-jynx.yml, run arizuko generate and restart. Never add a second token to the base fragment.
Source
compose/compose.go:263 variantOf, template/services/teled-jynx.yml, [compose README]

a release fix never reaches one adapter

Read
arizuko generate prints services/<name>.yml differs from the catalog and is FROZEN and lists the catalog lines the file lacks.
Cause
Generate turns an installed fragment into a link to the template only while the two are byte-identical. A hand edit, even to a comment, keeps the file as it is for good, so it never takes a mount, env var or timeout the template gains.
Fix
Move the difference into .env, where STORE_HOST_PORT and the <KEY>_<LABEL> overrides live. Copy the template over the edited file, and the next arizuko generate links it.
Source
compose/fragments.go:62 RelinkCatalog, cmd/arizuko/packages.go:1228

an adapter sits at "starting" or "unhealthy"

Read
sudo docker ps --format '{{.Names}}\t{{.Status}}' | grep -E 'starting|unhealthy', then sudo journalctl -u arizuko_<name> --since "10 min ago" | grep -E 'channel (registered|deregistered)'.
Cause
A crash loop is loud. An adapter that never passes its healthcheck is just as down and stays quiet: no restarts, status health: starting for days. The cause is usually a credential the platform refuses, and routd deregisters the channel over and over.
Fix
Read the adapter's lines in the journal for the platform's refusal, put the new credential in .env, run arizuko generate and restart. A deregister count that tracks the register count means a flapping adapter.
Source
chanlib/chanlib.go:180, chanreg/chanreg.go:203

a chat takes messages and answers none

Read
/dash/activity/ for the newest message in and out of that chat, and /dash/routes/, whose unrouted section lists every chat routd drops. ./arizuko route <name> list prints the table by seq.
Cause
No route matches, so routd marks the batch seen and runs no turn. Or an #observe route sorts above the route that answers: the first match wins, an observe route carries no verb, so it takes every message, mentions included (BUGS L327). The cursor moves, the breaker stays shut, and nobody gets an error.
Fix
Add the route, or move the answering route's seq above its #observe twin. A route row is the operator's data: change it with arizuko route.
Source
routd/loop.go:565 routeMiss, dashd/routes_admin.go:105
