timed

What it is

In plain terms, timed is the alarm clock. It sends the agent a message at a set time or on a repeating schedule, so things happen without anyone there to type.

timed is the scheduler daemon. One Go binary that ticks every 60 seconds, asks routd for the tasks that are due, and posts each task’s prompt back to routd as a message, as if a user had just typed it. It opens no store: every read and write goes over routd’s HTTP API with a service:timed token.

Once the message lands in messages, routd picks it up through the normal poll loop and routes it to the task’s folder. The agent has no idea the prompt came from a clock.

Why it exists

Cron, recurring runs, and one-shot reminders all collapse to one need: drop a prompt into a folder at a future time. Keeping that loop inside routd would mix two clocks — one for inbound polling, one for scheduling — and tie cron behavior to gateway restarts.

A separate daemon driving routd over HTTP means routd stays a pure router and the only writer of its tables. Without timed, no task ever fires. The cron tools (schedule_task, pause_task, …) still write rows, but nothing claims them.

The loop

Each 60-second tick:

  1. GET /v1/tasks/due on routd. routd claims every active task whose next_run has passed, in one guarded write, and returns them. Two timed instances cannot double-fire the same task.
  2. For each task, POST /v1/messages with sender='timed' (or timed-isolated:<id> when the task asked for an isolated session) and the task’s chat_jid. The message id is sched-<task>@<next_run>, so a retry of the same fire is a duplicate routd drops.
  3. Compute the next fire with core.NextRun: the cron value as a 5-field cron expression in the daemon’s TZ, or as a millisecond interval, or empty for a one-shot.
  4. POST /v1/tasks/{id}/reschedule with the new next_run (a fired one-shot is marked completed), then POST /v1/tasks/runlog for the task_run_logs row.

How it fits

agent (or operator)
   |  schedule_task / pause_task / …
   v
 scheduled_tasks  (rows with cron + next_run)
   |
   |  timed ticks every 60s: GET /v1/tasks/due (routd claims them)
   v
 POST /v1/messages  (one message per fire, sender='timed')
   |
   v
 routd  --->  routes by chat_jid  --->  agent run

Inputs: the due tasks routd hands back, which agents and operators created through routd’s task tools. Outputs: one message per fire and one task_run_logs row, both written by routd on timed’s request.

Hard deps: a reachable routd, which owns scheduled_tasks and serves /v1/tasks, and an authd to exchange AUTHD_SERVICE_KEY with. timed itself serves /health, /openapi.json (empty, since it mounts no resource) and the operator page /dash/timed/.

Concepts: concepts/tasks covers the row anatomy, context modes, and the five MCP tools agents use to manage tasks.

Standalone usage

Yes. timed is a plain Go binary and it opens no database of its own — it reads and writes tasks over routd's HTTP API, so point it at a running routd. scheduled_tasks and task_run_logs are routd's, which routd owns and creates.

# build
make build              # produces ./timed

# run against a running routd
ROUTER_URL=http://routd:8080 \
AUTHD_URL=http://authd:8080 \
AUTHD_SERVICE_KEY=$(grep ^AUTHD_SERVICE_KEY .env | cut -d= -f2) \
TZ=Europe/Prague ./timed

GET /health on :8080 always returns 200 — timed holds no database handle to check. Red flag: no rows appearing in task_run_logs while scheduled_tasks has active rows past their next_run.

Key env vars

  • ROUTER_URL — required; routd's address, e.g. http://routd:8080.
  • AUTHD_URL / AUTHD_SERVICE_KEY — exchanged at boot for a service:timed token. Unset, routd denies every call.
  • TZ — timezone used to evaluate cron expressions (default UTC).

Full list and defaults in reference/env.
