runed

What it is

In plain terms, runed is the thing that runs the agent. When a turn needs to happen, runed starts one fresh, empty KVM guest with qemu-system-x86_64, lets the agent work inside it, then throws the guest away. There is one substrate and no setting that selects it.

runed is the execution plane. It serves the work queue, starts one KVM guest per turn, and enforces the run timeout. It holds /dev/kvm, /dev/vhost-vsock and /dev/net/tun plus the NET_ADMIN and SYS_ADMIN capabilities, and mounts no Docker socket at all. It never appends a message (routd is the sole appender), and it neither signs nor mints a token: authd is the sole signer, and runed reads authd’s public keys only to verify the callers of its own /v1.

runed owns its tables and creates them itself — the runtime tables (spawns and session_log) that have no home in routd.

Why it exists

A turn is one ephemeral KVM guest. (See the Turn primitive.) Something has to hold /dev/kvm and the other device nodes a guest needs, and only one thing should: that access is root-equivalent on the host, so concentrating it in one small daemon keeps the blast radius small. runed is that daemon.

Starting a guest is more than qemu-system-x86_64 -m 2G. runed has to build the staging tree and start virtiofsd for it, bring up the guest’s tap and its rule set, start its egress proxy on the host side of that tap, enforce RUNED_RUN_TIMEOUT so a runaway turn can’t burn forever, steer a live run over the vsock ctl frame, and tear the guest down cleanly by reaping every pid the turn's record names. What keeps a turn inside its folder is not a token runed hands out. It is a host kernel fact across two hops: the guest’s vsock CID, which the host’s vhost driver refuses to let any other guest claim, and a uid-1000 bridge that accepts a connection only from that CID and dials that one turn’s folder socket — so there is no credential inside the guest to steal.

Without runed, routd would have to hold those device nodes itself, mixing the routing plane with host-level guest control. Keeping them apart means the daemon that talks to the network (routd) is not the daemon that can start processes on the host (runed).

How it fits

routd
        |  POST /v1/runs   (scope runs:run)
        v
      runed   verify the caller  <-- authd public keys
        |     start this turn's egress proxy on its tap's host side, wait for /health
        |     qemu-system-x86_64: one guest, its virtiofs share, its tap
        v
      KVM guest   runs one turn, then powers off
        |     agent tools  -->  routd, over vsock through the uid-1000 bridge
        |                       (MCP socket hosted in routd, not runed)
        +-- timeout / ctl steer / power off + reap every pid --> runed

Inputs: POST /v1/runs from routd (the routd↔runed contract); authd’s public keys, fetched once at start, which it verifies those requests against. Outputs: a running guest; status and kill over /v1/runs/{run_id}; spawn and session rows in its own tables.

Hard deps: /dev/kvm, /dev/vhost-vsock and /dev/net/tun on the host; authd as the JWKS source; routd, which hosts the per-turn MCP socket and receives the agent’s tool calls. runed also starts one egress proxy per turn on that guest’s tap, and stops it with the turn — that isn’t a setting, runed refuses to start at all if the egress binary is missing.

Timeouts and shutdown

RUNED_RUN_TIMEOUT (default 20m) is the run ceiling, and it bounds two things at once: the guest hard-kill, and the in-guest agent query timeout (ARIZUKO_QUERY_TIMEOUT_MS = RUNED_RUN_TIMEOUT − 30s). The 30-second gap lets the agent abort and deliver a graceful summary before runed kills the guest under it. On graceful shutdown runed detaches in-flight runs, so a guest outlives the daemon and a restart doesn’t murder a turn mid-sentence — the next runed reaps it from the on-disk record.

Standalone usage

runed runs as a daemon, but it cannot do its job without the KVM substrate’s preconditions met and an authd whose keys it can fetch. It also expects routd to host the MCP socket the guest talks to. Run it only alongside those.

cd /srv/data/myinstance
export DATA_DIR=/srv/data/myinstance
export LISTEN_ADDR=:8080
export AUTHD_URL=http://authd:8080
export RUNED_RUN_TIMEOUT=20m
export RUNED_KERNEL_DIR=/srv/data/myinstance/images/kernel-6.1.112-40e1508980d0
export RUNED_ROOTFS_DIR=/srv/data/myinstance/images/rootfs-a35045d89e3e
# the host must expose /dev/kvm, /dev/vhost-vsock and /dev/net/tun
./runed

With AUTHD_URL unset the verifier runs open — local-dev only. GET /health returns 200 once the process is up; the red flag is spawns stuck in state=queued, which means the concurrency cap is full or a precondition the guest needs went away under a running daemon. A precondition missing at boot fails earlier than that: runed refuses to start at all, and the refusal names every one unmet at once.

What runed does not do

runed does not route messages, does not append to the message log, and does not sign tokens. It takes a run request, produces a guest, enforces its limits, and reports the result — the execution plane, nothing else.
