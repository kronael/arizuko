dashd

What it is

In plain terms, dashd is the control panel for whoever runs the instance. Open /dash/ in a browser to see groups, messages and tasks, edit routes and grants, answer held tool calls, and edit a few of the agent’s files.

It is two things. The hub at /dash/services/ is a grid of tiles, one per daemon, each linking to that daemon’s own page. The cross-cutting pages — anything that spans daemons or covers the whole instance — live in dashd itself. A page about one daemon’s runtime lives in that daemon: routd serves /dash/routd/, runed serves /dash/runed/, and so on, each from handlers next to its own /v1.

Why it exists

Without dashd, operators inspect an arizuko instance through each daemon’s /v1, journalctl -u arizuko_<inst>, and the arizuko CLI. That works for an engineer, but it asks a lot of anyone else, and it never gives a one-screen answer to “what is this instance doing right now”.

How it fits

Here’s every door dashd uses. The left box is what it touches with its own store key; the right box is what it asks other daemons for over HTTP.

browser
   │ /dash/...
   ▼
proxyd: auth "user", strips and stamps X-User-*, adds service:proxyd
   │ /dash/<daemon>/ ──────────────► that daemon's own page
   │ /dash/ and the rest
   ▼
┌──────────────────────────────────────────────────────────────┐
│ dashd: guard (ProxydTransit), then requireUser, requireAdmin,│
│ requireVisible or requireOperator                            │
└──────┬──────────────────────────────┬────────────────────────┘
       │ own store key                │ service:dashd bearer,
       │ StoreReach: routd, onbod     │ empty folder claim
       ▼                              ▼
┌──────────────────────────┐   ┌───────────────────────────────┐
│ routd tables             │   │ routd /v1: groups, tasks,     │
│ acl for every gate       │   │ routes, acl, route_tokens,    │
│ admin writes, AsUser     │   │ cost/summary, messages,       │
│ portal counts, packages, │   │ sessions, principals,         │
│ cooldowns, route joins   │   │ routing, engagement,          │
│ secret and env key names │   │ pending_actions, audit        │
│ onbod tables             │   │ onbod /v1: invites, audit     │
│ invite writes            │   │ runed, authd /v1/audit        │
└──────────────────────────┘   │ proxyd /v1/proxyd_routes      │
                               │ whapd /v1/pair                │
                               └───────────────────────────────┘
groups/<folder>/ files: memory pages, skill toggles, group bootstrap

The split isn’t arbitrary. dashd holds a store key for routd’s and onbod’s tables and nobody else’s. Writes stay direct because AsUser puts your sub on the audit row, in the same batch as the write — a call over /v1 would carry only service:dashd, and routd takes a forwarded user only from proxyd. Reads go over the owner’s /v1 wherever the owner serves one. The exception is your own secrets page: routd’s secrets resource is write-only on purpose, so dashd lists the key names straight from the table rather than ask routd to publish an API that lists secrets.

Identity comes from proxyd. Every /dash/* handler — read views included — runs through guard, which checks proxyd’s service:proxyd transit bearer before it trusts X-User-Sub and X-User-Groups. A request that skips proxyd never reaches a handler. Only /health, /openapi.json and the htmx asset stay public. Admin writes also run requireAdmin (an admin grant on the folder) and a same-origin CSRF check.

The hub

Each visit probes every daemon’s /health at once, with a 500 ms timeout, so one slow daemon can’t stall the page. A tile is ok, err (refused, timed out, or not 2xx) or unknown (the name doesn’t resolve, so the container isn’t deployed). There’s no “up but denied” state, because /health is public on every daemon. davd has no /health, so its tile probes GET /.

A tile links only if proxyd actually routes its /dash/<daemon>/ — dashd asks proxyd’s /v1/proxyd_routes. The route is the registration; nothing is discovered. If proxyd doesn’t answer, the hub links the core daemons only, so you never click into a 404. A red dot never hides a link: the daemon that’s down is the one you want to open.

Standalone usage

dashd needs a port and a way to reach routd’s tables — the store endpoint the instance is served from. Point AUTHD_URL at authd and dashd verifies proxyd’s transit bearer against its keyset on every /dash/* request. Leave authd unwired for local dev and the guard passes through, which is why you still front dashd with proxyd on the public internet: proxyd terminates TLS, runs the login flow, and stamps the X-User-* headers dashd trusts.

export DATA_DIR=/srv/data/arizuko_demo
export DASH_PORT=:8080
./dashd
# browse http://localhost:8080/dash/

DYNAMODB_URL names the store server, and dashd reads routd’s and onbod’s tables from it. DATA_DIR resolves the groups tree at $DATA_DIR/groups/, which is files on disk. GET /health answers 200 as soon as the process is up; a store that won’t open shows up as a red banner on the pages that need it, not as a failed health check.

The page set

Read views:

  • /dash/ — portal index linking the other pages.
  • /dash/status/ — groups, sessions, channels at a glance; for the operator, also which chats got no answer.
  • /dash/activity/ — the most recent messages across all groups.
  • /dash/tasks/ — scheduled tasks.
  • /dash/groups/ — group folders with their channel routes.
  • /dash/memory/ — the editable markdown view per group.
  • /dash/packages/ — installed packages and blended products from installed_packages (name, source, revision, owned assets). Read-only; install / upgrade / remove is the arizuko packages CLI.
  • /dash/profile/ — the subs linked to your login.
  • /dash/usage/ — per-folder model spend and turn counts. The spend comes from the model gateway through routd’s /v1/cost/summary; an instance with no gateway has no meter, and the page says so rather than showing a zero.
  • /dash/audit/ — the audit trail: newest first, filtered by category, actor or folder. Federated across routd, runed, authd and onbod — each serves its own audit_log at GET /v1/audit and dashd merges them, with a Source column. onbod joins only when its store is there: onboarding is optional, and a daemon you never deployed isn’t a source that failed. The “older” cursor carries one position per source, because two owners’ rows can share an instant and paging on the time alone would drop some.

Write pages (admin grant + CSRF):

  • /dash/routes/ — the message-routing table: which folder an inbound message lands in. For the operator it also lists the unrouted chats — every chat that has messaged the instance and reaches no group — with a one-click claim that writes the rule.
  • /dash/groups/new and /dash/groups/{folder} — group create, settings, grants, skill toggles, delete.
  • /dash/tasks/ — create, pause, resume, cancel. The create form takes a cron expression; a one-shot RFC3339 time is refused here, though the agent’s schedule_task accepts it.
  • /dash/tokens/{folder}/ — list and revoke route tokens. Nothing in the cockpit mints one.
  • /dash/me/secrets, /dash/me/env, /dash/me/connections — your own capability tokens, model keys, and “Connect GitHub” style OAuth.
  • /dash/approvals/ — held tool calls waiting for a human, scoped to the folders you hold admin on.
  • /dash/engagement/ — every conversation the agent is staying in without being addressed, with a disengage button. Operator-only.
  • /dash/proactive/ — which groups may speak first. Read-only: mode: stays in the group’s CLAUDE.md.
  • /dash/invites/ — invite create and revoke. Operator-only.
  • /dash/channels/whatsapp/pair — WhatsApp re-pair by code. Operator-only; dashd calls whapd’s /v1/pair/start and writes an audit row.

When an owner doesn’t answer, the page shows a red banner naming it. Never an empty table: “no routes” or “costs nothing” are things you’d act on, and they’re false when the source simply didn’t reply.

What dashd does not do

dashd does not send messages, mint tokens, or render another daemon’s runtime — runs, keys, the proxy route table and the onboarding queue are on their own daemons’ pages. It owns no table; every write lands in routd’s or onbod’s.
