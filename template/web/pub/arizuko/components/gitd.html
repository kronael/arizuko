gitd

gitd lets a GitHub repository talk to the agent in the same way as a Slack channel. It takes the signed webhook deliveries of GitHub, turns each one into an ordinary inbound message and gives it to routd. After that, a pull request is one more conversation.

gitd is a channel adapter for GitHub webhooks

gitd is a channel adapter with the same shape as slakd or teled. It checks the signed webhook deliveries and posts chanlib.InboundMsg rows to routd. A completed CI delivery can produce one row for each associated pull request. The actions of the agent on the repository, such as merge, label, review or close, go through the GitHub MCP connector. They do not use channel verbs, because they are repository actions, not chat.

gitd lets the agent hear from a repository

Without gitd, the agent can be told about a repository but cannot hear from it. Someone has to paste the pull request, and the agent answers about a snapshot that has already changed. With gitd, the repository takes part. The comment arrives as a message, the agent reads its thread, and the reply lands on the same pull request.

gitd receives events and posts replies. Repository changes such as merges use the GitHub MCP connector. Tool grants and GitHub permissions control those changes.

gitd sits between GitHub and routd

A webhook becomes an inbound message. gitd verifies the signature and sends the message to routd. The route table selects the group. gitd posts reply comments with a personal access token or an App installation token. Repository changes use the GitHub MCP connector.

gitd depends on routd for delivery and on the github_sources table of routd for the secrets. Nothing depends on gitd: without it, the repository stops talking to the agent.

A source is one webhook secret for one folder

A source is one webhook secret registered for a folder. GitHub sends the same signed post for all three kinds, and one receiver handles them:

kindnamepaste the URL and secret into
repo<owner>/<repo>the Webhooks page in the settings of the repository
org<owner>the Webhooks page in the settings of the organization, for every repository it owns
app<slug>the webhook settings of the GitHub App, for every installation
arizuko github -i <inst> add app arizuko-krons eng   # prints url + secret ONCE
arizuko github -i <inst> list                        # secrets never print again
arizuko github -i <inst> rm app/arizuko-krons eng    # 404s the URL, drops the routes

routd seals the secret under SECRETS_KEY in its github_sources table, and gitd unseals it for each delivery. The URL path /github/<kind>/<name> selects the secret that verifies the signature, so a payload never chooses its own verifier. A repository or organization source is also bound to its repository or organization. gitd refuses a payload that names another repository with 400, even when the signature is valid.

Open GitHub sources at /dash/github_sources/ to list, add or delete sources for your groups. Only group admins can change sources. The dashboard never shows secrets. Use arizuko github add for the one-time setup secret.

A GitHub App connects selected repositories

Use one GitHub App per instance. An installation gives the App access to selected repositories. A source checks webhook signatures and routes events to a group.

  1. In GitHub account or organization settings, open Developer settings → GitHub Apps → New GitHub App. Enter a name and your instance's public HTTPS homepage URL. Create the App. Record its numeric App ID. Read its slug from https://github.com/apps/<slug>. A private App installs only on its owner's account. Other accounts require a public App.
  2. Under Private keys, select Generate a private key. Keep the downloaded PEM file private. Run base64 -w0 /path/to/private-key.pem to encode the file as one line. Set the App ID and encoded key in the instance's .env:
GITHUB_APP_ID=<numeric-app-id>
GITHUB_APP_PRIVATE_KEY=<base64-pem>
  1. Register app/<slug> for the group that receives the events. Use the command below. Copy the returned URL and one-time secret into the App's Webhooks settings. Select Active. The URL is https://<instance-host>/github/app/<slug>.
arizuko github -i <inst> add app <slug> <folder>
  1. In Permissions & events, set the repository permissions below. Save the changes.
PermissionAccessPurpose
MetadataRead-onlyGitHub includes this permission automatically
IssuesRead and writeIssue comments and reactions
Pull requestsRead and writePull request comments, reviews and reactions
ContentsRead-only for file toolsWrite tools need Read and write
Checks and ActionsRead-only, optionalCI events

Subscribe to Issues, Issue comment, Pull request, Pull request review, Pull request review comment and Pull request review thread. For CI, also select Check run, Check suite and Workflow run. Add other permissions only when the selected tools or events need them.

  1. Open Install App and select an account. Choose Only select repositories. Select the repositories and install the App. An organization owner may need to approve the installation.
  2. Add the connector block from template/connectors/github.toml to the instance's connectors.toml to enable repository tools. Keep GITHUB_INSTALLATION_TOKEN in secrets and the Authorization header. Restart the instance with sudo systemctl restart arizuko_<inst> to load the configuration.

routd derives GITHUB_INSTALLATION_TOKEN from the trusted turn repository. Do not set this slot in .env or user secrets. The private key and installation tokens stay on the host. Tool access still requires mcp:github_<tool> grants. Holds still require approval.

In the App's Recent deliveries, check that a ping receives HTTP 200.

GitHub setup details: [App registration] and [permissions].

Source deletion and installation removal stop access

Delete a source in GitHub sources or run the command below. The webhook URL then returns 404. routd removes the source's seeded routes.

arizuko github -i <inst> rm app/<slug> <folder>

Source deletion does not uninstall the App or remove tool grants. To remove GitHub access, uninstall the App under Settings → Applications → Installed GitHub Apps. You can also remove individual repositories from the installation. gitd replies and App connector calls refuse access when the source or installation is missing.

GitHub describes the controls in [installation and removal].

The JID names the owner, the repository and the thread

github:<owner>                    account or org event, no repository
github:<owner>/<repo>             repo event — push, release, …
github:<owner>/<repo>/pr/<n>      one pull request
github:<owner>/<repo>/issue/<n>   one issue

The owner and the repository are in the JID, so one App secret for fifty repositories gives fifty JIDs. The ordinary route table maps them. The sender is github:<login>, the same principal that authd creates for a GitHub sign-in. So the dashboard login of a person and the comment of that person on a pull request are one identity.

Requests to the bot start a turn and the rest is observed

A new source gets <folder>#{jid} mention routes and <folder>?observe#{jid} fallbacks. The fragment gives each chat its full JID as the topic. An @mention of the bot written by a person anywhere (pull request, issue, discussion, commit comment, commit message or CI output), a review request or assignment to the bot, or a direct reply to a bot comment starts a turn. Pushes, review states and CI results that name no one never start a turn, even on a pull request that the bot reviews. Human comments and reviews with a body on a bot-authored pull request or issue also map to mention. Other activity lands as <folder>?observe#{jid}. After the bot replies, a human comment on an engaged pull request or issue starts a turn without a new mention. Only a message or mention rides that engagement. To route other CI rows while a conversation is engaged, add a route above the fallback, for example chat_jid=github:o/r/pr/* verb=check_run to team/reviewer?engaged#{jid}.

gitd makes no GitHub API call to classify an event. For CI, subscribe to check_run, check_suite and workflow_run. A completed delivery adds one observation row for each associated pull request. One CI delivery allows ten distinct pull requests; more are refused with 400.

Repository rows use seq 10 and 100, organization rows 20 and 200, and App rows 30 and 300, so a narrower registration wins. To change the split, edit the rows on /dash/routd/ or with arizuko route.

Every message opens with a location header

gitd puts one header line before the text of each message. For an inline review comment it names the event, the message id, the thread, the review, the file, the lines and the side, and it adds the last lines of the diff hunk in a code block:

[github kind=pull_request_review_comment id=gh-rc5678901234 thread=gh-rc5678901200 review=gh-r6789012345 path=gitd/verify.go lines=10-12 side=RIGHT url=https://github.com/kronael/arizuko/pull/12#discussion_r5678901234]

Every other event carries the keys it has, such as kind, id, url and the review state. The agent reads the place of a comment from the header and needs no extra API call.

gitd posts replies as comments

For each reply, gitd selects the most specific registered source: repo/<owner>/<repo>, then org/<owner>, then app/<slug>. Repository and organization sources use GITHUB_TOKEN, a personal access token. App sources use an installation token for that repository. Missing App access refuses the reply without a PAT fallback. The connector's GITHUB_INSTALLATION_TOKEN slot also requires an App source for the trusted repository.

A reply goes to the pull request or issue that the JID names. The agent must pass replyToId from the message header. A gh-rc id keeps the reply in that review thread. A gh-c id answers in the conversation.

gitd does not edit comments. The eyes reaction on the starting comment shows that a turn runs. gitd drops its own comments and other bot comments. Without a personal access token or App credentials, gitd only receives events.

The answer to a delivery shows what happened

The “Recent deliveries” tab on GitHub shows the answer of gitd, which is the fastest way to see what happened:

answermeaning
200 {"ok":true,…}delivered to routd
202 {"retained":true}routd was down, and the row waits in the tables of gitd for delivery
200 {"dropped":"bot"|"self"}ignored on purpose
401bad signature
404unknown source
400a payload outside the source, or routd refused it
503neither routd nor retention accepted the message

GET /dash/gitd/ lists the last accepted delivery for each source. It is the shared adapter page, rendered by the same code as for every other adapter.

gitd runs alone with routd and the store

gitd runs alone. It needs routd to deliver to and a store to read its sources from, and nothing more:

Run arizuko store enroll first. The commands read the external store settings from .env and the scoped pair from env/gitd.env.

export ROUTER_URL=http://routd:8080
export SECRETS_KEY=$(grep ^SECRETS_KEY .env | cut -d= -f2)
set -a
. ./.env
. ./env/gitd.env
set +a
export GITHUB_TOKEN=<token>        # optional; enables send_text
export LISTEN_ADDR=:8080
./gitd

Point a webhook at http://<host>:8080/github/<kind>/<name> with the secret that arizuko github add printed. Any program that speaks POST /v1/messages like routd can replace routd, and the end-to-end tests run gitd in that way.
