gitd

A GitHub repository talks to the agent the way a Slack channel does. gitd takes GitHub's signed webhook deliveries, turns each one into an ordinary inbound message, and hands it to routd. From there a pull request is just another conversation.

What it is

gitd is a channel adapter, the same shape as slakd or teled. It checks signed webhook deliveries and posts chanlib.InboundMsg rows to routd. Completed CI can produce a row for each associated pull request. Repository actions — merge, label, review, close — go through the GitHub MCP connector.

Why it exists

Without it a repository is a place the agent can be told about but cannot hear from. Someone has to paste the pull request, and the agent answers about a snapshot that has already moved. gitd makes the repo a participant: the comment arrives as a message, the agent reads the thread it belongs to, and the reply lands back on the same pull request.

It stays an ingress and nothing more on purpose. Merging, labelling and reviewing are repository actions with their own permissions, and routing them through chat verbs would mean inventing a second permission model beside GitHub’s. They go through the MCP connector instead, where the token’s own scope is the limit.

How it fits

Shape: GitHub webhook → gitd (verify signature, resolve the source, build the JID) → routd (route table decides the folder, and whether this fires a turn) → the agent. Outbound is the GitHub MCP connector, not gitd — except send_text, which posts a comment when GITHUB_TOKEN is set.

gitd depends on routd for delivery and on routd’s github_sources table for the secrets. Nothing depends on gitd: remove it and the repo simply stops talking.

Sources

A source is one webhook secret registered against a folder. GitHub sends the same signed POST for all three kinds, and one receiver handles them:

kindnamepaste the URL and secret into
repo<owner>/<repo>the repo’s Settings → Webhooks
org<owner>the org’s Settings → Webhooks, covering every repo it owns
app<slug>the GitHub App’s Webhook settings, covering every installation
arizuko github <inst> add app arizuko-krons eng   # prints url + secret ONCE
arizuko github <inst> list                        # secrets never print again
arizuko github <inst> rm app/arizuko-krons eng    # 404s the URL, drops the routes

The secret is sealed under SECRETS_KEY in routd’s github_sources table and unsealed per delivery. The URL path /github/<kind>/<name> picks which secret verifies the signature, so a payload never chooses its own verifier. A repo or org source is bound to its repo or org as well: a payload naming a different repo is refused with 400 even when the signature checks out.

The JID

github:<owner>                    account or org event, no repository
github:<owner>/<repo>             repo event — push, release, …
github:<owner>/<repo>/pr/<n>      one pull request,  topic=pr/<n>
github:<owner>/<repo>/issue/<n>   one issue,         topic=issue/<n>

Owner and repo ride in the JID, so one App secret serving fifty repos yields fifty JIDs and the ordinary route table maps them. The sender is github:<login> — the same principal authd mints for a GitHub sign-in, so a person’s dashboard login and their PR comment are one identity.

What triggers a turn

PR mentions, direct replies to bot comments, and assignments or review requests addressed to the bot trigger a turn. Assign the bot to a PR to watch state changes and completed CI. Plain comments stay in <folder>#observe, including on watched PRs and in bot-started threads. Issue-only events, requests for other people, and repository events also stay in context. Engagement does not promote these events.

Subscribe to check_run, check_suite and workflow_run for CI. Completed events read current PR assignees with the token’s Pull requests read permission. Unassociated, queued and in-progress events perform no lookup. A delivery allows ten distinct PRs and ten seconds for lookups. A lookup failure returns 503 before forwarding; GitHub’s redeliver button retries the same delivery safely.

Repo rows sit at seq 10 and 100, org at 20 and 200, app at 30 and 300, so a narrower registration wins. Operators can edit the rows in /dash/routd/ or with arizuko routes.

Replying

send_text, send_file and edit require GITHUB_TOKEN. Replies post to the PR or issue the JID names. A reply to an inline review comment stays in that review thread. The token’s own comments and other bot comments are dropped; typed PR state and CI events from automation remain eligible. Without a token gitd is ingress-only.

Reading a delivery

GitHub’s “Recent deliveries” tab shows gitd’s answer, which is the fastest way to tell what happened:

answermeaning
200 {"ok":true,…}delivered to routd
202 {"retained":true}routd was down; the row waits in gitd’s tables for re-delivery
200 {"dropped":"bot"|"self"}ignored on purpose
401bad signature
404unknown source
400payload outside the source, or routd refused it
503CI lookup failed, or neither routd nor retention accepted the message

GET /dash/gitd/ lists the last accepted delivery per source. It is the shared adapter page, rendered by the same code every other adapter uses.

Standalone usage

gitd runs on its own. It needs routd to deliver to and a store to read its sources from, and nothing else:

export ROUTER_URL=http://routd:8080
export SECRETS_KEY=$(grep ^SECRETS_KEY .env | cut -d= -f2)
export DYNAMODB_URL=https://extenddb:18443
export AWS_ACCESS_KEY_ID=... AWS_SECRET_ACCESS_KEY=... AWS_REGION=us-east-1
export GITHUB_TOKEN=ghp_...        # optional; enables send_text
export LISTEN_ADDR=:8080
./gitd

Point a webhook at http://<host>:8080/github/<kind>/<name> with the secret arizuko github add printed. Anything that speaks routd’s POST /v1/messages can stand in for routd, which is how the end-to-end tests run it.
