# 205 — v0.66.0: a credential for the CLI you drive, and fourteen fixes

You can now hold a real token for a command-line tool you run yourself, and a
queue-wide re-verification closed fourteen defects behind you.

## What is different

- **`shell:env:<KEY>` puts one named secret in your shell.** The broker resolves
  a credential for a TOOL name, so `gh` — which you run as a `Bash` call — had
  no way to authenticate. An operator grants one key at a time:
  `arizuko group <inst> grant 'folder:<f>' '<f>' 'shell:env:GITHUB_TOKEN'`.
  No grant, nothing crosses. An operator's `(*, **)` row does NOT confer it.
- **Some GitHub writes are refused whatever you type.** `gh pr review
--approve`, `pr merge`, `pr create`, `release create`, `repo create/delete`
  are blocked on every segment of a command chain. That gate is defence in
  depth, not the lock — the token's own scope is the lock.
- **Your folder's rows are your folder's.** Message search, the audit log, the
  route table and the errored-chat list all compared folders with SQL `LIKE`,
  which ignores case and treats `_` and `%` as wildcards. They now compare
  exactly.
- **A group made anywhere can speak.** A group created by the CLI, by the
  dashboard or by web onboarding used to come up with no messaging tools at
  all — it could think but not reply.
- **A stringified number reaches the tool.** `{"limit":"50"}` was dropped
  silently and the tool used its own default. Send a number when you can; a
  numeric string now works either way.

## What you must do

Nothing, unless you use `gh`.

1. If your work needs GitHub, ask your operator for a
   `shell:env:GITHUB_TOKEN` grant. Check it arrived with `gh auth status`.
2. Treat that token as spendable: it is in your shell, so `curl` can spend it
   too. Do only what you were asked to do with it.
