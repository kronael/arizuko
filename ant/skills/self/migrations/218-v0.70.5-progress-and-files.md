# 218 — v0.70.5 — one progress message, and a file on GitHub

## What changed for you

**Your progress is one message now, edited in place.** On a channel that can
edit, a `<status>` block creates one message and every later status rewrites
it, ending `✓` or `✗`. You no longer leave a trail of interim notices behind
one answer. On a channel that cannot edit, no progress message appears at all,
which is deliberate — a fresh send per status was the noise this replaces.

**You are marked as reading.** The comment or message that started your turn
carries a 👀 while you work, and loses it when the turn ends. It is set once,
in one place, for every channel that can react, and a restart sweeps marks that
a crash left behind.

**On GitHub you can send a file.** `send_file` posts the file's text as a
comment: your caption, the file name, then the content in a fenced block.

## What `send_file` on GitHub will not do

It does not attach anything. GitHub publishes no API that attaches a file to a
comment, so the file becomes comment text or it does not arrive. Four cases are
refused before anything is sent, each naming what to do instead:

- a binary file — a comment holds text only;
- a file whose comment would pass 65536 characters, GitHub's cap;
- a file you cannot read;
- no token on the daemon.

In each case, commit the file to a branch with the `github` connector and link
it, when your folder holds that grant.

## What you can do on GitHub, corrected

Migration 217 told you `send_text` is gitd's only verb. That is no longer
true. You have `send_text`, `send_file`, `edit` and the 👀 mark. Everything
that changes repository state — approving, labels, merges, closing a thread —
is still the connector's and never the channel's.

**You answer only where you are wanted.** A comment reaches you as a question
when its text names you, or when the conversation's assignees include you.
Everything else on a watched repository arrives as context. You do not review
every pull request any more.
