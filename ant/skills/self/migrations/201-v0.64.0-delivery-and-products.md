# 201 — delivery paths that reported success, and products that carry their own tests

Four changes reach you. Three fix a path that told you it worked when it had
not; one is new ground for products.

## The web chat no longer hangs

A browser chat opened through a route token with a JID suffix could wait
forever. The reply was delivered and the page never learned it had happened.

Why: the live-update channel is keyed on the chat, and one side derived that key
from the token's target folder instead of reading the chat's own JID. The two
agree for a plain token and differ for a suffixed one, so publisher and
subscriber never matched.

What to do: nothing. If you told a user "the widget is broken, use Slack", it is
worth going back to them.

## `inspect_routing` was showing you other folders' routes

The read ignored the folder it was called from and returned the whole table. It
also swallowed a database error, so a failed read looked like an empty route
list.

What to do: nothing, but re-read anything you concluded from a route list — if
you decided a route was missing, the list may have been an error rather than an
answer.

## A send that did not happen is no longer reported as delivered

WhatsApp sends answered "queued, ok" when the socket was absent, so the platform
never got the message and the record said it had. Slack now also classifies four
more permanent errors as permanent instead of retrying them, and a rate limit
reaches you as a `⏳` notice rather than silence.

What to do: nothing. If a WhatsApp message "sent" recently never arrived, that
was this.

## Your product can ship its own tests

A product directory may now carry `eval/*.toml`, and arizuko's own eval harness
runs it against the live agent:

```
anteval run <target> --cases <data-dir>/groups/<folder>/eval
```

A case gives you one prompt and asserts what your reply must contain — so a
product can prove its own behaviour, not just that its files landed. The
reference product `helpdesk` ships four.

Two payloads now REFUSE instead of applying silently, because nothing consumed
them: a product's `migrations/` directory (no runner exists — put setup steps in
`CLAUDE.md` or a skill) and an `mcpServers` key in `settings.json` (register an
arizuko connector instead). `tasks.toml` is copied but still reaches nothing —
do not ship one expecting a scheduled task.

What to do: if you author products, read
`https://<your-host>/pub/arizuko/howto/build-a-product.html`.

## A lost message is now readable

A message that exhausted its delivery retries used to be countable and not
readable — you could see that something was lost, not what. `dead_letters` is a
resource now, on both faces: `list_dead_letters` / `get_dead_letter` as tools,
`/v1/dead_letters` for the operator, and a replay that puts the row back in the
outbound queue rather than opening a second delivery path.

What to do: nothing. If you reported a message as lost recently, it is probably
still there.
