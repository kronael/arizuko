# specs/RETIRED — every spec ID that no longer resolves

A spec ID is a pointer a reader follows. When a spec is deleted or renumbered
the pointers to it do not disappear — they survive in `BUGS.md`, in
`CHANGELOG.md`, in code comments, in the diary and in the web docs. This file
is where they land.

**The rule this file exists to enforce:** every `<phase>/<id>` in the tree
resolves either to a live file under `specs/<phase>/` or to a row below.
`tests/specrefs` checks it. A reference that resolves to neither is a broken
pointer and fails the build.

**Why it is not optional here.** Phases 6 and 7 have been renumbered three
times (`5acc0655` shifted 6-16 up to 7-17 on 2026-07-10; `819d43cd` cut the
corpus from 230 files to 161 on 2026-08-02). `specs/6/1` has been five
different specs and `specs/6/29` six. Without this table a stale `6/2` is not a
dangling pointer a reader notices — it is a live pointer to a spec about
something else. That is the failure BUGS `L43` measured and it is why the graph
is repaired before any further renumber.

A number in this table is **burnt**: never reuse it for new work. Numbering
continues past the highest ID the phase has ever held.
